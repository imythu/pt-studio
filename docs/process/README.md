# 工程流程与文档规范

> 适用范围：PT Studio 全部内核与插件的文档编写、评审、实现与验收。

## 1. 流程

```
需求分析 ──► 概要设计 ──► 详细设计 ──► 测试设计 ──► 评审 ──► 实现 ──► 测试 ──► 验收
 (SRS)        (HLD)        (LLD)        (TP)     (Review)  (Code)  (Test)  (Accept)
```

| 阶段 | 产出 | 通过标准 |
|---|---|---|
| 需求分析 | `01-需求规格说明书.md` | 功能需求、非功能需求均有编号且可验证；范围（含“不做什么”）明确 |
| 概要设计 | `02-概要设计说明书.md` | 架构、模块划分、对外接口（服务/事件/钩子/路由/MCP/前端插槽）清单完整，与平台契约一致 |
| 详细设计 | `03-详细设计说明书.md` | 每个接口有签名与错误码；每张表有 DDL；关键算法有伪代码；需求可追溯到设计 |
| 测试设计 | `04-测试计划.md` | 每条需求至少一个测试用例；含性能、安全、异常用例 |
| 评审 | `docs/reviews/` 下的评审记录 | 所有“阻断”级问题已关闭 |

## 2. 目录结构

```
docs/
├─ design/                 # 总体设计（架构级）
├─ process/                # 本规范与模板
├─ platform/               # 平台契约：内核、插件 API、事件/钩子/服务目录、数据库与编码规范
├─ plugins/<plugin-id>/    # 每个插件一个目录，含 01～04 四份文档
└─ reviews/                # 评审记录
```

## 3. 编号规则

| 对象 | 格式 | 例子 |
|---|---|---|
| 功能需求 | `FR-<插件缩写>-<3位序号>` | `FR-BONUS-001` |
| 非功能需求 | `NFR-<插件缩写>-<3位序号>` | `NFR-BONUS-001` |
| 测试用例 | `TC-<插件缩写>-<3位序号>` | `TC-BONUS-001` |
| 设计决策 | `DD-<插件缩写>-<序号>` | `DD-BONUS-1` |
| 错误码 | `<plugin_id>.<snake_case>` | `bonus.insufficient_balance` |

## 4. 通用约定

- 全部使用中文编写；代码、标识符、接口名使用英文。
- 服务名、事件名、钩子名、权限点、术语键必须与 `docs/platform/` 中的目录一致；需要新增时，在本插件文档的“对平台契约的新增”小节列出，由评审统一合入平台目录。
- 不得直接访问其他插件的数据表，跨插件只能通过服务、事件、钩子交互。
- 站点可变的叫法一律使用术语键，不写死。
- 每份文档开头填写：文档编号、版本、状态（草案/评审中/已批准）、作者、日期、修订记录。
