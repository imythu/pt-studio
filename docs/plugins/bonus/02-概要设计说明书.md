## 1. 设计目标与原则

1. **规则是数据**：公式、分档、行为奖励全部是版本化的数据，后台可改，不改代码、不迁移（design/05 §2.3 “数据驱动规则”）。
2. **表达式安全且确定**：自研受限表达式语言，只有纯函数；预编译为 AST，按版本缓存；同输入同版本结果逐位一致，才能回放重算。
3. **计算与记账分离**：事件处理只写本插件数据库（由 inbox 保证恰好一次）；记账由 cron 批量调用 ledger，持久化入账批 + 稳定幂等键保证恰好一次（kernel/03 §7.5）。
4. **以快照为输入**：做种收益只依据 accounting 的小时快照（实际做种秒数），不读取 tracker 内存状态；种子静态属性取自本插件镜像，避免逐事件跨插件调用。
5. **最小作用域**：只在 ledger 上持有本插件币种作用域；其他插件经 `ctx.bonus.award` 发放，bonus 负责限额与原因码。

## 2. 总体结构

### 2.1 位置

```
 accounting ──traffic.seeding_snapshot_taken（每用户每小时）──┐
 accounting ──traffic.swarm_stats_updated──┐                   │
 torrent ──torrent.created/status/tags/deleted──┐              │
 comments/forum/requests/subtitles/invite ──行为事件──┐        │
                                                    ▼        ▼ ▼
 ┌──────────────────────────────── bonus（WASM）─────────────────────────────────┐
 │ expr（解析/校验/求值）  rules（规则集版本、编译缓存）  facts（种子镜像）          │
 │ hourly（快照合并→求值→用户小时→待入账）  actions（行为奖励、每日上限、回收）      │
 │ posting（入账批 → ctx.ledger.transfer_batch）  recalc（回放差额→补发/回收）        │
 │ estimate（估算、明细）  service（ctx.bonus）  http  mcp  ui                        │
 └───────┬──────────────────────────────────────────────┬────────────────────────┘
         │ PG schema bonus                              │ ctx.ledger / ctx.terms / ctx.users / ctx.accounting
         ▼                                              ▼
  rule_sets / user_hours / accruals / postings …   ledger（币种 bonus、seed_points）
```

### 2.2 模块

| 模块 | 职责 |
|---|---|
| `expr` | 词法、Pratt 解析、静态检查（标识符、函数、类型、限额）、依赖分析（引用了哪些易变/用户变量）、求值 |
| `rules` | 规则集 CRUD、分档编译、发布（版本号、`effective_from`）、按时间选版本、编译结果缓存（kv + 每次调用内存） |
| `facts` | 种子事实镜像：事件更新、视图回填、批量读取 |
| `hourly` | 快照订阅：部分合并、资格判断、求值、封顶、取整、写用户小时与待入账、发布事件 |
| `actions` | 行为奖励规则、事件处理、每日上限、发放（直接 ledger.transfer）、回收与待回收重试 |
| `posting` | 入账批：选取到期待入账 → 汇总 → `transfer_batch` → 标记 |
| `recalc` | 重算任务、回放投递分流、差额预览、执行（补发/回收） |
| `estimate` | 实时估算（当前做种列表 × 当前规则）、明细、Redis 缓存 |
| `currencies` | init 时 define 术语、注册 ledger 币种 |
| `service` / `http` / `mcp` / `ui` | 接口层 |

## 5. 关键流程

### 5.1 小时结算

```
accounting ─traffic.seeding_snapshot_taken{user, period_start, parts…}─► bonus.on_seeding_snapshot
  （内核：inbox 去重，ordered by user key）
  replay=true 且有覆盖 period 的 running 重算任务？→ recalc 分流（§5.4）
  parts > 1：upsert snapshot_parts，未收齐 → 返回；收齐 → 合并
  user_hours 已有 (user, period_start) → 返回（防御）
  user = ctx.users.get(user)（状态、class）；资格判断
  ver = rules.version_at(period_start)；facts = torrent_facts 批量（缺失 → 视图）
  每种子：过滤 size ≥ min；求值种子级项 → 按项求和
  每币种：求用户级公式 → floor(v × 10^scale) → clamp(0, max_per_hour)
  INSERT user_hours；INSERT accruals（金额 > 0 的币种）
  publish bonus.hourly_settled（可关）
```

### 5.2 入账

```
cron post_accruals（:40）：
  续跑：postings WHERE state IN ('open','submitting') → 继续第 3 步
  1 计算到期周期边界 cutoff = floor_to_interval(now − 1h)
  2 每币种：INSERT postings(state=open, currency, cutoff)；
           UPDATE accruals SET posting_id = P WHERE currency=c AND posting_id IS NULL AND period_start < cutoff（分批 5 万）；
           INSERT posting_items(P, user, Σamount, Σhours)；state = submitting；commit
  3 for chunk(1000) of posting_items WHERE state='pending':
           ledger.transfer_batch([{from: None, to: user, amount, reason: "bonus.seeding",
                                   memo: "<周期>", idempotency_key: "post:<P>:<user>"}])
           逐笔结果 → posting_items(state=done|failed, entry_id, error)；commit
  4 全部完成 → postings.state = done（failed 笔在下次续跑重试，最多 5 次后人工处理）
```

### 5.3 行为奖励

```
comment.created{comment_id, target, author_id} ─► actions
  rules = action_rules WHERE event='comment.created' AND enabled
  for r: 条件求值（变量：target_kind、本日次数…）→ 每日上限（条件 UPSERT action_daily）
         ledger.transfer({to: author, amount, reason: "bonus.action_<r.code>", key: "<event_id>:<r.id>"})
         INSERT action_awards(ref = "comment:<id>", rule, entry_id, clawback_until)
         publish bonus.awarded
comment.deleted ─► 查 action_awards(ref) 未回收且 now ≤ clawback_until
         ledger.reverse(entry_id, "bonus.clawback", key "<event_id>:<award_id>", false)
         成功 → clawed；insufficient_balance → clawback_pending（retry_clawbacks 每日重试至 retry_days）
```

### 5.4 回放重算

```
管理员：POST /admin/recalcs {from, to, target_version, currencies, note} → recalc_jobs(state=awaiting_replay)
   前端提示 sysop（或具备 kernel.events.replay 的管理员）调用
   POST /api/kernel/v1/events/replays {subscription: "bonus.on_seeding_snapshot",
        type: "traffic.seeding_snapshot_taken", from, to, force: true}，记录 replay_id → recalc_jobs.state = replaying
回放投递（delivery.replay = true）：
   job 覆盖 period_start → 用 target_version 求值（与 5.1 相同算法，facts 取当前镜像）
   UPSERT recalc_items(job, user, period_start, currency, old = user_hours 中原值, new)
   不写 user_hours / accruals，不发事件
管理员查看预览（Σ差额、受影响用户、示例）→ POST …/applications
   延迟任务 recalc_apply_step 按用户分批：Σ(new − old) > 0 → ledger.transfer(issue)，< 0 → ledger.transfer(burn)，
   幂等键 "recalc:<job>:<user>:<currency>"；burn 余额不足 → 仅回收可用部分并记录缺口（DD-BONUS-8）
```

无重算任务覆盖的回放投递按正常结算处理（用户小时已存在则跳过），用于补齐漏算（FR-BONUS-024）。

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论 | 理由 |
|---|---|---|---|---|
| DD-BONUS-1 | 公式配置方式 | A 固定公式调参数（NexusPHP）；B 有序条件项（UNIT3D）；C 通用安全表达式；D 嵌入脚本（Rhai/Lua） | C，并提供 B 风格的分档表编译为 C | A 不够灵活；B 难以表达 arctan 递减；D 体积大、难以限制资源且难以证明确定性；C 可做静态检查、限额和确定性求值 |
| DD-BONUS-2 | 表达式求值类型 | A 定点整数；B f64，最后取整 | B | 公式含 exp/atan/sqrt，定点实现复杂；WASM 的 f64 与 `libm` 纯 Rust 实现确定；只在最后一步转为整数最小单位（database.md §4 约束的是存储） |
| DD-BONUS-3 | 求值两层结构 | A 只有用户级公式（变量为聚合值）；B 种子级项 + 用户级公式 | B | NexusPHP 的 A 值、UNIT3D 的逐种子分档都需要逐种子求值；用户级的非线性（arctan、封顶）必须在求和之后 |
| DD-BONUS-4 | 何时调用 ledger | A 每个事件即时 `transfer`；B 写待入账，cron 批量入账 | B，周期可配（默认 1 小时） | 事件处理只有数据库副作用，恰好一次由 inbox 保证；批量接口每笔约为单笔开销的 1/10；周期可按 DD-LED-8 调大以降低流水量 |
| DD-BONUS-5 | 入账幂等键 | A `<user>:<period>`；B 入账批 ID + 用户 | B | 迟到的用户小时（如部分快照迟到、漏算补齐）会在后续批中入账，A 无法表达“同一周期第二次入账”；B 的批在发起调用前已持久化，重试必然复用 |
| DD-BONUS-6 | 种子属性来源 | A 每事件调 `ctx.torrents.get_many`；B 每事件读视图；C 本插件镜像 + 视图兜底 | C | 70 条/秒 × 80 种子，A/B 在峰值造成 1 万次/秒跨插件读取；镜像由事件维护，创建时间、体积不变，适合回放 |
| DD-BONUS-7 | 回放重算的数据来源 | A 自存每小时每种子输入；B 依赖内核事件日志回放 | B | A 每天约 5 亿行；事件日志已经保存了原始快照（需按 accounting N-2 设置保留期 ≥ 30 天）；代价是重算需要 sysop 触发回放 |
| DD-BONUS-8 | 重算差额为负且余额不足 | A 允许负余额；B 只回收可用部分并记录缺口；C 放弃回收 | B | ledger 只允许管理员形成负余额；缺口在报告中可见，由管理员决定是否经 ledger 后台处理 |
