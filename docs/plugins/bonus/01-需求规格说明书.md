## 1. 引言

### 1.1 目的

定义 `bonus` 插件（WASM，提供 `ctx.bonus`）的需求。bonus 按站点自定义的公式计算“做种魔力值”（及可分开的“做种积分”），对发种、评论、求种应求等行为发放奖励，并把全部发放通过 `ctx.ledger` 记账。bonus 只负责“发多少、发给谁、为什么”，记账正确性由 ledger 保证（D13）。

### 1.2 范围

| 包含 | 不包含 |
|---|---|
| 注册本插件的币种（默认 `bonus` 魔力值、`seed_points` 做种积分；站点可追加），币种名称走术语键 | 余额、冻结、转账、冲正的实现（ledger） |
| 安全表达式语言：解析、静态校验、限额、确定性求值 | 商城、彩票、签到等消费与奖励（shop、lottery、checkin） |
| 规则集（Rule Set）：版本化、草案/发布/退役、生效时间；种子级表达式 + 用户级表达式；分档（UNIT3D 风格）规则 | 流量（上传/下载量）计算与倍率（accounting） |
| 订阅 `traffic.seeding_snapshot_taken` 按小时计算做种收益，多部分快照合并 | 作弊判定（anticheat）；bonus 只读取用户状态决定是否发放 |
| 待入账（accrual）与批量入账（`ledger.transfer_batch`），入账周期可配 | 求种悬赏的冻结与支付（requests 直接用 ledger） |
| 行为奖励：发种审核通过、评论、发帖、应求、字幕、邀请注册等；每日上限；删除回收 | |
| 回放重算：基于事件回放与规则版本的预览、差额补发/回收 | |
| 时薪估算（用户页“每小时收入”）与按种子明细 | |
| `ctx.bonus.award` 供其他插件以本插件币种发放（作用域 `award`） | |
| 用户页、后台规则编辑器（含试算）、MCP `get_my_bonus` | |

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 魔力值 | 可消费的虚拟货币，币种代码 `bonus`，术语键 `bonus.currency` |
| 做种积分 | 只累计、默认不可消费/转账的积分，币种代码 `seed_points`，术语键 `bonus.seed_points`；常用于等级规则 |
| 快照 | accounting 每小时发布的 `traffic.seeding_snapshot_taken`：某用户上一小时每个种子的做种秒数、体积、做种人数 |
| 用户小时（user-hour） | (user_id, period_start) 唯一的计算单元 |
| 规则集 | 一组版本化的计算定义：种子级项（torrent terms）、用户级公式（每个币种一条）、上限、适用条件 |
| 种子级项 | 对每个做种的种子求值并按用户求和的表达式，如 NexusPHP 的 A 值 |
| 用户级公式 | 以种子级项之和与用户变量为输入、输出某币种本小时金额（显示单位）的表达式 |
| 待入账（accrual） | 已算出但尚未写入 ledger 的金额；按入账周期批量记账 |
| 入账批（posting） | 一次批量记账的持久化记录，保证崩溃后以相同幂等键重试 |
| 重算任务（recalc） | 用新规则版本对历史用户小时重新求值，得到差额并（经确认后）补发/回收 |
| 易变变量 | 求值时取当前值而非快照时刻值的变量（如 leechers、completed），回放时不保证与原值一致 |

### 1.4 参考资料

- 平台：`plugin-api.md`（§2.2 bonus world 示例、§4 清单示例）、`catalog/services.md`（`ctx.bonus`、`ctx.ledger`、`ctx.accounting`、`ctx.terms`）、`catalog/events.md` §4.4/§4.5、`kernel/03` §7.5（inbox）、§7.7（回放）、§9（cron、延迟任务）。
- 依赖插件：`docs/plugins/ledger/`（`transfer_batch`、`reverse`、DD-LED-8 建议合并发放）、`docs/plugins/accounting/`（快照载荷 LLD §2.2：含 `period_start`、`batch_id/part/parts`）、`docs/plugins/terms/`（`define`/`retire`）。
- NexusPHP（`include/functions.php` 的做种魔力计算，阅读思路、未复制代码）：A = Σ(1 − e^(ln0.1·周龄/T0)) · GB · (1 + √2·e^(ln0.1·(做种人数−1)/(N0−1)))；每小时 = B0·(2/π)·arctan(A/L) + P·min(做种数, MAX)；另有“官方种子加成”“零魔力标签”“勋章加成”“捐赠者倍数”“后宫加成（被邀请人做种积分之和）”；做种积分与魔力值同源但分开累计；行为奖励（发种、评论、上传字幕、求种应求）为固定值并可在删除时扣回。
- UNIT3D（`bon_earnings` / `bon_earning_conditions` 表与 `AutoBonAllocation` 命令，阅读思路）：管理员配置有序的“收益项”，每项有变量（1、age、size、seeders、seedtime …）、乘数、`append`/`multiply` 操作和若干条件；每小时按当前 peers 计算并直接 `UPDATE users SET seedbonus`。
- Gazelle / OPS（`Task/UpdateUserBonusPoints`、`User/Bonus::userTotals`，阅读思路）：数据库函数 `bonus_accrual(size, seedtime, seeders)` × 分类系数 `bonus_scale`，定时任务批量加分；BonusPool（活动奖池）。

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | WASM（站点规则，D5；热路径不在此，按事件与 cron 运行） |
| 提供服务 | `ctx.bonus@0.1.0` |
| 依赖服务 | `ctx.ledger`（必需，作用域 `currency:bonus`、`currency:seed_points` 等）、`ctx.accounting`（必需，`read`）、`ctx.users`（必需）、`ctx.terms`（必需，`define`）、`ctx.torrents`（必需，行为奖励取上传者）、`ctx.rbac`（可选，用户变量 `has_role`）、`ctx.levels`（可选）、`ctx.medals`（可选，勋章加成，见 HLD §7） |
| 只读视图 | `torrent.v_torrent_public`、`accounting.v_snatch` |
| 消费方 | shop、lottery、checkin（展示、作用域外发放可走 `award`）、levels（读做种积分余额）、ai-assistant / MCP |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 普通用户 | 查看魔力值/做种积分余额（来自 ledger）、每小时收入估算、按种子的收益明细、规则说明；在 MCP 中问“我现在每小时多少魔力” |
| 管理员 | 编辑规则集（表达式或分档表），用样例数据或真实用户试算，发布新版本并指定生效时间；配置行为奖励与每日上限；配置入账周期；发起重算并预览差额 |
| sysop | 为重算触发内核事件回放（`kernel.events.replay`） |
| 其他插件 | requests / medals / forum 活动等以 `ctx.bonus.award` 发放魔力值（无需自持币种作用域） |
| 运维 | 观测每小时处理量、入账延迟、表达式错误率 |

### 2.3 现有开源 PT 程序的做法调研

| 项目 | 做法 | 优点 | 缺点 | 采纳 | 改进 |
|---|---|---|---|---|---|
| NexusPHP | 固定形状的公式（T0、N0、B0、L、P、MAX 六个参数可配）；按 peers 实时计算；cleanup 定时批量 `UPDATE users SET seedbonus`；做种积分与魔力分列；行为奖励固定值；官方/零魔力标签、勋章加成、捐赠者倍数、后宫加成 | 公式经过多年验证，arctan 使收益边际递减、抑制“囤大包”；参数可调 | 只能调参数不能改形状；按 cleanup 时刻的 peers 计算（cleanup 间隔内上下线不准）；批量 UPDATE 不入账、无法对账与回放；浮点存余额 | 默认规则集即 NexusPHP 公式（参数化）；做种积分独立币种；官方加成、零魔力标签、捐赠者倍数、后宫加成作为可选变量/函数 | 公式形状可自定义（表达式）；以 accounting 的小时做种秒数为输入（按实际做种时长折算）；全部入账、可回放重算；整数最小单位 |
| UNIT3D | 有序收益项 + 条件 + append/multiply；后台可视化编辑；每小时按 active peers 计算（peer 需存在 30 分钟以上） | 可配置性强，非程序员可改；分档直观（Dying/Legendary/Huge …） | 生成 SQL 片段在数据库求值（耦合表结构）；只看当前 peers；不入账；规则修改无版本，无法重算历史 | 分档规则模式（编译为表达式）；“保种奖励”（最后一个做种者、老种）预设 | 规则版本化、按小时快照求值、确定性回放；分档名称走术语键 |
| Gazelle / OPS | 数据库函数按体积、做种时长、做种人数计算，按分类系数缩放；定时任务批量加分；BonusPool 活动奖池 | 分类系数简单有效 | 公式写死在 SQL 函数；改公式要迁移 | 分类/类型系数（`type("music")` 函数） | 公式在插件配置中，无需迁移 |
| TorrentPier / Luminance | 简单的“每做种一个种子每小时 X 点” | 简单 | 不区分体积、稀缺度 | — | 作为最简预设 |

### 2.4 约束与假设

1. 输入来自 `traffic.seeding_snapshot_taken`（v1，key `user:<id>`，16 分区，订阅 `ordered = true`）；单用户单小时可能拆成多部分（`batch_id/part/parts`），须合并后才能求用户级公式（arctan 非线性）。
2. 每次调用新实例、一个事务；事件订阅的数据库副作用由 inbox 保证恰好一次，调用 ledger 必须自带幂等键。
3. 体量：30 万用户中约 25 万每小时有做种，平均 80 个种子/人；即约 70 条/秒、峰值 140 条/秒的事件，每条求值约 80 次种子级表达式。
4. 金额在表达式中以“显示单位”的 f64 计算，最后按币种 scale 向下取整为最小单位整数；WASM 浮点运算与 `libm` 实现确定，同一输入同一规则版本结果逐位一致。
5. 快照事件日志的保留期决定可重算的时间范围（建议 ≥ 30 天，见 accounting HLD §7 N-2）。
6. 不做多租户（D6）。

| FR-BONUS-023 | 回放重算 | 管理员创建重算任务（时间范围、目标规则版本、币种）；sysop 触发对订阅 `bonus.on_seeding_snapshot` 的强制回放；回放投递在任务范围内只写差额预览；确认后按用户合并补发（发行）或回收（回收，不足则记缺口）；任务可取消 | P1 | 预览差额与离线计算一致；执行两次不重复补发 |
| FR-BONUS-024 | 漏算补齐 | 不带 `--force` 的回放（或死信重投）对未处理过的快照正常结算，已处理的跳过 | P0 | 删除某小时 inbox 外的结算记录模拟漏算后，回放补齐且不重复 |
| FR-BONUS-025 | 种子信息镜像 | 维护种子事实镜像（体积、类型、创建时间、上传者、标签、删除标记、leechers、completed），来源为 torrent 事件、`traffic.swarm_stats_updated` 与视图回填 | P0 | 新种 1 分钟内进入镜像；缺失时回退读视图 |
| FR-BONUS-026 | 用户删除 | `user.deleted`（purge）：删除该用户的用户小时、待入账（未入账部分作废）、行为奖励记录中的个人数据；ledger 流水由 ledger 处理 | P1 | purge 后本插件表无该用户行 |
| FR-BONUS-027 | 前端 | `user.profile.stats`（余额与每小时收入）、`nav.user_menu` 入口、`/p/bonus/` 用户页（余额、收益明细、规则说明）、后台规则编辑器、行为奖励、重算、入账状态页 | P1 | |
| FR-BONUS-028 | MCP | `get_my_bonus`：余额（各币种）、每小时收入估算、最近收支（经 ledger） | P1 | 输出经术语渲染 |
| FR-BONUS-029 | 规则审计 | 规则集保存/发布/退役、行为奖励修改、重算创建/执行写审计 | P0 | 审计含版本号与差异摘要 |
| FR-BONUS-030 | 每小时上限与全局开关 | `max_per_hour`（每币种）、全局暂停开关（暂停时快照照常记录为“暂停”并可在恢复后由重算补发） | P1 | 暂停期间待入账为 0，恢复后重算可补发 |

## 4. 非功能需求

| 编号 | 类别 | 描述 | 指标 |
|---|---|---|---|
| NFR-BONUS-001 | 性能 | 单个快照事件处理（80 个种子、默认规则） | p99 ≤ 30 ms（含 SQL），吞吐 ≥ 300 条/秒（8 并发分区消费） |
| NFR-BONUS-002 | 性能 | 表达式求值 | 每次种子级求值 ≤ 2 µs（预编译 AST） |
| NFR-BONUS-003 | 时效 | 小时结算在快照发布后完成 | 整点后 60 分钟内完成 99% 用户；入账延迟 ≤ 入账周期 + 15 分钟 |
| NFR-BONUS-004 | 一致性 | 恰好一次：同一用户小时只入账一次；ledger 幂等键稳定 | 对账（本插件已入账合计 = ledger 中 `bonus.seeding` 合计）差异 0 |
| NFR-BONUS-005 | 确定性 | 同一快照、同一规则版本、无易变变量时结果逐位一致 | 回放重算差额为 0 |
| NFR-BONUS-006 | 安全 | 表达式不能执行任意代码、不能读写数据；规则只有 `bonus.rules.manage` 可改；`award` 作用域最小化 | 安全测试通过 |
| NFR-BONUS-007 | 容量 | 用户小时记录每天约 600 万行，按日分区，保留 `hourly.retention_days`（默认 90） | 单日分区 ≤ 1 GB |
| NFR-BONUS-008 | 可观测性 | 处理量、延迟、表达式错误、跳过原因、入账批状态、重算进度 | 见 LLD §8 |
| NFR-BONUS-009 | 隐私 | 不申请敏感能力；事件不含个人文字；匿名发种的奖励不在公开处展示种子 | — |
| NFR-BONUS-010 | 可配置性 | 公式、分档、行为奖励、入账周期、上限全部热更新（规则以发布版本生效） | 无需重启 |
