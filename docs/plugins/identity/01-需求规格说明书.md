## 1. 引言

### 1.1 目的

定义 `identity` 插件（Native，提供 `ctx.auth`、`ctx.users`、`ctx.rbac`）必须实现的功能与质量要求，作为概要设计、详细设计、测试计划和实现验收的依据。

### 1.2 范围

**包含**：

- 账户：注册（通过 `user.before_register` 钩子把邀请、答题、验证码、名额等策略交给 G2 插件）、用户名规则与改名、资料、账户状态与限制（封禁、禁止下载、待验证/待审核、删除与个人数据清除）。
- 认证：密码登录（Argon2id）、登录失败限流与临时锁定、二次验证（TOTP、恢复码、WebAuthn 凭据，WebAuthn 也可无密码登录）、会话（多副本共享存储、空闲/绝对超时、列出与撤销）、近期重新验证。
- 凭据：个人 API token（`pts_`）、MCP token（`ptm_`，由 mcp 插件经 `ctx.auth.issue_token` 签发）、订阅 key（`ptf_`，供 rss、crossseed-api 的 `?key=` 只读路由）；全部 scope 化、只存哈希。
- tracker passkey：生成、展示、重置、吊销、历史，及通过事件与 tracker-bridge 同步。
- 邮箱：验证、修改、找回密码（经“挑战”机制 + notify 投递）。
- 登录风控：失败限流、新设备 / 新地区登录提醒、IP 记录与隐私处理（保留期、截断）。
- RBAC：权限点登记（由各插件声明）、内置角色、插件动态角色、管理员自定义角色、角色授予（含到期）、按等级（class）绑定角色的机制、用户级权限覆盖、账户状态对权限的屏蔽。
- 审计与用户可见的安全事件记录。

**不包含**：

- 邀请码、邀请树、答题、验证码、邮箱域名白名单、注册名额（G2：invite、registration-policy）。
- 等级规则、升降级、保号（levels）；identity 只存 `class_id` 并提供“等级→角色”绑定机制。
- 分享率、H&R、作弊判定等“何时封禁/禁止下载”的策略（ratio-policy、hnr、anticheat 等），identity 只提供带来源的限制机制。
- 邮件、Telegram 等实际投递（notify）；identity 只产生挑战并发布事件。
- 向 pt-tracker 写 `trk:*` 键（tracker-bridge）；identity 只发布事件并提供 passkey 读取服务。
- MCP 协议、OAuth 授权页与确认流程（mcp）；identity 只存储与校验 MCP token。
- 头像图片存储（只存 URL；上传由前端经对象存储完成，后续可由独立插件提供）。
- 流量数据（accounting）、余额（ledger）。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| passkey | **tracker passkey**：announce URL 中的 32 位小写十六进制密钥（平台 README Q12、security.md §4） |
| WebAuthn 凭据 | FIDO2/WebAuthn 公钥凭据（常被称作“通行密钥”）；本项目一律不称 passkey |
| 会话 | 浏览器登录状态，cookie `__Host-pt_session` 中保存随机令牌，服务端保存其哈希 |
| token | 个人 API token / MCP token / 订阅 key 的统称，均为 Bearer 或查询参数凭据 |
| 挑战（challenge） | 一次性、限时的验证材料：邮箱验证链接、找回密码链接、改邮箱确认链接 |
| 限制（restriction） | 作用在账户上的状态限制（`ban`、`leech_disabled`、`pending`），带来源、原因与到期时间；有效状态由全部生效限制合成 |
| class / 等级 | 由 levels 插件决定的用户等级编号 `class_id`；叫法用 `levels.class.<id>.name` 术语 |
| 角色（role） | 权限点集合；内置角色、插件动态角色 `<plugin_id>:<name>`、自定义角色 `custom:<name>` |
| 近期重新验证（reauth） | 会话在 N 分钟内输入过密码或通过 2FA |
| IDN | identity 的文档编号缩写 |

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | **Native**（Rust crate `pt-plugin-identity`）。理由：每个 HTTP 请求都经过 `ctx.auth.authenticate` 与 `ctx.rbac.check`，属于热路径；需要 Argon2、AES-GCM、WebAuthn 等原生密码学库与进程内缓存 |
| 提供服务 | `ctx.auth@0.1.0`、`ctx.users@0.1.0`、`ctx.rbac@0.1.0`（single，site.toml `[services]` 选定） |
| 依赖服务 | 只依赖内核服务（sql、redis、events、hooks、jobs、audit、time、random、terms、config、metrics）。**不依赖任何业务插件**：内核在依赖图中让 identity 最先激活，而 notify、tracker-bridge、levels 等都依赖 `ctx.users`，若 identity 反向依赖会成环（kernel/03 §2.3） |
| 与其他插件的协作方式 | 对上游：钩子（`user.before_register`、`user.before_login`、`user.before_rename`）；对下游：事件（`user.*`）+ 下游调用 identity 服务拉取敏感材料（notify 拉取挑战投递内容，tracker-bridge 拉取 passkey） |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 访客 | 注册（填写 G2 插件扩展的表单字段）、登录、找回密码、验证邮箱 |
| 普通用户 | 改密码 / 邮箱 / 资料；开启 TOTP、登记 WebAuthn 凭据；查看与撤销会话；查看、重置 passkey；签发 API / 订阅 token；查看自己的安全事件 |
| 版主（moderator） | 查看用户详情、封禁 / 禁止下载 / 解除自己施加的限制、改名 |
| 管理员（admin） | 查看敏感信息（邮箱、IP，留审计）、按 IP 查同 IP 账户、重置他人 2FA / passkey、强制下线、删除用户、授予低于自己的角色 |
| 站务（sysop） | 角色与权限配置、全部操作 |
| 其他插件 | levels 改等级并配置等级角色；ratio-policy / hnr / anticheat 施加或解除自己的限制；mcp 签发 MCP token；notify 投递挑战；tracker-bridge 同步 passkey 与状态；torrent 下载时注入 passkey |
| 内核 | 网关鉴权（`authenticate`）、权限检查（`check`）、启动时登记权限点 |

### 2.3 现有开源 PT 程序的做法调研

| 主题 | 项目与做法 | 优点 | 缺点 | 我们采纳 / 改进 |
|---|---|---|---|---|
| 等级与权限模型 | **NexusPHP**：单一整数 `class`（0 Peasant … 9 Nexus Master、10 VIP、11 Retiree、12 Uploader、13 Moderator … 16 Staff Leader），权限判断写成 `get_user_class() >= UC_MODERATOR` 并把阈值放在站点设置中 | 简单直观，站点可在后台调整“某功能所需最低等级” | 等级（凭流量晋升）与职务（发布员、管理员）混在一条线上：发布员必须“高于”所有普通等级；比较散落在代码中，难以审计；无法给个别用户单独授权 | **拆开两个维度**：`class_id` 只表示等级（levels 决定），职务用角色表示；权限一律是命名权限点，通过 `ctx.rbac.check` 检查，不做数值比较 |
| | **UNIT3D**：`groups` 表有 `level`（排序）和十几个布尔列（`is_modo`、`is_admin`、`can_upload`、`can_invite`、`can_comment`、`is_immune`、`is_freeleech`…）；`autogroup` + `min_uploaded`/`min_ratio`/`min_age` 实现自动升降；用户另有 `can_download` 等列 | 组即模板，后台可视化配置；自动升级条件数据化 | 新增权限需改表结构（加列），插件无法扩展；组既是等级又是职务，一人只能一组；员工只能处理 `level` 低于自己的用户这条规则分散在各控制器 | 采纳“组的权限后台可配”和“只能管理低于自己的人”；改进为：权限点由插件**登记**（无需 DDL），一人可有多个角色；“级别比较”集中在 identity 的 `rank` 规则中（DD-IDN-6） |
| | **Gazelle（OPS）**：主 class（`permissions.Level`）+ **secondary class**（如 Donor、FLS、Interviewer，可叠加）+ 每用户 `CustomPermissions`（序列化的增删覆盖） | 主次 class 叠加最灵活；可以对个人单独加减权限 | 序列化数组难以查询和审计；secondary class 与主 class 的冲突规则隐晦 | 采纳“多角色叠加 + 用户级覆盖（allow / deny，deny 优先，可到期）”；覆盖存为普通表行，可查询、审计 |
| | **Luminance**（Gazelle 分支，公开资料）：引入更细的权限组与按用户权限 | 细粒度 | 继承 Gazelle 的音乐中心模型，已停更 | 同上 |
| 账户状态 | **NexusPHP**：`enabled`（yes/no）+ `downloadpos`（禁止下载）+ `leechwarn` 等独立列，由 cleanup 脚本按分享率自动加、到期自动解 | 字段直接，tracker 判断简单 | 多个来源（分享率、管理员、作弊）写同一列：自动任务“解除分享率警告”时可能把管理员施加的禁止下载一起解掉 | **限制按来源分层**（DD-IDN-3）：每条限制记录来源插件 / 管理员、原因、到期；某来源只能撤销自己的限制；有效状态 = 最严重的生效限制 |
| | **UNIT3D**：`bans` 表记录封禁原因与解封原因；`can_download` 布尔 | 封禁有历史 | 禁止下载无历史，同样有覆盖问题 | 所有限制都有历史 |
| | **Gazelle**：`Enabled` + `can_leech`，`AutoEnable` 让被禁用户用邮箱申请恢复 | 自助恢复流程降低客服成本 | — | 自助申诉留给 reports/moderation 插件，identity 预留 `restriction.appealable` 字段（P2） |
| 密码 | **NexusPHP**：`sha256(secret . sha256(password))`（更早为 md5 加盐）；**UNIT3D**：Laravel bcrypt；**Gazelle**：PHP `password_hash`（bcrypt），并保存密码修改历史 | bcrypt 尚可 | NexusPHP 的快速哈希可被 GPU 暴力破解；均无泄漏密码检查 | Argon2id（security.md §3）；支持导入 NexusPHP / bcrypt 旧哈希，首次登录成功即重哈希；离线泄漏密码表检查 |
| passkey | **NexusPHP**：`md5(username . 当前时间 . passhash)`，并且注册了**以 passkey 作为 API 鉴权**的守卫 | 实现简单 | 由可猜测的输入派生、熵不足；passkey 一旦当 API 凭据，泄漏面扩大到全站接口 | 128 位 CSPRNG；passkey **不得**用于 API 鉴权（api.md §8），RSS/辅种用独立的订阅 key |
| | **UNIT3D**：`md5(random_bytes(60) . password)`；`passkeys` 表保存历史（`deleted_at`）；员工可重置，仅限 level 低于自己的用户；先调用 announce 服务 `addUser` 再写数据库事务 | 有历史、可追查泄漏 | 先改 tracker 后提交 DB：DB 回滚时 tracker 与 DB 不一致；明文存储 | 采纳历史与“员工只能处理低级用户”；改进为**事务内写库 + 发布事件**（outbox），tracker-bridge 消费后同步，DB 与 tracker 最终一致；DB 中加密存储并以 HMAC 查找 |
| | **Gazelle**：`users_history_passkeys` 记录新旧 key、时间、IP；`Tracker::modifyPasskey(old, new)` 通知 Ocelot | 原子“旧换新”消息，tracker 立刻失效旧 key | 依赖 tracker 直连 | 采纳“同步消息含旧 key 以便删除”的思想：tracker-bridge 通过 `passkey_material` 拿到当前与近期退役的 key |
| 2FA | **NexusPHP**：TOTP（`two_step_secret`），新版本支持 WebAuthn（其代码里称 passkey，正是我们要避免的命名混淆）；**UNIT3D**：TOTP + 恢复码；**Gazelle**：TOTP + 恢复码（`burnRecovery`），密钥存库 | 覆盖主流需求 | 密钥多为明文；缺少 TOTP 码防重放；少有“敏感操作重新验证” | TOTP 密钥 AES-256-GCM 加密；记录最近使用的时间步防重放；恢复码哈希存储；敏感操作要求近期重新验证；WebAuthn 可作第二因素或无密码登录 |
| 登录风控 | **NexusPHP** `loginattempts`：按 IP 计失败次数，超过 `maxloginattempts` 封 IP；**Gazelle** `LoginWatch`：按 IP 记录并临时封禁、成功后清零；**UNIT3D** `failed_login_attempts` 表 | 有效抵御单 IP 暴力破解 | 只按 IP：分布式撞库无效；按用户名硬锁定会被用来恶意锁死他人账户 | 同时按 IP 与按用户名计数，采用**递增延迟 + 短时软锁**，已知设备（设备 cookie）不受用户名软锁影响；错误信息不区分用户不存在 / 密码错误 |
| IP 记录 | **Gazelle**：站点 IP、tracker IP、API IP 分别记录历史并附 ASN；**NexusPHP**：`iplog` 表永久保留 | 便于查多号、追查盗号 | 永久保留明文 IP，隐私风险大 | 记录登录/会话 IP 与 ASN/国家；默认 90 天后截断为 /24、/48，再到期删除；查看需 `identity.users.read_sensitive` 并写审计；用户可查看自己的登录记录 |
| 会话 | **NexusPHP**：cookie 中保存 uid + 由 passhash 派生的值；**UNIT3D/Gazelle**：框架会话 / `users_sessions` 表，可在设置页查看并注销 | Gazelle 可逐个注销 | NexusPHP 方案改密码前无法单独注销会话 | 服务端会话（PG 持久 + Redis 缓存），cookie 只含 256 位随机令牌；列出、逐个撤销、全部撤销；改密码自动撤销其他会话 |
| API / RSS key | **UNIT3D**：`rsskeys`、`apikeys` 表，可重置并保留历史；**Gazelle**：`UserToken`（API token）| 与 passkey 分离 | UNIT3D 的 API token 无 scope、无过期 | 统一的 token 机制：类型（api/mcp/feed）+ scope + 到期 + 最近使用时间，只存 SHA-256 |
| 注册策略 | 三者都把邀请、开放注册、名额写在注册控制器里 | — | 策略与身份耦合，站点改规则需改代码 | 注册策略全部经 `user.before_register` 钩子交给 G2 插件（design/01 原则 1） |
| Arcadia（Rust，AGPL，早期） | 公开资料显示采用现代 Rust 后端与 JWT 风格认证 | 技术栈接近 | 早期、AGPL | 只参考整体思路，不读不抄代码 |
| TorrentPier（公开资料） | 论坛式 tracker，用户组 + 论坛权限 | 论坛权限细 | 与论坛深度耦合 | 论坛权限由 forum 插件以权限点 + 角色实现 |

### 2.4 约束与假设

- 遵守平台契约：Native 插件，服务签名以 catalog/services.md 概要为准；不读其他插件的表；跨插件交互只经服务、事件、钩子、已登记视图。
- 内核网关对 `Principal` 缓存 5 s（kernel/03 §8.2）：撤销会话、封禁、撤销 token 的生效延迟上限 = 5 s + identity 自身缓存失效时间（本插件保证自身缓存在写入时同步删除）。
- 钩子处理者不能出站 HTTP：外部验证码（hCaptcha 等）无法在 `user.before_register` 中校验，由 registration-policy 自行设计本地方案，不属于本插件。
- identity 不能 `requires` 任何依赖 `ctx.users` 的插件（避免依赖环），因此邮件投递、tracker 同步一律走“事件 + 下游拉取”。
- 密钥：`PT_SECRET_KEY`（内核 secret key）经 HKDF 派生 identity 专用子密钥；密钥轮换见详细设计。
- 规模假设：注册用户 ≤ 100 万，日活 ≤ 30 万，峰值 API 5 万 rps（全部副本合计），峰值登录 50 次/s。
- PostgreSQL ≥ 16、Redis ≥ 7.2。

## 3. 功能需求

### 3.1 注册与用户名

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-IDN-001 | 注册提交 | 访客提交用户名、密码、邮箱、语言、可选邀请码及扩展表单 `form{}`；identity 完成格式校验与唯一性检查后，触发 `user.before_register` 钩子，依据合并后的 `attributes` 创建用户 | P0 | 合法请求创建用户并返回 201；钩子拒绝时返回处理者的错误码且不创建用户 |
| FR-IDN-002 | 用户名规则 | 长度 3～20（可配置）；NFC 规范化；允许字母、数字、`_`、`-`、`.` 及可配置的 CJK 字符；拒绝控制字符、首尾标点；混淆字符检查（UTS #39 skeleton）；大小写不敏感唯一；保留名单（admin、sysop、system 等，可配置） | P0 | `Admin`、`admin`、`аdmin`（西里尔 а）与已存在的 `admin` 视为冲突；保留名被拒 |
| FR-IDN-003 | 邮箱规则与唯一 | 邮箱规范化（小写域名，可配置是否小写本地部分）；全站唯一（含未验证）；长度 ≤ 254 | P0 | 重复邮箱返回 `identity.email_taken`；查询接口不回显邮箱 |

| FR-IDN-111 | 角色到期 | 到期的角色授予与权限覆盖自动失效（延迟任务 + 定时兜底） | P1 | |
| FR-IDN-112 | 级别（rank）规则 | 员工只能对“最高内置角色低于自己”的用户执行封禁、改名、重置 passkey/2FA 等操作；sysop 例外 | P0 | moderator 封禁 admin 被拒 `identity.insufficient_rank` |

## 6. 外部接口需求概述

- **服务**：`ctx.auth`、`ctx.users`、`ctx.rbac`（WIT `pt:auth@0.1.0`、`pt:users@0.1.0`、`pt:rbac@0.1.0`）。
- **事件**：发布 `user.*` 全部 15 个目录事件，另申请 `user.challenge_issued`、`user.restriction_changed`（见 HLD §7）。不订阅业务事件。
- **钩子点**：拥有 `user.before_register`、`user.before_login`、`user.before_rename`。
- **HTTP**：`/api/p/identity/v1/...`（登录、注册、会话、2FA、passkey、token、资料、管理）。
- **MCP**：`get_my_profile`、`admin_inspect_user`、`admin_set_user_status`。
- **只读视图**：`identity.v_user_public`、`identity.v_user_email`（敏感）。
- **前端**：页面 `/p/identity/*`、后台 `/admin/p/identity/*`，插槽 `user.settings.tabs`、`nav.user_menu`、`nav.admin`、`admin.dashboard.widgets`。
