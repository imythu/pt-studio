## 1. 设计目标与原则

1. **只提供机制，不决定策略**：谁能注册（G2）、何时升级（levels）、何时禁止下载（ratio-policy / hnr / anticheat）都不在 identity；identity 提供钩子、带来源的限制、等级→角色绑定、作用域化的写服务。
2. **热路径快且无状态**：`authenticate` 与 `check` 每个请求都会调用。会话与角色走 Redis + 进程内缓存，PostgreSQL 为唯一事实来源；任何副本可服务任何请求。
3. **敏感数据最小暴露**：passkey、TOTP 密钥加密存储；会话令牌、token、恢复码、挑战令牌只存哈希；事件只带 ID；敏感读取经授权检查并审计。
4. **处于依赖图根部**：identity 不 `requires` 任何业务服务，下游协作一律“事件 + 下游拉取”，避免依赖环。
5. **一致性靠事务 + outbox**：所有状态变更与 `user.*` 事件同事务提交；跨插件副作用（tracker 同步、发邮件）由消费方幂等完成。
6. **撤销优先**：凡是会降低权限的写入（封禁、撤销会话 / token / 角色）在提交后立即删除相关缓存，生效延迟只受内核 5 s principal 缓存约束。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
             浏览器 / 脚本 / AI 客户端
                     │ cookie / Bearer pts_ ptm_ / ?key=ptf_
                     ▼
 ┌──────────────── 内核网关 ────────────────┐
 │ 鉴权中间件 ──► ctx.auth.authenticate ────┼──┐
 │ 权限检查   ──► ctx.rbac.check_principal ─┼──┤
 │ 启动登记   ──► ctx.rbac.register_permissions ┤
 └──────────────────────────────────────────┘  │
                                               ▼
 ┌──────────────────────── identity（Native）─────────────────────────────┐
 │ http  accounts  auth/sessions  credentials(pw/totp/webauthn)  tokens   │
 │ status(restrictions)  passkey  challenges  risk(ip/geo/throttle)  rbac │
 │ crypto(keyring)  cache  jobs  mcp                                      │
 └──┬───────────────┬────────────────────┬─────────────────────┬─────────┘
    │PG schema      │Redis p:identity:*  │钩子 user.before_*    │事件 user.*（outbox）
    ▼ identity      ▼                    ▼                     ▼
 PostgreSQL       Redis main     invite / registration-   tracker-bridge ──► trk:pk:* ──► pt-tracker
                                 policy / anticheat …     notify（拉取挑战投递）
                                                          levels / invite / search / 各插件
    ▲ 服务调用（下游 → identity）：ctx.users.* / ctx.rbac.* / ctx.auth.*
    └── levels(set_class, set_class_roles)  ratio-policy/hnr/anticheat(set_status)
        mcp(issue_token)  notify(challenge_delivery, get_sensitive email)
        tracker-bridge(passkey_material)  torrent(get_sensitive passkey)  medals/shop(set_title, rename)
```

### 2.2 内部模块

| 模块 | 职责 |
|---|---|
| `http` | axum 路由（清单声明的全部路由），请求校验、cookie 设置、错误映射 |
| `accounts` | 注册（含钩子）、用户名规则与混淆检测、资料、改名、删除 / 清除、管理员建号、导入 |
| `auth` | 登录编排（密码 → 2FA 票据 → `user.before_login` → 会话）、会话签发 / 校验 / 刷新 / 撤销、近期重新验证、`authenticate` 服务实现 |
| `credentials` | 密码（Argon2id、旧哈希验证、泄漏表、策略）、TOTP、恢复码、WebAuthn（登记、断言、无密码） |
| `tokens` | `pts_`/`ptm_`/`ptf_` 签发、校验、scope、撤销、最近使用 |
| `status` | 限制（restriction）的施加 / 解除 / 到期，有效状态合成与物化，`set_status` 服务 |
| `passkey` | 生成、加密存储、展示、重置 / 吊销、历史、`passkey_material` |
| `challenges` | 邮箱验证、找回密码、改邮箱挑战；`challenge_delivery` |
| `risk` | 登录失败计数与递增延迟、软锁、设备识别、IP 记录、GeoIP/ASN、风险标记、IP 保留期 |
| `rbac` | 权限点登记、角色定义、授予、等级绑定、用户覆盖、状态屏蔽、有效权限计算与缓存、rank 规则 |
| `crypto` | HKDF 子密钥、AES-256-GCM、HMAC、密钥版本与轮换 |
| `cache` | Redis 会话 / token / 角色缓存，进程内 RBAC 快照（版本号失效） |
| `jobs` | cron 与延迟任务入口 |
| `mcp` | 3 个 MCP 工具实现 |
| `events` | 事件载荷构造（统一保证无敏感字段） |

## 4. 数据设计概要

| 实体 | 存储 | 说明 |
|---|---|---|
| 用户 `users` | PG `identity.users` | 用户名（显示形 + 规范形）、class、物化状态、头衔、资料、时间戳；软删除 |
| 邮箱 `user_emails` | PG | 当前邮箱、验证时间；唯一（规范形） |
| 密码 `user_passwords` | PG | PHC 串、算法、修改时间（与 users 分表，降低误读风险） |
| 改名历史 `username_history` | PG | 旧名、新名、保留到期 |
| 限制 `restrictions` | PG | 类型、来源、原因、到期、施加/解除者；部分唯一索引“同来源同类型只一条生效” |
| passkey `passkeys` / `passkey_history` | PG | 当前（密文 + HMAC + 版本）；历史（HMAC、短期密文、原因） |
| 会话 `sessions` | PG + Redis 缓存 `p:identity:sess:<hash>` | 令牌哈希、设备、IP 摘要、reauth/2FA 时间 |
| 设备 `devices` | PG | 设备 cookie 哈希、首次/最近使用 |
| token `tokens` | PG + Redis `p:identity:tok:<hash>` | 类型、scope、到期、最近使用 |
| TOTP / 恢复码 / WebAuthn | PG（`totp_secrets`、`recovery_codes`、`webauthn_credentials`） | 密文 / 哈希 / 公钥 |
| 挑战 `challenges` | PG | 令牌哈希、用途、目标邮箱（改邮箱时）、过期、投递次数 |
| IP 记录 `ip_log` | PG（按月分区 by `first_seen_at`） | 用户、IP（inet）、国家、ASN、次数 |
| 安全事件 `security_events` | PG（月分区，保留 12 个月） | 用户可见的安全日志 |
| RBAC | PG：`permissions`、`roles`、`role_permissions`、`user_roles`、`class_roles`、`permission_overrides` | 有效权限缓存在进程内 + Redis |
| 登录限流、2FA 票据、WebAuthn 挑战状态、TOTP 防重放 | Redis 私有前缀 | 均带 TTL |
| 搜索索引 | 不贡献（`users_admin` 索引由 search-meilisearch 通过 `v_user_public` / 事件构建；邮箱只给哈希，见 §7） | |

## 5. 关键流程

### 5.1 注册

```
客户端 POST /users {username, password, email, locale, invite_code?, form{}}
 → 限流（ip:5/h）→ 校验格式、密码策略、用户名混淆/保留、邮箱格式
 → 预检唯一（用户名规范形、邮箱规范形、改名保留期）            —— 冲突 409
 → hooks.run("user.before_register", input)                    —— invite 预留、registration-policy 检查名额/答题
       deny  → 返回处理者错误码（403/422），不写库
       allow → 得到合并后的 attributes
 → 事务：
     INSERT users / user_emails / user_passwords / passkeys
     若需邮箱验证或 initial_status=pending：INSERT restrictions(pending, source=identity|<plugin>)
     INSERT challenges(email_verify) → publish user.challenge_issued
     publish user.registered{…attributes, registration_mode}
     （唯一约束兜底并发；冲突 → 409，invite 预留由其 TTL 释放）
 → 201 + 可选自动登录（配置；pending 用户也可登录但受限）
下游：invite 消费 user.registered 确认预留；notify 消费 user.challenge_issued → ctx.auth.challenge_delivery → 发邮件；
      tracker-bridge 消费 user.registered → passkey_material → 写 trk:pk
```

### 5.2 登录（密码 + 2FA）

```
POST /sessions {username, password, remember}
 → 限流检查（Redis：fail:u:<hmac(username)>、fail:ip:<hmac(ip)>）→ 需要延迟则 429 identity.login_throttled
 → 查用户（不存在时对假哈希执行 Argon2 以对齐耗时）→ Argon2 验证（信号量）
 → 失败：计数 + publish user.login_failed → 401 identity.invalid_credentials
 → banned → 403 identity.account_banned
 → 已开启 2FA → 创建票据 p:identity:2fa:<ticket>（5 min，5 次）→ 200 {two_factor_required, ticket, methods}
       POST /sessions/two-factor {ticket, totp|recovery_code|webauthn}
 → hooks.run("user.before_login", {user_id, username, method, ip?})  （fail-open）
 → 事务：INSERT sessions、UPSERT devices、UPSERT ip_log、INSERT security_events、publish user.logged_in{risk_flags}
 → 清零用户名失败计数；Set-Cookie 会话 + CSRF + 设备
```

### 5.3 每请求鉴权

```
内核：cookie → ctx.auth.authenticate(Session{token})
 identity：h = sha256(token)
   Redis HGETALL p:identity:sess:<h> 命中 → 检查 idle/absolute 过期、用户状态版本 → Principal
   未命中 → PG 查 sessions + users → 回填 Redis（TTL = min(剩余空闲, 1h)）
   最近活动刷新：距上次 > 15 min 时异步写 PG（节流），IP 变化写 ip_log
 内核：ctx.rbac.check_principal(principal, route.permission, safe_method)
   进程内快照（角色→权限，版本号 p:identity:rbac:ver 每 1 s 比对）
   + 用户有效角色（Redis p:identity:ur:<uid>，缺失时由 PG 计算）
   + 覆盖、状态屏蔽、token scope、2FA 强制
```

### 5.4 passkey 重置与 tracker 同步

```
用户 POST /users/me/passkey-resets（reauth、频率限制）
 → 事务：passkey_history INSERT(旧 HMAC、旧密文、retired_at、reason)
         passkeys UPDATE(新密文、新 HMAC、version+1)
         publish user.passkey_reset{user_id, passkey_version, op: reset, by}
 → 200 {passkey}（仅本次响应返回新值，no-store）
tracker-bridge（订阅 user.passkey_reset，ordered by user）：
 → ctx.users.passkey_material(user_id) → {current, version, retired[]}
 → 对 retired 中每个：DEL trk:pk:<old>；SET trk:pk:<current> {uid, st, ver}；XADD trk:sync
 → pt-tracker ≤ 1 s 内使旧 key 失效
```

端到端时延 = 事件投递（p99 < 1 s，NFR-KRN-004）+ bridge 处理；design/10 要求“正常 1 秒内生效”，见 §6 DD-IDN-5 与风险说明。

### 5.5 限制施加（以 ratio-policy 为例）

```
ratio-policy → ctx.users.apply_restriction{user_id, kind: leech_disabled, reason_code, until?, idempotency_key}
 identity：校验 caller scope write:status → 事务：
   upsert restrictions WHERE (user_id, kind, source=ratio-policy, lifted_at IS NULL)
   重算有效状态 → 若变化：UPDATE users.status, status_version+1；publish user.status_changed
   publish user.restriction_changed；调度 restriction_expire（如有 until）
   提交后：DEL 会话 / 角色缓存（状态版本变化）
 tracker-bridge 订阅 user.status_changed → 更新 trk:pk.st
```

### 5.6 挑战投递

```
identity：INSERT challenges(token_hash, purpose, …) + publish user.challenge_issued{challenge_id, purpose, expires_at, locale}
notify：订阅 → ctx.auth.challenge_delivery(challenge_id, "<event_id>:deliver")
identity：检查调用方作用域 challenges:deliver 与 user.email 授权 → 若挑战未过期、未使用、取用 < 3 次：
         令牌需要可重建 → 令牌由 HMAC(challenge_key, challenge_id ∥ nonce) 派生（库中只存 nonce 的哈希校验值，见 LLD §1.8），
         返回 {to, purpose, url, code?, expires_at, template_key, locale}；同一幂等键重复调用返回同一结果
notify：渲染模板、发送；令牌不入日志、不入事件
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论 | 理由 |
|---|---|---|---|---|
| DD-IDN-1 | 多副本会话存储 | A 仅 Redis；B 无状态 JWT；C PG 持久 + Redis 读缓存 | C | A：Redis 淘汰 / 故障即全站掉线；B：无法即时撤销，违背“可查看并撤销所有会话”；C：PG 为事实来源、Redis 只是缓存，命中路径 1 次 Redis 往返 |
| DD-IDN-2 | 发验证 / 找回邮件 | A identity 内置 SMTP；B `requires ctx.notify`；C 事件 + notify 拉取 | C | B 形成依赖环（notify 依赖 ctx.users）；A 与 notify 重复且多一份 SMTP 密钥；C 保持事件无敏感数据，令牌只经授权服务调用取得 |
| DD-IDN-3 | 多来源设置状态的冲突 | A 单一状态列（NexusPHP 式）；B 按来源分层的限制 + 合成 | B | 防止“ratio-policy 自动解除时误解管理员封禁”；每条限制有历史与到期；`set_status` 语义在 catalog 概要上保持：调用方只能施加 / 撤销自己的限制 |
| DD-IDN-4 | 等级与权限的关系 | A levels 每次升降级 grant/revoke 角色；B identity 提供 class→角色绑定 | B（A 仍可用） | B 原子：`set_class` 一次写入即切换权限，无中间态；避免 levels 每次评估都改大量 user_roles；等级规则仍完全在 levels |
| DD-IDN-5 | passkey 存储与同步 | A 明文；B 仅哈希；C 密文 + HMAC，事件只含版本，bridge 拉取 `passkey_material`（含近期退役 key） | C | 需要向用户展示和注入种子，不能只存哈希；退役 key 的短期密文让 bridge 即使丢失自身状态也能删掉 `trk:pk:<old>`；时效依赖事件链路 p99 < 1 s，若实测超标，备选是 tracker-bridge 提供“同步路径”（见 §7 问题 Q-IDN-3） |
| DD-IDN-6 | 员工能处理哪些用户 | A 任何人；B 按 rank（最高内置角色序） | B | 采纳 UNIT3D/Gazelle 经验，防止版主封管理员；sysop 例外 |
| DD-IDN-7 | RBAC 缓存 | A 每次查 PG；B 进程内快照 + Redis 版本号；C 全在 Redis | B | 角色→权限映射小（< 1 MB）、变化少，进程内查找最快；版本号每 1 s 比对，Native 插件无法用 `k:bus`，用私有键 `rbac:ver` 实现跨副本失效；用户角色集合放 Redis（改动时删除） |
| DD-IDN-8 | 邮箱存储 | A 加密 + 盲索引；B 明文，独立表 + 角色隔离 | B | catalog 已登记敏感视图 `v_user_email(id, email)` 需要明文；PG 中无密钥无法在视图内解密。保护依赖 schema 隔离 + 敏感视图授权 + 磁盘加密；对外（搜索）只提供 HMAC |
| DD-IDN-9 | token 格式与哈希 | A 随机 + bcrypt；B 前缀 + 32 字节随机（base62）+ CRC32 校验，SHA-256 存储 | B | 高熵随机值无需慢哈希；前缀与校验位便于 secret scanning 与快速拒绝伪造 |
| DD-IDN-10 | WebAuthn 实现 | A 自研；B `webauthn-rs`（MPL-2.0） | B | 密码学协议不自研；MPL-2.0 为文件级弱 copyleft，可与 MIT/Apache 代码静态链接，需加入 cargo-deny 许可证白名单（§7 Q-IDN-4）；仪式状态序列化存 Redis（需启用 `danger-allow-state-serialisation` 特性，状态只存服务端） |
| DD-IDN-11 | 登录锁定策略 | A 按用户名硬锁；B 只按 IP；C 双维度递增延迟 + 软锁，已知设备豁免 | C | A 可被恶意锁死他人；B 挡不住分布式撞库 |
| DD-IDN-12 | 注册钩子中的 email/ip | A 永不提供；B 内核按处理者授权裁剪；C identity 只提供给有授权的处理者（按处理者分别调用） | B（§7 申请内核支持），内核未支持前退化为 A | `hook-runner.run` 只接受单一输入，identity 无法逐处理者裁剪 |
| DD-IDN-13 | Argon2 资源控制 | A 无限制；B 每副本信号量 + 排队超时 | B | 每次哈希约 19 MiB 内存 + 数十毫秒 CPU，突发登录可耗尽内存 |
| DD-IDN-14 | 挑战令牌 | A 随机令牌只存哈希（无法再取）；B 令牌由服务端密钥 + challenge_id + nonce 派生，库中存派生值哈希 | B | notify 需要“事后取回”链接：B 允许 identity 重建同一令牌，而数据库泄漏也无法得到令牌（缺服务端密钥） |
| DD-IDN-15 | `pending` 用户能否登录 | A 不能；B 能，但只有 guest 权限 + 白名单接口 | B | 让用户能重发验证邮件、查看申请进度，减少客服工作 |

## 7. 对平台契约的新增

以下需评审后合入 `docs/platform/`。

### 7.1 事件

| 类型 | 内容 |
|---|---|
| 新事件 | `user.challenge_issued`（identity，key `user:<id>`）：`user_id, challenge_id(uuid), purpose(email_verify/password_reset/email_change/email_change_notice_old), expires_at, locale`。不含令牌、邮箱 |
| 新事件 | `user.restriction_changed`（identity，key `user:<id>`）：`user_id, restriction_id, kind(ban/leech_disabled/pending), source, op(applied/updated/lifted/expired), reason_code, until?, effective_status` |
| 新事件（P2） | `user.token_expiring`（identity）：`user_id, token_id, kind, expires_at` |
| 字段新增 | `user.logged_in`：`new_device: bool, risk_flags[]（new_device/new_region/new_asn/after_reset）, region?（ISO 国家码，配置可关）`；`method` 增加 `passwordless` 区分 WebAuthn 无密码与 WebAuthn 第二因素 |
| 字段新增 | `user.passkey_reset`：`passkey_version, op(reset/revoke/regenerate), by(user/admin/plugin), reason_code` |
| 字段新增 | `user.status_changed`：`restriction_source`（触发本次变化的来源） |
| 字段新增 | `user.login_failed`：`stage(password/two_factor/hook/throttled/status)` |

### 7.2 钩子

| 项 | 内容 |
|---|---|
| `user.before_register` 可修改字段 | 增加 `attributes.registration_mode`（open/invite/application/admin/import）、`attributes.pending_reason` 与 `attributes.pending_source`（须等于作出 modify 的处理者插件 ID，由内核校验；使该插件之后能用 `lift_restriction` 解除自己设下的待审核。未合入前，hook 设的 pending 来源固定为 `identity:review`，只能由管理员解除；需要自行解除的插件应在消费 `user.registered` 后自己 `apply_restriction`） |
| `user.before_register` 输入裁剪 | 请内核在 `hook-runner.run` 中按处理者有效敏感能力删除 `email`、`ip` 字段后再交给该处理者（catalog 已写“需 user.email / user.ip”，但 kernel/03 §5.2 未描述裁剪） |
| `user.before_login` 输入 | 增加 `new_device: bool, risk_flags[]` |
| 建议（P2） | 新钩子点 `user.before_login_attempt`（凭据校验前，输入 `username_hash, ip?, form{}`，fail-open，200 ms），供本地验证码插件在失败次数高时要求额外字段；本期不阻断 |

### 7.3 服务方法与作用域

| 服务 | 新增 | 说明 |
|---|---|---|
| `ctx.auth` | `challenge_delivery(challenge_id, idempotency_key) -> ChallengeDelivery` | 作用域 `challenges:deliver`（需授权），调用方还须有 `user.email` |

| `ctx.users` | `apply_restriction(req)`、`lift_restriction(req)`、`restrictions(id)` | 带到期与幂等键，`set_status` 为其简写 |

| `ctx.users` | `ip_history(id, cursor)`、`users_by_ip(ip, cursor)` | 需 `user.ip`；返回值仍属敏感，调用方不得写入事件 / 日志 |

### 7.5 需要确认的问题

| # | 问题 |
|---|---|
| Q-IDN-1 | 内核是否支持钩子输入按处理者裁剪（§7.2）；不支持时 identity 不提供 email/ip |
