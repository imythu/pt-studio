## 1. 引言

### 1.1 目的

定义 `tracker-bridge` 插件（Native，提供 `ctx.tracker`）的需求。它是内核侧与独立进程 pt-tracker（AGPL-3.0-only，D16）之间**唯一的写入方**：把 passkey、用户状态、种子白名单、客户端规则、运行参数以“快照键 + 变更流”的形式写入 Redis（design/10 §5.5），提供全量重建、一致性校验与告警、客户端规则管理界面，以及只读的 peer 查询。

### 1.2 范围

**包含**

- 用户同步：passkey 生成 / 重置 / 用户状态变化 / 用户删除 → `trk:pk:*`、`trk:u:*`。
- 种子同步：上传、状态变化、文件替换、删除、恢复 → `trk:t:*`（含 hybrid 的 v2 截断 hash、墓碑与删除原因）。
- 客户端规则（允许 / 拒绝列表，peer_id 前缀、最低版本、User-Agent）→ `trk:clients`。
- tracker 运行参数（announce 间隔、peer 数、过滤开关等）→ `trk:cfg`。
- 变更流 `trk:sync`、单调版本号、幂等写入。
- 全量重建（全站 / 单用户 / 单种子）、一致性校验（抽样 + 每日全量）、孤儿键清理、告警。
- pt-tracker 节点健康与同步延迟监控（读取 pt-tracker 写出的节点状态）。
- peer 列表查询（读 `ps:*`）。
- 管理界面：客户端规则、规则测试、被拒客户端统计、同步状态、手动重建、校验结果。

**不包含**

| 不包含 | 归属 |
|---|---|
| announce 处理、增量计算、流量流 `acct:*` | pt-tracker、accounting |
| passkey 的生成与保存（主副本） | identity（`ctx.users.reset_passkey`、`get_sensitive`） |
| 种子状态的决定 | torrent、moderation |
| 用户状态的决定（封禁、禁止下载） | identity、ratio-policy、anticheat 等 |
| 做种数 / 完成数统计 | accounting（`traffic.swarm_stats_updated`） |
| 作弊判定 | anticheat |

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 快照键 | Redis 中描述某个对象当前完整状态的键（`trk:pk:<passkey>` 等），pt-tracker 以它为准 |
| 变更流 | Redis Stream `trk:sync`，只携带“哪个键变了”，pt-tracker 收到后重读快照键 |
| ver | 单调递增的同步版本号（全站一个序列）；快照键只接受更大的 ver |
| 墓碑 | 被删除对象的快照键保留一段时间（`st` 为删除类状态 + 原因 + `exp`），让客户端看到明确原因 |
| owner_only | 种子只允许发布者本人 announce（候选 / 待审期间） |
| 节点状态键 | pt-tracker 每个节点写出的 `trk:stats:node:<node_id>`（本插件提出新增，见 HLD §7） |

### 1.4 参考资料

- docs/design/03、10（尤其 §5.5 同步接口、§5.6 peer 会话状态、§5.8 配置、§7 风险）；docs/platform 全部契约；docs/components/pt-tracker/（本轮同时编写）。
- 开源实现（只读克隆于 `.spike/refs/`，只借鉴思路）：
  - Ocelot（OPS/Gazelle）：tracker 启动时直接读站点 MySQL 的 users / torrents / 白名单表；运行中站点通过 HTTP `GET /<site_password>/update?action=change_passkey|add_torrent|delete_torrent|update_user|add_whitelist…` 推送增量；删除种子时附原因码，tracker 在 `del_reason_lifetime` 内返回“Unregistered torrent: <原因>”。
  - UNIT3D-Announce：启动时从数据库加载，运行中主站通过带 API key 的 HTTP 接口 `PUT/DELETE /announce/<key>/users|torrents|blacklisted-agents…` 推送；客户端用**黑名单**（peer_id 前缀）+ 浏览器 UA 关键字拒绝 + 可疑请求头拒绝（`Accept-Language`、`Referer`、`want-digest` 等）+ 端口黑名单；记录用户对未注册 info_hash 的访问。
  - XBT Tracker：定时轮询数据库表（`xbt_users`、`xbt_files`、`xbt_config`）同步，按标志位增量读取；把 peer 统计批量写回数据库。
  - NexusPHP：announce.php 直接查库（带缓存）；客户端**允许列表** `agent_allowed_family`：peer_id 正则 + 版本捕获组 + 最低版本 + UA 正则，另有例外表 `agent_allowed_exception`，后台可维护。

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | Native（需要 `redis_global`、Lua 脚本、批量 pipeline、读取 `ps:*` 二进制值） |
| 提供 | `ctx.tracker@0.1.0` |
| 依赖 | `ctx.users`（passkey 敏感读、状态）、`ctx.torrents`（种子摘要，peer 查询用）、`ctx.rbac` |
| 可选依赖 | `ctx.notify`（不一致告警通知管理员） |
| 视图 | `identity.v_user_public`、`torrent.v_torrent_tracker`（敏感，需授权）、`torrent.v_torrent_hash_history` |
| 敏感能力 | `user.passkey`（必需）、`peer.ip`（可选，peer 列表显示 IP） |
| Redis 全局前缀 | `trk:*`（tracker_sync，rw）、`ps:*`（tracker_state，r） |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 系统（事件驱动） | 用户注册、重置 passkey、被封禁 / 禁止下载 / 解封、种子上传 / 审核 / 下架 / 删除 / 恢复 / 替换文件后，1 秒内在 tracker 生效 |
| 管理员（`tracker-bridge.clients.manage`） | 维护客户端允许 / 拒绝规则，测试某个 peer_id + UA 会命中哪条规则，查看被拒客户端排行，调整 announce 参数 |
| 站务（`tracker-bridge.resync`，sysop） | 在 Redis 故障恢复、迁移、数据异常后发起全量重建；查看一致性校验报告 |
| 审核员（`tracker-bridge.peers.read`） | 查看某种子的 peer 列表、某用户当前连接 |
| 普通用户 | 在个人页查看自己当前连接的客户端与种子（不含他人信息） |
| 其他插件 | 调用 `ctx.tracker.sync_user` 立即同步、`peers()` 查询；订阅 `tracker.*` 事件 |

### 2.3 现有开源 PT 程序的做法调研

| 主题 | 做法 | 优点 | 缺点 | 我们采纳 / 改进 |
|---|---|---|---|---|
| 同步通道 | Ocelot、UNIT3D-Announce：站点 HTTP 推送增量到 tracker 内存；启动时 tracker 直接读站点数据库 | 实时；实现简单 | ① 推送是“发了就忘”，tracker 重启或网络抖动期间的变更会丢，只能靠重启全量加载；② tracker 需要站点数据库凭据，与站点数据模型强耦合；③ 多 tracker 节点时站点要逐个推送 | **改进**：Redis 快照键（持久的“真相”）+ 变更流（可重放、多节点各自消费、缺口可检测并全量重载）；pt-tracker 不接触 PostgreSQL |
| 轮询 | XBT 定时轮询数据库 | 不会丢 | 延迟大（秒～分钟），数据库压力随节点数增长 | 不采用；只保留“每日全量校验”作为兜底 |
| 版本与乱序 | Ocelot/UNIT3D 无版本号，后到的旧消息会覆盖新状态 | — | 并发更新与重放时可能回退 | **改进**：全站单调 `ver`，Lua 原子“比较并写”；“先取 ver 再读源状态”保证重建与增量并发时不回退 |
| 删除原因 | Ocelot 在删除后一段时间返回原因 | 用户体验好 | 原因只在 tracker 内存 | **采纳**：墓碑快照键 + `rsn` + `exp`，重启不丢 |
| 客户端控制 | NexusPHP 允许列表 + 最低版本 + 例外；Ocelot 允许列表（peer_id 前缀）；UNIT3D 拒绝列表 + 浏览器 UA + 可疑请求头 | 允许列表更安全；最低版本可淘汰有漏洞的旧版本 | 规则难以测试；拒绝列表挡不住新出现的作弊客户端 | **采纳**：默认拒绝的有序规则（allow / deny 混合，先匹配者生效）+ peer_id 前缀 / 正则 + 最低版本 + UA 前缀 / 正则；提供“规则测试”接口与被拒客户端排行；浏览器 UA 与可疑请求头检查作为 `trk:cfg` 开关下发 |
| 未注册 info_hash | UNIT3D-Announce 记录用户访问未注册种子 | 便于发现旧种子、帮助用户 | — | pt-tracker 侧只计数（指标），不记录到用户；墓碑覆盖最常见场景 |
| 一致性校验 | 各实现均无系统化校验 | — | 数据漂移只能靠重启发现 | **新增**：抽样（每 10 分钟）+ 全量（每日）校验、自动修复、指标与告警 |

### 2.4 约束与假设

1. pt-tracker 与内核不共享代码（D16、licensing.md §2）；本插件按文档化的数据格式独立实现写入与 `ps:*` 值解析。
2. `tracker_sync` 角色的 Redis 必须是**单分片**（非 Cluster 或所有 `trk:*` 落同一槽位），因为写入脚本同时操作快照键与 `trk:sync`。数据量：30 万 passkey + 100 万种子 ≈ 150 MB。
3. `tracker_state`（`ps:*`）可以是 Cluster；本插件只按单键读取。
4. 事件至少一次投递；同一 key（`user:<id>`、`torrent:<id>`）的事件有序（订阅 `ordered = true`）。
5. identity 在 passkey 重置后发布 `user.passkey_reset`（不含 passkey），本插件凭 `get_sensitive` 读取新值。
6. 规模：30 万用户、100 万种子、10 个 pt-tracker 节点；日均同步写入约 5 万次。

## 3. 功能需求

### 3.1 同步写入

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-TRB-001 | 原子写入 | 每次写快照键与追加 `trk:sync` 在同一个 Redis 脚本中完成；快照键已有 `ver ≥` 新 ver 时不写、不追加 | P0 | 并发 / 乱序写入后快照键为最大 ver 的内容；`trk:sync` 中无“旧 ver 覆盖” |
| FR-TRB-002 | 单调版本 | 全站单调 `ver`（PostgreSQL 序列）；任何写入**先取 ver 再读源状态** | P0 | 重建与增量并发的交错测试中无回退 |
| FR-TRB-003 | 用户同步 | 处理 `user.registered`、`user.passkey_reset`、`user.status_changed`、`user.deleted`：读当前状态与 passkey，写 `trk:pk:<pk>{uid, st, ver, rsn?}` 与反向索引 `trk:u:<uid>{pk, ver}` | P0 | 事件发生后 p99 ≤ 1 s 快照键更新（不含事件投递积压） |
| FR-TRB-004 | 状态映射 | `active → 0`，`leech_disabled → 1`，`pending`、`banned → 2`（`rsn` 为状态名），`deleted → 3`（墓碑） | P0 | 映射表测试 |
| FR-TRB-005 | passkey 轮换 | 重置后：新 passkey 写入；旧 passkey 写墓碑 `st = 3, rsn = "reset"`（经 `trk:u` 找到旧值） | P0 | 旧 passkey 在 1 秒内被 tracker 拒绝，并显示原因 |
| FR-TRB-006 | 种子同步 | 处理 `torrent.created`、`torrent.status_changed`、`torrent.updated`（含 `info_hash`）、`torrent.deleted`：经视图读种子当前状态，写 `trk:t:<hash>{tid, st, acct, size, own, ver, rsn?, exp?}` | P0 | 上传后 p99 ≤ 1 s 可 announce |
| FR-TRB-007 | 种子状态映射 | 默认：`approved → 0 open`；`candidate`、`pending → 1 owner_only`；`rejected → 1 owner_only`；`disabled → 2`（`rsn = "disabled"`）；`deleted → 3` 墓碑（`rsn` = 删除原因码）；被替换的旧 hash → `4` 墓碑（`rsn = "replaced"`）。待审与拒绝的映射可在设置中改为 `open` / `deny` | P0 | 映射与设置测试 |
| FR-TRB-008 | hybrid | v1 hash 与 v2 截断 hash 都写入，指向同一 `tid`；有 v1 时 v2 截断 hash `acct = 0`；纯 v2 种子 `acct = 1` | P0 | hybrid 种子两个键均存在，只有一个计账 |
| FR-TRB-009 | 墓碑过期 | 墓碑带 TTL（`tombstone_ttl_days`，默认 7）与字段 `exp`（Unix 秒）；过期后自然删除 | P1 | TTL 与 `exp` 一致 |
| FR-TRB-010 | 客户端规则 | 维护有序规则集（allow / deny，peer_id 前缀或正则 + 可选最低版本，UA 前缀或正则），默认动作 `deny`；保存时整体校验并写 `trk:clients`（JSON，含 `ver`）；发布 `tracker.client_rules_changed` | P0 | 规则保存后 1 秒内 tracker 生效 |
| FR-TRB-011 | 规则校验 | 正则只允许线性时间引擎语法（Rust `regex`）、长度 ≤ 256、编译后大小 ≤ 64 KiB；规则数 ≤ 500；前缀 ≤ 20 字节；乐观锁（规则集版本） | P0 | 非法规则返回 422 并定位到规则下标 |
| FR-TRB-012 | 规则测试 | 输入 peer_id（原始或百分号编码）与 UA，返回命中的规则与最终动作（与 pt-tracker 算法一致） | P1 | 与 pt-tracker 共享的测试向量结果一致 |
| FR-TRB-013 | 运行参数 | 设置中的 announce 参数写入 `trk:cfg`（`interval`、`min_interval`、`max_peers`、`max_numwant`、`emit_zero_delta`、`require_ua`、`deny_browser_ua`、`deny_abnormal_headers`、`port_blacklist`、`scrape_enabled`）；校验 `min_interval ≤ interval`、`interval < pt-tracker max_peer_timeout`（读节点状态中的 `max_peer_timeout`，缺失时只告警） | P0 | 设置变更后 1 秒内各节点生效 |
| FR-TRB-014 | 服务接口 | `ctx.tracker`：`sync_user`、`sync_torrent`、`set_client_rules`、`client_rules`、`peers`、`rebuild_all`，以及新增的 `status`、`peers_of_user`（与 02 §4、03 一致；单用户 / 单种子重建即重新调用 `sync_user`、`sync_torrent`，后台 rebuild 任务支持 `scope = user | torrent`） | P0 | WIT 契约测试 |

### 3.2 重建、校验、监控

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-TRB-015 | 全量重建 | 后台任务：按批（1000）扫描全部用户与种子、重写快照键；写客户端规则与参数；清理本次重建未覆盖的孤儿键；最后向 `trk:sync` 追加 `kind = all, op = reload`；发布 `tracker.resynced{scope: full}`；同一时刻只允许一个全量重建 | P0 | 清空 `trk:*` 后重建，结果与数据库一致；30 万用户 + 100 万种子 ≤ 10 分钟 |
| FR-TRB-016 | 单对象重建 | 按用户 ID / 种子 ID 立即重写 | P1 | — |
| FR-TRB-017 | 重建可观察 | 重建任务有 ID、进度（已处理 / 总数）、结果统计；可在后台查看 | P1 | — |
| FR-TRB-018 | 抽样校验 | 每 10 分钟随机抽样用户与种子（默认各 2000），比较数据库与 Redis；不一致立即修复并计数 | P0 | 人为篡改的键在下一轮被修复 |
| FR-TRB-019 | 全量校验 | 每日全量比较，并清理孤儿键（`trk:pk` 的 uid 对应的当前 passkey 不同、`trk:t` 的 hash 在数据库中不存在且不是有效墓碑） | P0 | 孤儿键被清理；报告记录数量 |
| FR-TRB-020 | 告警 | 校验不一致数超过阈值（默认 10）、节点同步延迟超过阈值（默认 5 秒）、节点失联（节点状态键过期）、重建失败时：指标告警，并（可选）通过 `ctx.notify` 通知有 `tracker-bridge.resync` 权限的用户；发布 `tracker.inconsistency_detected` | P1 | 告警可触发与恢复 |
| FR-TRB-021 | 节点健康 | 每分钟读取 `trk:stats:node:*`，展示各节点版本、启动时间、已应用的变更流 ID、同步延迟、缓存规模、peer 数 | P1 | — |

### 3.3 peer 查询与管理界面

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-TRB-022 | 种子 peer 列表 | 读 `ps:<hash>`（v1 与 v2 截断各一），解析、去掉超时会话，返回用户 ID、客户端（由 peer_id 解析）、上传 / 下载累计值、剩余、是否做种、连接时长、最后 announce 时间、端口；IP 仅在调用方有 `peer.ip` 授权且请求者有 `tracker-bridge.peers.read_ip` 时返回 | P1 | 无授权时结果中无 IP 字段 |
| FR-TRB-023 | 用户当前连接 | 用户本人查看自己的连接（不含 IP 以外的他人信息；IP 只显示给本人且做掩码）；审核员查看任意用户（需要 accounting 的 `seeding_now` 得到种子集合，再逐个读 `ps`） | P2 | — |
| FR-TRB-024 | 规则管理界面 | 后台页面：规则列表（拖动排序、启用开关）、编辑、测试、预设模板（qBittorrent、Transmission、Deluge、rTorrent、BiglyBT 等）、被拒客户端排行（读 `trk:stats:denied:<日期>`） | P1 | 可用性评审通过 |
| FR-TRB-025 | 同步状态界面 | 后台页面：节点列表与延迟、最近校验报告、发起重建与进度 | P1 | — |
| FR-TRB-026 | 审计 | 规则变更、参数变更、重建、手动修复写审计 | P0 | 审计记录含操作者与前后差异（不含 passkey） |

## 4. 非功能需求

| 编号 | 类别 | 描述 | 指标 |
|---|---|---|---|
| NFR-TRB-001 | 时效 | 从源事件提交到快照键与变更流写入 | p99 ≤ 1 s（事件投递正常时）；封禁类在 pt-tracker 侧生效 ≤ 2 s |
| NFR-TRB-002 | 吞吐 | 增量同步 | ≥ 500 次/秒（单副本），突发 1 万条积压在 30 s 内消化 |
| NFR-TRB-003 | 重建性能 | 全量重建 | 30 万用户 + 100 万种子 ≤ 10 分钟，期间增量同步不中断 |
| NFR-TRB-004 | 幂等 | 事件重复、乱序、回放、任务重跑都不产生错误状态 | 交错与重放测试通过 |
| NFR-TRB-005 | 安全 | passkey 不进日志、事件、审计、指标、错误；Redis ACL：本插件账号只能写 `trk:*`、读 `ps:*` | 扫描零命中；ACL 测试 |
| NFR-TRB-006 | 隐私 | peer IP 默认不返回；返回时审计 | — |
| NFR-TRB-007 | 可用性 | Redis `tracker_sync` 不可用时，事件订阅失败重试（不丢）；恢复后自动追上；pt-tracker 侧使用本地缓存继续服务 | 故障注入测试 |
| NFR-TRB-008 | 可观测 | 同步延迟、写入数、版本冲突（被拒的旧写入）、校验不一致、节点延迟指标 | 见 LLD §8 |
| NFR-TRB-009 | 容量 | `trk:*` 内存 | ≤ 200 MB（30 万用户、100 万种子、7 天墓碑） |

## 6. 外部接口需求概述

- **服务**：`ctx.tracker@0.1.0`（LLD §2.1）。
- **Redis 契约**：`trk:pk:*`、`trk:u:*`、`trk:t:*`、`trk:clients`、`trk:cfg`、`trk:sync`（写）；`ps:*`、`trk:stats:node:*`、`trk:stats:denied:*`（读）。格式见 LLD §3.2，pt-tracker 文档 LLD-PTT §3 与之逐字段一致。
- **事件**：发布 `tracker.client_rules_changed`、`tracker.resynced`、`tracker.inconsistency_detected`（新增）；订阅用户与种子事件（HLD §3.4）。
- **HTTP**：`/api/p/tracker-bridge/v1/…`（LLD §2.4）。
- **界面**：后台“Tracker”菜单（客户端规则、同步状态）；种子详情“Peers”标签页；个人页“当前连接”。
