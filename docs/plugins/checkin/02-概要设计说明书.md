## 1. 设计目标与原则

1. **一人一日一次**：由数据库唯一约束 `(user_id, day)` 兜底，不依赖 Redis。
2. **奖励有流水**：奖励只经 `ctx.ledger` 发放，原因码与幂等键可追溯到具体签到日（改进 NexusPHP 直接改用户字段的做法）。
3. **记录与奖励最终一致**：签到记录与“发奖延迟任务”在同一事务内写入；同步尝试发奖，失败由延迟任务以同一幂等键重试。
4. **规则数据驱动**：曲线、里程碑、随机奖励、补签规则全部在设置中，修改即时生效。
5. **高峰友好**：状态查询走 Redis 位图与用户状态缓存；签到写路径只有一行 upsert + 一行 insert。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
用户 / MCP ──► 内核网关 ──► checkin (WASM)
                              │ ctx.hooks.run("checkin.before_check_in") ──► anticheat 等
                              │ ctx.ledger.transfer(系统发行) ──► ledger
                              │ events.publish(checkin.checked_in) ──► medals、notify、webhook
                              ▼
                      PG schema checkin / Redis p:checkin:*
shop ──ctx.checkin.grant_makeup_cards──► checkin
```

## 4. 数据设计概要

| 实体 | 存储 | 说明 |
|---|---|---|
| `user_state` | PG | 每用户一行：当前连签、最长连签、累计天数、最后签到日、补签卡余额、本月补签次数 |
| `records` | PG（按月分区） | 每次签到/补签一行：`(user_id, day)` 唯一、奖励明细、发奖状态 |
| `milestones_awarded` | PG | 每个连签周期已发放的里程碑 |
| `card_log` | PG | 补签卡流水 |
| `daily_stats` | PG | 每日汇总 |
| `idempotency` | PG | 服务方法与 HTTP 幂等 |
| `day:<yyyymmdd>` | Redis 位图 | 当日已签到用户（`SETBIT uid`），48 h 过期 |
| `rank:<yyyymmdd>` | Redis 计数 | 当日签到名次（INCR） |
| `st:<uid>` | Redis HASH | 状态缓存，签到/补签后失效 |
| `streak_top` | Redis STRING(JSON) | 连签榜缓存 |

## 5. 关键流程

### 5.1 签到

```
POST /check-in
 1. day = today(site_tz)；校验 enabled、用户状态
 2. 若 Redis 位图已置位 → 直接返回 already_checked_in（快速路径，以 PG 为准）
 3. hooks.run(checkin.before_check_in, {user_id, kind: daily, date: day})
 4. SELECT … FROM user_state WHERE user_id FOR UPDATE（不存在则插入）
 5. streak = (last_day == day−1) ? streak+1 : 1
 6. 计算奖励：曲线 + 里程碑（未发过）+ 随机
 7. INSERT records(user_id, day, kind=daily, …, payout_status=pending) —— 唯一冲突 → already_checked_in
 8. UPDATE user_state；INSERT milestones_awarded
 9. jobs.schedule_once("pay_reward", now+30s, {record}, dedupe_key = "<uid>:<day>")
10. 同步调用 ledger.transfer(幂等键 checkin:daily:<uid>:<day>)；成功 → UPDATE payout_status=paid
11. events.publish(checkin.checked_in)
12. 提交；提交后 SETBIT day:<day> uid、INCR rank:<day>、DEL st:<uid>
```

ledger 同步调用失败（超时/不可用）不影响签到成功，响应中 `reward.status = "pending"`，由 `pay_reward` 任务重试。

### 5.2 补签

```
POST /make-up {date}
 1. 校验 makeup.enabled、date ∈ [today − window, today − 1]、date ≥ 注册日、本月补签次数 < max
 2. hooks.run(checkin.before_check_in, {kind: makeup, date})
 3. 锁 user_state；补签卡余额 ≥ 1
 4. INSERT records(kind=makeup)（唯一冲突 → checkin.already_checked_in）
 5. 扣补签卡（card_log）；按 §1.6 重算连签（只需从 date 向前后查连续段）
 6. 补发重算后新达到且未发过的里程碑；按配置发当日基础奖励
 7. 发布 checkin.made_up、checkin.makeup_cards_changed
```

### 5.3 发放补签卡（shop 履约）

```
shop: ctx.checkin.grant_makeup_cards(uid, n, "shop.order:<order_id>", "<order_id>:checkin")
checkin: 幂等表命中 → 返回首次结果；否则 锁 user_state，加卡，写 card_log，发布事件
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论与理由 |
|---|---|---|---|
| DD-CHKIN-1 | 日界线 | 用户时区 / 站点时区 | 站点时区。全站名次、排行可比；防止改时区刷签到 |
| DD-CHKIN-2 | 奖励如何发放 | 调 `ctx.bonus.award` / 直接 `ctx.ledger.transfer` | 直接 ledger：签到币种可配置，不强依赖 bonus 插件；bonus 未启用时也可用其他币种 |
| DD-CHKIN-3 | 签到记录与奖励的一致性 | 先发奖后记录 / 记录 + 延迟任务 + 同步尝试 | 后者：记录与 `pay_reward` 任务原子写入，ledger 用确定性幂等键，重试安全；唯一残留风险是“ledger 已入账但本事务提交失败”，用户重试时同一幂等键返回首次结果，不会重复 |
| DD-CHKIN-4 | 连签存储 | 每次查询时从记录计算 / 冗余在 user_state | 冗余：签到只需比较 last_day；补签时局部重算 |
| DD-CHKIN-5 | 排名奖励 | 发 / 不发 | 默认只展示名次不发奖，避免 0 点脚本抢签（NexusPHP 系插件的教训） |
| DD-CHKIN-6 | 已签到判断 | Redis / PG | PG 唯一约束为准；Redis 位图只做快速路径和首页展示 |
| DD-CHKIN-7 | 补签对里程碑 | 不补发 / 补发 | 补发重算后新达到的里程碑，但同一连签周期内每个里程碑只发一次（以“周期起始日 + 里程碑天数”为键） |
