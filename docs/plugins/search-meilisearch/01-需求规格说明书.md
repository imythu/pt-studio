## 1. 引言

### 1.1 目的

本文定义 `search-meilisearch` 插件（`ctx.search` 的默认实现）的功能与非功能需求，作为概要设计（HLD-SRCH）、详细设计（LLD-SRCH）与测试计划（TP-SRCH）的依据。

### 1.2 范围

**包含**：

- `ctx.search` 服务：查询（服务端强制可见性过滤）、联想、索引注册、重建、删除、标脏；
- 索引贡献接口（`search-contributor` 导出）的发现、schema 合并、Meilisearch 设置生成；
- 标准索引 `torrents`、`groups`、`requests`、`forum`、`users_admin` 与插件注册的扩展索引；
- 事件驱动的增量同步：窗口合并、批量写入、删除优先流、做种数部分更新（订阅 `traffic.swarm_stats_updated`）；
- 零停机全量重建（Meilisearch `swap-indexes`），设置变更的就地应用或自动重建；
- 内核代理的搜索 HTTP API、`search.before_query` 钩子、可选的 tenant token 直连模式；
- 中文与中英混排标题预处理、发布名解析字段、`localizedAttributes`；
- 同义词汇总（内置 PT 词包、资源类型插件、术语表、管理员自定义）；
- 拼写容错关闭字段、facet 分布与 facet 值搜索、筛选面板 schema；
- 混合搜索（关键词 + 向量），向量来自 `ctx.llm` 或 Meilisearch 内置 embedder；
- Redis 结果缓存、多实例部署（社区版只读副本扇出写入；企业版 network 模式可选）；
- MCP 工具 `search_torrents`；管理后台（索引状态、重建、同义词、实例、一致性巡检）。

**不包含**：

- 各索引文档的业务字段内容（由 torrent、type-*、accounting、promotion、requests、forum、identity 等贡献者插件定义）；
- 推荐系统、个性化排序（P2 以后另行设计）；
- Meilisearch 的部署与备份运维脚本（只给出要求）；
- Meilisearch 的对话式搜索（`/chats`）与其内置 MCP 端点——**禁止对外暴露**（会绕过可见性过滤，见 DD-SRCH-2）；
- 列表接口的结构化过滤（由各插件自己的 REST 列表接口提供，conventions/api.md §6）。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 逻辑索引 | 平台层的索引名，如 `torrents`；对应一个 Meilisearch“在线索引”（live uid） |
| 在线索引 / 构建索引 | Meilisearch 中实际承接查询的索引 `pt_torrents`；重建时新建的 `pt_torrents__next` |
| 贡献者 | 导出 `search-contributor` 并在清单设 `search_contributor = true` 的插件 |
| 拥有者（owner） | 对某逻辑索引的实体负责的贡献者（如 torrent 之于 `torrents`），提供 `id`、可见性字段与实体枚举 |
| 片段 | 贡献者 `to-document` 返回的 JSON 对象，搜索插件把同一实体的多个片段合并为一个文档 |
| 标脏 | 记录“某索引的某实体需要重新生成文档”或“需要删除”，等待批量写入 |
| 优先通道 | 删除、隐藏、下架等降低可见性的变更所走的低延迟写入通道 |
| 可见性字段 | 每个文档必须包含的 `vis_level`、`vis_min_class`、`vis_owner_id` |
| CE / EE | Meilisearch 社区版（MIT）/ 企业版（BUSL-1.1，生产使用需商业协议） |

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | **Native**（热点读路径；需要批量、并发控制和长连接 HTTP 客户端） |
| 提供的服务 | `ctx.search@0.1.0`（single） |
| 依赖（requires） | `ctx.users`（读取 class_id）、`ctx.rbac`（检查可见性相关权限）、`ctx.terms`（同义词与字段显示名） |
| 可选依赖 | `ctx.llm`（查询向量、文档向量；缺失时关闭混合搜索） |
| 调用的扩展点 | 各贡献者的 `search-contributor`（由内核按提供方枚举调用，kernel/03 §4.7） |
| 只读视图 | `torrent.v_torrent_public`、`torrent.v_group_public`、`identity.v_user_public`（重建时枚举实体、按 Group 展开种子；在拥有者实现 `list-ids` 前作为兜底，见 HLD §7） |
| 外部系统 | Meilisearch CE ≥ v1.54（按 v1.54.3 验证），1～N 个实例 |

**为什么不 requires `ctx.torrents`**：torrent 插件需要 `optional_requires ctx.search`（调用 `touch`/`remove`），若 search 再依赖 `ctx.torrents` 会形成依赖环（kernel/03 §3.3）。搜索插件只通过事件、贡献接口和只读视图获取种子数据。

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 普通用户 | 关键词搜索种子 / 作品 / 求种 / 帖子；用筛选面板按类型、分辨率、促销、年份过滤；按做种数、时间排序；按作品折叠；自然语言搜索；输入时联想 |
| 审核员（moderator） | 搜索候选区与待审核资源（`vis_level = staff`），搜索被隐藏但未删除的资源 |
| 管理员 | 搜索 `users_admin`；查看索引状态与延迟；触发重建；维护同义词；查看实例健康；一致性巡检 |
| AI 客户端（MCP） | `search_torrents` 工具：以用户身份搜索，继承权限过滤，返回已渲染术语 |
| 其他插件 | rss（按条件生成订阅）、crossseed-api、requests（重复检查）、ai-upload-review（查重）、ai-assistant 通过 `ctx.search.query` 搜索；贡献者插件调用 `touch`/`remove` 通知变更 |
| 前端直连（可选） | 管理员开启 tenant token 模式后，前端用短期 token 直连 Meilisearch |

### 2.3 现有开源 PT 程序的做法调研

| 项目 | 做法 | 优点 | 缺点 | 我们采纳 / 改进 |
|---|---|---|---|---|
| **Gazelle（WCD/OPS/RED）** | Sphinx（OPS 后迁 Manticore）：`torrents` 主索引 + `delta` 增量索引；cron 每分钟重建 delta、定期全量合并；搜索参数直接映射为 SphinxQL；Group 维度聚合（同一作品的多个版本折叠） | 增量与全量分离，主索引重建不影响查询；Group 折叠体验好；按格式、码率、发行类型等结构化字段过滤 | 索引 schema 写死在 sphinx.conf，强绑定音乐；delta 依赖时间戳轮询数据库，删除需要额外的 kill-list，否则已删除资源会短暂可见；分钟级延迟 | 采纳“全量与增量分离”“Group 折叠（`distinct = group_id`）”“结构化字段过滤”；改进：事件驱动替代轮询；删除走独立优先通道（秒级）；schema 由贡献者插件声明而非写死 |
| **UNIT3D** | Laravel Scout + Meilisearch；`config/scout.php` 为 Torrent 模型手写 `searchableAttributes`、细粒度 `filterableAttributes`（`attributePatterns` + `features`，区分 equality / comparison，关闭 facetSearch）、`sortableAttributes`、`rankingRules`、`typoTolerance.disableOnWords`（如 `blu-ray`）、`dictionary`；文档中反规范化大量关联（`history_seeders.user_id`、`bookmarks.user_id`、`tmdb_movie.genres.id` 等） | 已在生产验证 Meilisearch 可承载 PT 种子搜索；细粒度 filterable 降低索引成本；对 `blu-ray` 这类词关闭容错并加入词典 | 设置绑定 TMDB 影视字段；把“谁在做种、谁收藏了”等按用户的数组写进文档，任一用户行为都触发文档重写，写放大严重；Scout 的模型观察者每次保存即推送，没有窗口合并；没有服务端强制可见性抽象（依赖查询代码自觉加条件） | 采纳细粒度 filterable、词典与 `disableOnWords`、排序规则思路；改进：**不把按用户的行为数组写进文档**（“我在做种”之类走 accounting 查询再按 ID 过滤）；窗口合并 + 批量；可见性在服务端统一强制，并开放 `search.before_query` 钩子只能追加条件 |
| **NexusPHP** | 传统 SQL：`torrents.php` 用 `LIKE '%kw%'` 或数据库全文检索，按“标题 / 简介 / 副标题 / 上传者 / IMDb”选择搜索范围；分类、来源、媒介、编码、分辨率等是独立的字典表，筛选面板由这些表生成 | 筛选维度由管理员在后台维护，适合中文站点；简单可靠 | `LIKE` 无法利用索引，数据量大时全表扫描；中文无分词；历史上 SQL 拼接导致注入（design/08）；无拼写容错、无同义词 | 采纳“筛选维度数据驱动、后台可维护”的思路（由资源类型插件 schema 驱动）；改进：全文检索交给 Meilisearch；过滤一律结构化参数，由服务端生成表达式，禁止用户传原始表达式 |
| **Luminance** | 继承 Gazelle 的 Sphinx 方案，增加标签搜索 | 标签检索 | 停更 | 标签（`torrent.tags`）作为可搜索 + 可筛选字段 |
| **Arcadia** | Rust 后端，内容无关目标；早期阶段，以 PostgreSQL 查询为主 | 内容无关的模型 | 尚无成熟搜索设计；AGPL | 只作为“内容无关 schema”方向的佐证 |
| **TorrentPier** | 关系数据库 + 可选 Sphinx/Manticore，论坛式结构 | 论坛帖子与种子统一检索 | 搜索与论坛强耦合 | 论坛帖子作为独立索引 `forum`，由 forum 插件贡献 |

调研结论落实为：DD-SRCH-1（事件驱动 + 窗口合并）、DD-SRCH-3（可见性字段契约）、DD-SRCH-5（swap 重建）、DD-SRCH-6（不写按用户数组）、DD-SRCH-8（同义词与术语联动）。

### 2.4 约束与假设

1. Meilisearch 只维护最新版本，没有 LTS（官方说明）。插件锁定“最低兼容版本”v1.54，CI 用固定版本镜像 `getmeili/meilisearch:v1.54.3` 回归；升级 Meilisearch 主版本前须跑 TP-SRCH 全量。
2. 默认只使用 **CE（MIT）** 功能。复制与分片仅在 EE（BUSL-1.1，生产使用须与 Meilisearch 签商业协议）v1.37+ 提供，插件把它作为可选部署模式，不作为默认依赖（D19 要求官方插件 MIT OR Apache-2.0；我们通过 HTTP 调用 Meilisearch，不链接其代码，不产生许可证传染）。
3. 平台约束：钩子中不能出站 HTTP、不能调 LLM——搜索本身不在钩子中执行；`search.before_query` 的处理者也不得调用 LLM。事件订阅只保证数据库副作用恰好一次，写 Meilisearch / Redis 必须自带幂等。
4. 做种数来自 accounting 发布的 `traffic.swarm_stats_updated`（每 3～5 分钟，只含变化的种子），精度由 accounting 决定（平台 README Q13）。
5. 规模假设：种子文档 1000 万、作品 300 万、帖子 2000 万；峰值查询 2000 QPS（缓存后到 Meilisearch 约 600 QPS）。
6. Meilisearch 的 `pagination.maxTotalHits` 默认 1000，深分页不支持（与 Gazelle/UNIT3D 一致的产品取舍）。

## 3. 功能需求

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-SRCH-001 | 查询服务 | 提供 `ctx.search.query(SearchRequest) -> SearchResult`，对每次查询在服务端强制附加可见性过滤 | P0 | 任意调用方（HTTP、MCP、服务调用）都无法得到其无权看到的文档 |
| FR-SRCH-002 | 贡献者发现 | 启动时通过 `ctx.plugins.search_contributors()` 取得贡献者列表，调用其 `index-schemas()` | P0 | 后台可见每个索引的贡献者与字段来源；单个贡献者失败不影响其他 |
| FR-SRCH-003 | schema 合并 | 合并同一索引的全部字段声明；同名字段冲突、类型非法时拒绝该贡献者的冲突字段并告警，不阻止启动 | P0 | 冲突出现时指标 `schema_conflicts` > 0，索引仍可用 |
| FR-SRCH-004 | 字段命名与黑名单 | 非拥有者字段必须带贡献者前缀；保留前缀 `vis_`、`rel_`、`_`；字段名或文档键命中敏感黑名单（passkey、email、ip、password、token、secret 等）一律拒绝 | P0 | 违规字段不进入设置也不进入文档；记录日志与指标 |
| FR-SRCH-005 | 设置生成 | 由合并 schema 生成 Meilisearch 设置：`searchableAttributes`（按 rank）、细粒度 `filterableAttributes`、`sortableAttributes`、`typoTolerance`、`localizedAttributes`、`synonyms`、`dictionary`、`rankingRules`、`displayedAttributes`、`embedders`、`pagination`、`faceting` | P0 | 设置 JSON 与 LLD §1.3 规则一致，同输入生成同输出（哈希稳定） |
| FR-SRCH-006 | 标准索引 | 内置 `torrents`、`groups`、`requests`、`forum`、`users_admin` 五个逻辑索引及其拥有者映射 | P0 | 拥有者插件启用时索引自动建立；未启用时索引处于 `disabled` |
| FR-SRCH-007 | 扩展索引注册 | 插件通过 `ctx.search.register_index(IndexDef)` 注册自己的索引（名称须以插件 ID 派生的前缀开头），可声明 `audience` | P1 | 注册幂等；重名、越权前缀被拒绝 |
| FR-SRCH-008 | 事件标脏 | 订阅事件目录中与索引相关的事件（LLD §1.5 映射表），把受影响实体写入待写表；同一实体多次标脏合并为一条 | P0 | 同一事件重复投递只产生一次标脏；1 万次对同一实体的更新只写 1 次文档 |
| FR-SRCH-009 | 批量写入 | 待写实体按窗口（默认 2 s）合并，批量调用贡献者生成文档、批量写 Meilisearch | P0 | 普通变更 p95 ≤ 15 s 可被搜索到 |
| FR-SRCH-010 | 删除优先通道 | 删除、隐藏、下架、禁转、降级可见性的变更走优先通道（不等窗口、单独批次、单独 Meilisearch 任务），并使结果缓存立即失效 | P0 | 从事件提交到搜索不可见 p99 ≤ 5 s |
| FR-SRCH-011 | 做种数部分更新 | 订阅 `traffic.swarm_stats_updated`，按种子合并最新值，每分钟对 `torrents` 做只含 `accounting_seeders`、`accounting_leechers`、`accounting_completed` 的部分更新 | P0 | 不触发贡献者调用；不为未建索引的种子创建残缺文档；乱序事件不回退数值 |
| FR-SRCH-012 | 已索引记录 | 记录每个已写入实体的文档哈希、正文哈希与写入时间，用于去重写、向量复用、一致性巡检 | P0 | 文档未变化时不重复写入 |
| FR-SRCH-013 | 零停机重建 | 建立构建索引 → 枚举实体批量写入 → 校验 → `swap-indexes` 原子交换 → 删除旧索引；全程在线索引可查询 | P0 | 重建期间查询成功率 100%，交换前后结果无空窗 |
| FR-SRCH-014 | 重建期间双写 | 重建开始后的增量变更同时写入在线与构建索引，并记录被触碰实体，枚举结束后再处理一遍 | P0 | 重建期间更新的实体在交换后为最新状态 |
| FR-SRCH-015 | 设置变更分类 | 启动或同义词变更时比较设置哈希：仅设置变化 → 就地更新；字段集合或贡献者版本变化 → 按配置自动或手动重建 | P0 | 新增贡献者字段后自动触发重建（`auto_rebuild = true` 时） |
| FR-SRCH-016 | 搜索 HTTP API | `POST /api/p/search-meilisearch/v1/search` 等接口，经内核鉴权、权限、限流 | P0 | OpenAPI 完整；未登录 401；限流 429 |
| FR-SRCH-017 | 可见性基线 | 按调用者生成基线过滤：`vis_level`、`vis_min_class`、`vis_owner_id`；有 `search-meilisearch.restricted.read` 者可见 `staff` 级 | P0 | 普通用户看不到候选区（若站点配置为 staff）与等级限定资源 |
| FR-SRCH-018 | 查询钩子 | 每次查询触发 `search.before_query`，处理者只能追加过滤条件；钩子拒绝则返回其错误码；钩子失败 fail-closed | P0 | 删除已有条件的补丁被内核拒绝（TC-KRN-033 覆盖），本插件返回 503 `kernel.hook_failed` |
| FR-SRCH-019 | 结构化过滤校验 | 客户端只能传结构化过滤（字段、操作符、值）与排序字段；服务端校验字段可筛选、操作符被该字段支持，再生成表达式并转义字符串值 | P0 | 注入式输入（引号、`OR`、括号）不改变过滤语义 |

## 4. 非功能需求

| 编号 | 类别 | 描述 | 指标 |
|---|---|---|---|
| NFR-SRCH-001 | 性能 | 查询延迟（插件入口到返回，含钩子，不含网关） | 缓存命中 p95 ≤ 10 ms；未命中 p95 ≤ 80 ms、p99 ≤ 200 ms（1000 万文档，单实例 8C/32G） |
| NFR-SRCH-002 | 性能 | 混合搜索延迟（`llm` 模式，查询向量未命中缓存） | p95 ≤ 600 ms（主要为 embed 调用） |
| NFR-SRCH-003 | 新鲜度 | 普通变更可见延迟 | p95 ≤ 15 s，p99 ≤ 60 s |
| NFR-SRCH-004 | 新鲜度 | 删除 / 降可见性变更 | p99 ≤ 5 s |
| NFR-SRCH-005 | 吞吐 | 做种数部分更新 | ≥ 20,000 文档/分钟持续，不使 Meilisearch 任务队列积压超过 5 分钟 |
| NFR-SRCH-006 | 吞吐 | 全量重建 | 1000 万种子文档 ≤ 8 h（贡献者支持批量接口时目标 ≤ 3 h，待 P0 实测） |
| NFR-SRCH-007 | 可用性 | 重建、设置变更期间查询可用 | 100%（swap 原子） |
| NFR-SRCH-008 | 可靠性 | 增量同步不丢失 | 事件 → 标脏有 inbox 恰好一次；标脏行只在 Meilisearch 任务入队成功后删除；失败任务回收 |
| NFR-SRCH-009 | 幂等 | 所有对 Meilisearch 的写都是“按主键整体或部分替换”，重复执行结果相同；对外服务写方法带幂等键 | 重复投递 / 重复 cron 测试通过 |
| NFR-SRCH-010 | 安全 | 可见性过滤不可绕过；Meilisearch master key 只在服务端；tenant token 使用仅含 `search` 动作的专用 API key | 安全测试全部通过 |
| NFR-SRCH-011 | 隐私 | 索引与查询日志不含敏感字段；查询词在日志中截断为 64 字符并不记录 user_id 与查询词的组合到长期存储 | 日志审查通过 |
| NFR-SRCH-012 | 可观测性 | 指标：查询量 / 延迟 / 缓存命中率、待写积压、写入延迟、Meilisearch 任务失败、重建进度、实例延迟 | Grafana 面板 + 告警规则（LLD §8） |
| NFR-SRCH-013 | 可配置性 | 窗口长度、缓存 TTL、批大小、语义比例、自动重建、实例列表等可配置 | 运行时设置变更无需重启（实例列表除外） |
| NFR-SRCH-014 | 可扩展性 | 新资源类型插件只需导出 `search-contributor`，无需修改搜索插件和前端 | 新增 `type-x` 测试插件后筛选面板自动出现其字段 |
| NFR-SRCH-015 | 兼容性 | 最低 Meilisearch v1.54；启动时检查 `/version`，低于最低版本拒绝写入并告警 | 版本检查测试 |
| NFR-SRCH-016 | 许可证 | 默认部署只依赖 Meilisearch CE（MIT）；EE 功能只在显式配置时使用 | 配置审查 |
| NFR-SRCH-017 | 资源 | Redis 私有前缀配额 256 MB；PG 待写表在稳态 < 10 万行 | 监控 |
