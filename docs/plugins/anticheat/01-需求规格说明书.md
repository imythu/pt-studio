## 1. 引言

### 1.1 目的

本文定义 `anticheat` 插件（WASM，提供 `ctx.anticheat`）的需求。accounting 只输出作弊的**基础信号**（design/03 §6、SRS-ACC FR-ACC-015～020），不做判定；anticheat 负责把信号变成**判定与处置**：按站点可配置的数据驱动规则给用户打分，超过阈值自动开案进入人工复核队列，由版主/管理员决定警告、冻结流量、锁定钱包、禁止下载、封禁、回收虚报流量等处置，处置通过 identity、accounting、ledger 的服务执行；用户可以对处置申诉，申诉结果反馈到规则的误判统计中。

### 1.2 范围

| 包含 | 不包含 |
|---|---|
| 消费 `traffic.signal_raised`，把信号存为证据；接收其他插件上报的证据；本插件派生的“每日上传跳变”证据 | 信号的计算（accounting）；announce 与客户端白名单（pt-tracker / tracker-bridge） |
| 数据驱动的规则集（JSON DSL）：证据规则、聚合规则、乘数规则、处置策略；版本管理、影子模式、回测模拟 | 分享率、H&R、等级等其他规则判定（ratio-policy、hnr、levels） |
| 评分模型：权重、严重度、命中次数、时间衰减、单种子与单规则上限、跨 swarm 聚合、乘数；风险分段 | 机器学习模型训练（P2 以后可作为外部证据来源接入） |
| 案件：自动 / 手动开案、复核队列（排序、认领、SLA）、案件详情、处置决定、四眼复核 | 举报（reports 插件）——但举报可经 `report()` 作为证据进入 |
| 处置：警告、冻结流量、锁定钱包、禁止下载、封禁、回收虚报流量、重置 passkey；期望状态协调、到期、撤销 | 处置机制本身（identity 的限制、accounting 的倍率与调整、ledger 的锁定） |
| 钩子：`ledger.before_transfer`（调查中禁止转出），`checkin.before_check_in`（可选） | 注册、登录、评论等钩子（见 HLD DD-ACH-9） |
| 申诉：登录用户申诉、被封禁用户凭申诉令牌申诉；申诉复核与结果回滚 | 通用工单 / 客服系统 |
| 误判反馈、规则命中与准确率统计 | |
| 服务 `ctx.anticheat`、HTTP API、MCP 工具（含用 `ctx.llm` 解释案件）、前端插槽与页面 | |
| 同 IP 对端关联（P2，需站点授权 `peer.ip`、`user.ip`） | 存储或展示 IP 原文 |

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 信号（signal） | accounting 发布的基础事实（6 种：`cross_check_mismatch`、`speed_exceeded`、`peer_not_in_swarm`、`negative_delta`、`counter_jump`、`client_not_allowed`），含严重度、命中次数、证据详情 |
| 证据（evidence） | anticheat 内部保存的一条可计分事实。来源：accounting 信号、本插件派生（如 `daily_upload_spike`）、其他插件上报（`<plugin_id>.<kind>`）、管理员手工录入 |
| 规则集（ruleset） | 一份带版本号的 JSON 文档，包含阈值、证据规则、聚合规则、乘数规则与处置策略；同一时刻只有一个“生效”版本 |
| 证据规则 | 匹配单条证据并给出分值贡献的规则 |
| 聚合规则 | 在时间窗内对证据做聚合（不同种子数、不同证据类型数、计数、求和）并按阶梯给分，例如“7 天内 3 个以上种子交叉校验异常”（跨 swarm 关联） |
| 乘数规则 | 满足条件时把分数（或部分标签的分数）乘以系数，如“新账号 ×1.2”“曾被确认作弊 ×1.5”“盒子 ×0.5” |
| 处置策略（policy） | 分数 / 标签满足条件时建议或自动执行的处置组合 |
| 风险分（score） | 0～100 的整数；由生效规则集对用户窗口内证据计算得到 |
| 风险分段（band） | `none`（< low）、`low`、`watch`（观察名单）、`high`（开案）、`critical`（开案并优先），阈值在规则集中定义 |
| 影子模式（shadow） | 规则只计算“影子分”用于统计，不影响风险分、案件与处置 |
| 案件（case） | 针对一个用户的一次调查；同一用户同一时刻至多一个进行中的案件 |
| 认领（claim） | 复核员锁定案件以处理，带到期时间，防止多人重复处理 |
| 处置（sanction） | 案件决定产生的一项措施，带种类、到期时间与状态 |
| 效果（effect） | 处置在外部服务上的落地状态（identity 限制、accounting 倍率规则、ledger 锁、流量调整）；由“期望状态协调器”保证幂等落地 |
| 冻结流量 | 通过 `ctx.accounting.set_rate_rule` 为该用户设置 override 规则，使其上传计入倍率为 0（下载按配置照常计入或不变），到期自动解除 |
| 锁定钱包 | 通过 `ctx.ledger.lock_account` 禁止该用户全部币种转出 |
| 结论性规则（conclusive） | 带 `conclusive` 标签、误判率经统计极低的规则（如速度超过上限 5 倍且单次 ≥ 10 GiB），只有它可以触发自动处置 |
| 熔断器 | 一小时内自动处置数超过上限时暂停全部自动处置并告警，防止错误规则大面积误伤 |
| 四眼原则 | 封禁与申诉复核必须由不同于原决定人的第二人完成 |

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | WASM（低频、规则密集、需要可替换；不在热路径上） |
| 提供服务 | `ctx.anticheat@0.1.0`（single） |
| 必需依赖 | `ctx.users`（用户摘要、限制施加 / 解除；作用域 `write:status`）、`ctx.accounting`（信号查询、用户总量、倍率规则、流量调整；作用域 `read`、`read:signals`、`write:rates`、`write:adjust`） |
| 可选依赖 | `ctx.ledger`（锁定钱包；作用域 `lock`）、`ctx.messages`（站内信通知）、`ctx.notify`（邮件 / 即时通讯通知，封禁时投递申诉令牌）、`ctx.seedbox`（盒子识别，降低速度类规则权重）、`ctx.tracker`（案件证据补全：swarm peer 快照）、`ctx.llm`（MCP / 后台解释案件）、`ctx.rbac`（服务调用时检查操作者权限） |
| 只读视图 | `accounting.v_user_daily`（每日上传跳变；见 HLD §7 A-12） |
| 钩子处理 | `ledger.before_transfer`、`checkin.before_check_in`（可选） |
| 敏感数据 | 默认不申请；P2 的同 IP 关联在 `sensitive_optional` 中申请 `peer.ip`、`user.ip`，只在内存中比较，不落库 |
| 消费方 | levels / invite / shop 等可调 `risk()` 在调查期间限制特权（各自决定）；mcp；ai-assistant（只读） |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 普通用户 | 收到警告 / 处置通知；在“我的案件”查看处置原因摘要、影响的种子与到期时间；在申诉期内提交申诉，查看申诉结果 |
| 被封禁用户 | 无法登录；凭封禁通知邮件中的申诉令牌在公开申诉页提交申诉 |
| 版主（复核员） | 浏览复核队列，按风险分与等待时长处理；认领案件，查看证据、分数构成、相关流量与 peer 快照；作出“误判 / 不处理 / 处置”决定；处理申诉（四眼） |
| 管理员 | 编辑规则集草案、影子运行、回测模拟、激活与回滚；配置处置策略与熔断器；批准封禁（四眼）；查看规则准确率与运营看板；手工开案、手工处置与解除 |
| 其他插件 | accounting 发布信号；seedbox 等上报外部证据；levels / invite 查询 `risk()`；ledger 在转账前触发钩子 |
| AI 客户端（管理员） | `admin_list_anticheat_cases` 查看队列；`admin_explain_anticheat_case` 获取对异常信号的自然语言解释；`admin_resolve_anticheat_case` 在确认后处置 |

### 2.3 现有开源 PT 程序的做法调研

| 项目 | 做法 | 优点 | 缺点 | 我们采纳 | 我们改进 |
|---|---|---|---|---|---|
| NexusPHP | announce 中同步执行 `check_cheater()`：速度超过“必定作弊”阈值直接禁用账号并写封禁日志；“可能作弊”与“无下载者 / 下载者少时上传”写 `cheaters` 表，(用户, 种子) 24 h 内累加 `hit`；`cheaterdet_security` 安全等级缩放阈值；后台 `cheaters` 页人工标记已处理 | 规则直观；hit 去重让队列不被刷屏；安全等级一键调整灵敏度 | 判定在 announce 热路径上，阈值写死在代码中；单条规则直接封号，盒子、千兆用户、客户端统计 bug 都会误伤，且无申诉流程；无评分、无多证据综合；处理结果不反馈到规则 | 分档严重度；同一 (用户, 种子, 规则) 去重计 hit（accounting 已实现）；“极端速度”作为结论性规则 | 判定移出热路径；多证据加权评分；结论性规则默认也只**冻结**不封号，封禁需人工 + 四眼；安全等级变为可回测的规则集版本 |
| UNIT3D | “作弊种子”页：种子平衡值（累计上传 − 累计下载）相对体积超出容差即列出，按“被刷倍数”排序，复核后重置基线；“可疑 leech 作弊者”页：在 history 中出现但没有任何传输记录的用户；Announce 服务按 UA / 正则 / 端口黑名单拒绝；警告累计到期 | 平衡值本质上就是 swarm 守恒校验，排除“最近一个 announce 间隔仍在传输”的种子以消除边界误差；基线重置避免历史问题反复出现 | 停留在“列表给员工看”，没有把种子维度的异常归因到具体用户；无评分与处置流程，处置仍靠员工手工改用户；列表查询直接扫描 history 大表 | 种子视角的异常列表（FR-ACH-042）与“复核后重置”；交叉校验的容差与边界排除（accounting 已在小时粒度做） | 归因到上传占比最高的用户（accounting `cross_check_mismatch`），再由 anticheat 做跨 swarm 聚合；列表读本插件的证据表而不是扫描大表 |
| Gazelle / OPS（含 Ocelot） | Ocelot 只接受白名单客户端前缀；员工工具箱有 ratio watch、重复 IP、ASN 查询等；警告以时间区间存储并从现有警告到期时顺延，写用户审计轨迹；被禁用户可经邮箱提交 enable request 自助恢复 | 严格的客户端白名单从源头减少作弊客户端；警告叠加到期语义清晰；自助恢复流程降低客服负担 | 没有基于流量数据的自动作弊检测；工具分散、依赖员工经验；enable request 只针对“非活跃禁用”，不区分作弊封禁 | 警告顺延叠加；审计轨迹；被封用户的自助申诉通道（申诉令牌，经通知渠道投递） | 申诉与案件关联、四眼复核；申诉结果自动回滚处置并反馈规则统计 |
| Luminance / TorrentPier | 依赖 tracker 的基础检查与员工人工判断；TorrentPier 展示 peer 速度，无作弊判定模块 | — | 缺少系统化检测 | — | — |
| TU Wien（Amanshauser 2009） | swarm 内上传 / 下载守恒校验 + 跨 swarm 关联分析 | 不依赖客户端指纹，作弊者难以规避；论文结论是两种方法在作弊者采取对策时仍有效 | 单个 swarm 的守恒存在时间边界与统计误差，单次异常只是弱证据 | swarm 内守恒（accounting 已输出 `cross_check_mismatch`）；跨 swarm 聚合规则：同一用户在 7 天内多个不同种子上出现超额归因，分数阶梯上升 | 把论文的两类方法表达为可配置、可回测的规则，与速度、无对端、计数异常等证据综合打分 |

总结：前人的共同问题是“单规则即判定”“阈值写死”“处置后无反馈”。我们的改进是：**证据与判定分离、多证据评分、规则数据化且可影子运行与回测、人工复核为默认、处置可撤销、申诉结果反馈准确率**。

### 2.4 约束与假设

1. WASM 插件：每次调用一个新实例，无跨调用内存状态（规则集每次从数据库加载并解析）；每次调用一个数据库事务；cron 与延迟任务 `tx = "manual"` 分批提交；钩子中不能出站 HTTP、不能调用 `ctx.llm`。
2. 跨插件调用（identity、accounting、ledger、messages、notify）不与本插件事务原子；所有调用带幂等键，处置的落地采用“先在本事务中记录期望状态，再由延迟任务执行并确认”的方式（HLD DD-ACH-4）。
3. 信号量级：accounting 去重后每用户每种子每信号每日至多 1 条 + 严重度升级（SRS-ACC FR-ACC-020）；按 30 万用户估算，日常 ≤ 5 万条 / 天，异常高峰（错误配置的阈值）≤ 50 万条 / 天。
4. `traffic.signal_raised` 只在首次、去重期过期、严重度升级时发布，之后的命中累加在 accounting 的 `hits` 中不再发布；anticheat 在开案和每日重算时调 `ctx.accounting.signals()` 刷新命中数。
5. identity 对同一 (用户, 类型, 来源) 只保留一条生效限制，且插件不能封禁拥有 `moderator` 及以上角色的用户（`identity.target_protected`）；anticheat 必须把同一用户的多个处置合并为一条期望限制。
6. accounting 的 `adjust` 不允许使计入总量为负；回收虚报流量的金额以复核员确认的值为准，不超过用户当前计入上传。
7. 依赖尚未合入平台目录的接口：identity 的 `apply_restriction` / `lift_restriction` / `restrictions` 与 `user.restriction_changed`（identity HLD §7）、ledger 的 `lock_account` / `unlock_account` 与作用域 `lock`（ledger HLD §7 L-1、L-2）、accounting 的 `signals` 游标与视图 `v_user_daily`（accounting HLD §7 N-5、N-11）。未合入时对应功能降级（HLD §7）。
8. 不读取、不存储 IP；事件、日志、MCP 输出中不出现 IP、passkey、邮箱（security.md §4）。

## 3. 功能需求

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|

| NFR-ACH-001 | 性能 | 单条信号处理（入库 + 增量评分 + 可能开案） | p99 ≤ 200 ms（用户窗口内证据 ≤ 2000 条） |

| NFR-ACH-004 | 确定性 | 同一证据集、同一规则集版本、同一计算时间点得到相同分数与构成 | 参考实现比对 0 差异 |
| NFR-ACH-005 | 一致性 | 本插件数据库副作用对同一事件恰好一次；外部处置至少一次落地且幂等（不重复封禁 / 不重复回收） | 混沌测试 0 重复调整、0 遗漏处置 |

| NFR-ACH-007 | 可解释性 | 每个分数可追溯到规则贡献与证据；每个处置可追溯到案件、决定人与规则集版本 | 案件详情可完整重建分数 |
| NFR-ACH-008 | 安全 | 全部后台接口按权限点检查；四眼规则在服务端强制；申诉令牌只存哈希；公开申诉接口限流 | 安全用例通过 |
| NFR-ACH-009 | 隐私 | 不存储 IP、passkey、邮箱；事件、日志、MCP、LLM 输入不含敏感字段与申诉正文；用户 purge 24 h 内完成 | 扫描零命中 |

| NFR-ACH-012 | 可配置性 | 阈值、权重、策略全部数据化（规则集）；运行参数经 settings schema 校验；非法规则集不能激活 | 测试通过 |
| NFR-ACH-013 | 容量 | 证据 ≤ 2000 万行 / 年；用户风险表 ≤ 用户数；WASM 内存 ≤ 64 MiB | 见 LLD §3.1 估算 |
| NFR-ACH-014 | 资源 | 单次调用遵守 WASM 截止时间：事件 2 s、HTTP 2 s、cron / 延迟任务单批 ≤ 30 s | 无超时失败 |

## 6. 外部接口需求概述

- **服务**：`ctx.anticheat`（LLD §2.1 WIT）。
- **事件发布**：`anticheat.case_opened`、`anticheat.case_resolved`（已登记）；`anticheat.sanction_changed`、`anticheat.appeal_submitted`、`anticheat.appeal_decided`（新增）。
- **事件订阅**：`traffic.signal_raised`、`user.restriction_changed`（identity 新增事件）、`user.deleted`。
- **钩子**：处理 `ledger.before_transfer`、`checkin.before_check_in`。
- **HTTP**：`/api/p/anticheat/v1/…`（LLD §2.4）。
- **MCP**：`admin_list_anticheat_cases`、`admin_explain_anticheat_case`、`admin_resolve_anticheat_case`（已预留）。
- **前端**：`admin.dashboard.widgets`、`admin.user.tabs`、`/admin/p/anticheat/*`、`/p/anticheat/*`。
- **视图**：读取 `accounting.v_user_daily`。
