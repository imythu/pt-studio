## 1. 设计目标与原则

1. **证据与判定分离**：accounting 只产信号；anticheat 把信号、派生证据、外部证据统一存为不可变证据，判定只依赖证据与规则集版本，任何分数都可重算、可解释。
2. **规则是数据**：阈值、权重、聚合、乘数、处置策略全部在版本化的 JSON 规则集中；规则可以影子运行、回测模拟，激活与回滚可审计。站点不需要改代码就能调整灵敏度。
3. **人工复核为默认**：自动处置只限“结论性规则 + 可逆措施”（冻结流量、锁定钱包），封禁永远经人工且默认四眼；熔断器防止错误规则大面积误伤。
4. **处置是期望状态**：每个用户的全部处置合成一组期望效果，由协调器幂等地落地到 identity / accounting / ledger；本插件事务只记录“想要什么”，外部调用在延迟任务中带幂等键执行并确认（平台：跨服务调用不与本事务原子）。
5. **可撤销、可申诉、有反馈**：每项处置都有撤销路径；申诉撤销自动回滚并把结论回写为规则的误判统计。
6. **WASM 友好**：无跨调用内存状态（规则集每次加载）；单次调用工作量有上界（每用户证据窗口上限、批量任务分批提交）；钩子路径只读一行。
7. **隐私最小化**：不存 IP、passkey、邮箱；用户可见信息不暴露阈值与分数，避免规避；LLM 只看数值证据。

## 2. 总体结构

```
 accounting ──traffic.signal_raised──┐          identity ──user.restriction_changed / user.deleted──┐
 seedbox / 其他插件 ──ctx.anticheat.report──┤                                                          │
 cron daily_upload_spike（读 accounting.v_user_daily）──┤                                              │
                                     ▼                                                                 ▼
 ┌──────────────────────────────── anticheat（WASM）─────────────────────────────────────────────────┐
 │ ingest ─► evidence ─► scoring（rules 解释器 + context）─► user_risk ─► cases（开案 / 追加 / 队列） │
 │                                         │                     │                                     │
 │                                  policies（自动处置、熔断）    decisions（复核、四眼、批准）          │
 │                                         └──────────► sanctions ◄──────────┘   appeals（申诉、令牌）  │
 │                                                          │                                          │
 │                                     effects（期望状态 rev → 延迟任务 run_effects 落地 / 巡检）        │
 │ enrich（刷新 hits、swarm 快照、IP 关联）  simulate（回测）  stats（准确率）  privacy（purge / 保留）    │
 │ hooks（ledger.before_transfer、checkin.before_check_in）  service  http  mcp  ui                      │
 └───────────────┬────────────────────────────┬──────────────────────────┬───────────────────────────┘
                 ▼                            ▼                          ▼
   ctx.users.apply/lift_restriction   ctx.accounting.set/remove_rate_rule、adjust   ctx.ledger.lock/unlock_account
   ctx.users.reset_passkey            ctx.accounting.signals、user_totals          ctx.messages / ctx.notify（通知）
                 PostgreSQL schema anticheat：rulesets / evidence / user_risk / user_context / cases / case_* /
                 sanctions / effects / effect_ops / appeals / appeal_tokens / rule_stats / simulations / explanations
```

| 模块 | 职责 |
|---|---|
| `ingest` | 信号订阅入库；`report()` 与手工证据；`daily_upload_spike` 派生证据 |
| `rules` | 规则集加载（生效版本）、JSON Schema + 语义校验、DSL 解释器（纯函数） |
| `context` | 用户上下文（账号天数、等级、受保护角色、确认作弊次数）与按种子的盒子标记，24 h 缓存 |
| `scoring` | 读取窗口证据 → 规则计算 → 分数、影子分、构成、分段；写 `user_risk` |
| `cases` | 开案、追加证据、优先级、认领、SLA、关闭；时间线 |
| `decisions` | 复核决定、权限分级、四眼批准、员工保护 |
| `policies` | 处置策略的自动执行、熔断器 |
| `sanctions` | 处置记录、合并为期望效果、到期 |
| `effects` | 期望状态修订号、执行器（延迟任务）、巡检（cron）、外部覆盖检测；一次性操作队列（流量调整、通知、passkey 重置） |
| `appeals` | 申诉提交（会话 / 令牌）、复核、结果回滚 |
| `enrich` | 开案与重算时刷新命中数、swarm 快照、（P2）同 IP 对端 |
| `simulate` | 回测草案规则集 |
| `stats` | 规则命中与准确率 |
| `privacy` | 用户删除、数据保留 |
| `hooks` / `service` / `http` / `mcp` / `ui` | 接口层 |

## 4. 数据设计概要

| 实体 | 存储 | 说明 |

## 5. 关键流程

### 5.1 信号 → 评分 → 开案 → 自动策略

```
accounting ──traffic.signal_raised{signal_id, user_id, torrent_id?, signal, severity, hits, details, first_at}──► on_signal（一个事务）
  inbox 去重（内核）
  INSERT evidence(source='accounting', external_ref='signal:<id>', …) ON CONFLICT DO NOTHING
  rs = load_active_ruleset()；ctx = context.get(user)（过期则刷新：ctx.users.get、ctx.rbac.roles_of、ctx.seedbox）
  s = scoring.compute(user, rs, ctx, now)            -- 窗口内证据 ≤ 2000 条
  UPSERT user_risk(score, shadow, band, breakdown, transfer_blocked, ruleset_version)
  if s.band ≥ high:
      case = 进行中案件 ?? INSERT cases(...)（部分唯一索引防并发重复） → publish anticheat.case_opened
      INSERT case_evidence(快照)；更新 case.score/priority；jobs.schedule_once(enrich_case, dedupe=case_id)（仅新开案）
  for p in rs.policies where p.auto and p 条件满足:
      if 熔断/总开关/受保护/激活重算中 → 记录“建议处置”于时间线，不执行
      else INSERT sanctions(state='pending', by=policy) → effects.bump(user) → schedule run_effects
COMMIT（含事件、延迟任务）
run_effects(user)（延迟任务）：见 5.3
```

### 5.2 人工复核

```
版主 ─POST /admin/cases/{id}/claims─► UPDATE cases SET assigned_to, claim_expires_at WHERE id AND (assigned_to IS NULL OR claim_expires_at < now() OR assigned_to = me)
版主 ─POST /resolutions {decision: sanction, actions:[{kind: freeze_traffic, days: 7},{kind: adjust_traffic, up_bytes: …}], note}─►
   校验：认领者 = me；每个处置的权限（rbac）；员工保护；ban 且 four_eyes → sanction.state = proposed
   INSERT sanctions；cases.state = resolved；case_events；stats；publish anticheat.case_resolved
   effects.bump(user)；schedule run_effects；audit
管理员 B ─POST /sanctions/{id}/approvals─► B ≠ 提议人 → state proposed → pending → bump → run_effects
```

### 5.3 期望状态协调

```
effects.bump(user)：在当前事务内根据 sanctions(state ∈ pending/active) 计算期望：
    ban      = 最晚到期（任一永久 → 永久）     leech = 同上
    freeze   = 最晚到期                         wallet = 是否存在
  与 effects 行比较，变化则 rev += 1，state = pending；schedule_once(run_effects, now, {user}, dedupe="eff:<user>:<rev>")
run_effects(user)（tx manual）：for e in effects(user) where applied_rev < rev:
    调用外部服务（幂等键 "ach:eff:<user>:<effect>:<rev>"）
      ban/leech：apply_restriction{kind, reason_code, note:"case:<id>", until} 或 lift_restriction
      freeze：set_rate_rule{external_ref:"freeze:<user>", users[user], override, up 0, down?, ends_at} 或 remove_rate_rule
      wallet：lock_account / unlock_account
    成功：applied_rev = rev，记录外部 ID，pending sanctions → active，publish sanction_changed；commit
    可重试错误：attempts += 1，退避重新调度；永久错误（target_protected 等）：state = failed，sanction failed，告警
  再处理 effect_ops（流量调整、通知、passkey）：同样“幂等键 + 结果回写”
effect_reconcile（cron）：重试 pending/failed(可重试) 超时项；抽样调 ctx.users.restrictions 比对漂移
on_restriction_changed：source=anticheat 且 op=lifted 且非本插件发起（无匹配 pending lift）→ effects.state = overridden，案件时间线记录
```

### 5.4 申诉

```
用户 ─POST /users/me/cases/{id}/appeals{body}─► 窗口内、次数内 → INSERT appeals(submitted) → publish appeal_submitted
被封用户：封禁生效时 effect_ops(notify) 生成令牌（存哈希）→ ctx.notify.send(user, "anticheat.ban_notice", {link: /p/anticheat/appeal#t=<token>})
         ─POST /appeals:by-token{token, body}─► 校验哈希、未用、未过期 → 标记 used → 同上
复核员（≠ 原决定人）─POST /appeals/{id}/decisions{outcome: overturned, compensate_freeze: true}─►
   overturned：全部 sanctions → overturned；adjust 撤销 op；可选补偿 op；evidence verdict=false_positive；case.state=overturned
   reduced：修改 until / 解除部分；upheld：不变
   effects.bump；stats；publish appeal_decided（+ case_resolved{resolution: overturned}）；通知用户
```

### 5.5 规则集生命周期

```
POST /rulesets（草案 v4）→ validate（schema + 语义）→ POST /rulesets/4/simulations（异步 simulate_batch 分批）
→ 查看结果（分段分布、新增开案数、与历史结论重合、估计准确率、与 v3 差异）
→ POST /rulesets/4/activations（require_simulation_before_activate 时检查有完成模拟且草案未再修改）
   事务：v3 → retired，v4 → active；audit；schedule rescore_batch(cursor=0, mode=activation)
rescore_batch：分批 500 用户重算（不触发自动策略，只更新分数、开案）；进度存 kv
回滚：激活 v3（重新复制为新版本 v5 = v3 内容，保证版本单调）
```

## 6. 设计决策

| 编号 | 问题 | 备选方案 | 结论 | 理由 |
|---|---|---|---|---|
| DD-ACH-1 | 判定在哪里执行 | A announce 热路径（NexusPHP）；B accounting 落库时；C 本插件异步订阅信号 | C | 热路径不能有业务规则（design/01 原则 2）；判定需要跨种子、跨时间的证据，异步订阅天然适合；WASM 插件可替换 |
| DD-ACH-2 | 单规则判定还是评分 | A 任一信号即判定；B 加权评分 + 结论性规则 | B | 单信号误判率高（盒子、客户端 bug、交叉校验时间边界）；TU Wien 指出跨 swarm 关联才是强证据；结论性规则保留“明显作弊立即止损”的能力 |
| DD-ACH-3 | 规则表达方式 | A 写死在代码中；B 受限 JSON DSL；C 嵌入表达式语言（CEL / Rhai）；D 规则作为独立 WASM 插件 | B | B 可用 JSON Schema 校验、可视化编辑、可回测、执行时间线性有界、无注入面；C 引入大型解释器（体积、沙箱逃逸评估）且错误表达式难以给出友好提示；D 粒度过大，站长无法自己改；需要更复杂逻辑的站点可以通过 `report()` 以外部插件上报证据 |
| DD-ACH-4 | 处置如何落地到其他插件 | A 在决定事务中直接调用服务；B 记录期望状态，延迟任务落地并确认 | B | 跨服务调用不与本事务原子：A 在服务成功而本事务回滚时产生“无记录的封禁”；B 的决定是持久事实，外部调用带由修订号派生的幂等键可安全重试，失败可见、可巡检 |
| DD-ACH-5 | 同类处置合并 | A 每个处置单独调用 identity；B 合成期望状态 | B | identity 对同一 (用户, 类型, 来源) 只保留一条限制（identity LLD §1.6）；逐个解除会误解除其他案件的限制 |
| DD-ACH-6 | 冻结流量的实现 | A 事后用 `adjust` 扣回；B 用户级 override 倍率规则（上传 0）；C 让 tracker 拒绝 announce | B | 实时生效、到期自动解除、不改历史（只追加）；A 需要计算冻结期间的上传且用户先看到虚高数据；C 等于禁止下载，过重 |
| DD-ACH-7 | 自动处置的边界 | A 允许自动封禁（NexusPHP）；B 仅可逆措施自动；C 完全不自动 | B，默认仅结论性规则 | 结论性作弊需要立即止损（否则虚报流量继续换取魔力值与等级）；冻结与锁钱包可逆且不影响用户正常下载；封禁不可逆的社会成本高，必须人工 |
| DD-ACH-8 | 证据是否复制信号 | A 只存 signal_id，用时调 `signals()`；B 复制必要字段为不可变证据 | B | 评分需要批量读取（每次几百条），逐条跨插件调用不可行；accounting 信号保留 12 个月且可能更新 hits，案件需要不可变快照；外部证据与派生证据需统一结构 |
| DD-ACH-9 | 注册哪些钩子 | catalog 预期 anticheat 处理 `user.before_register`、`user.before_login`、`comment.before_create`、`checkin.before_check_in`、`ledger.before_transfer`、`mcp.before_tool_call` | 只处理 `ledger.before_transfer`（+ 可选签到） | 注册钩子无 IP / 邮箱时没有作弊相关输入，且 fail-closed（锁定）会让 anticheat 故障阻断注册；登录：被封用户已由 identity 拒绝；评论与 MCP 与流量作弊无关。转账钩子用于防止调查期间把魔力值转移到小号 |
| DD-ACH-10 | WASM 无内存状态下的规则集加载 | A 每次从 PG 读取并解析；B 编译结果放 kv | A | 规则集 ≤ 64 KiB，解析 < 1 ms；B 需要处理缓存失效与版本漂移，收益很小 |
| DD-ACH-11 | 是否使用 Redis | A 分数缓存在 Redis；B 物化在 PG `user_risk` | B | 钩子只读一行主键查询（< 1 ms）；Redis 与 PG 双写引入不一致；信号量低 |
| DD-ACH-12 | 被封用户如何申诉 | A identity 提供受限会话；B 一次性申诉令牌经通知渠道投递 | B | 不改动 identity 的封禁语义（封禁撤销全部会话）；令牌放 URL fragment，不进入服务器日志与 Referer；Gazelle 的 enable request 也走邮件 |
| DD-ACH-13 | AI 解释的执行方式 | A HTTP 内同步调用 `ctx.llm`；B 延迟任务生成并缓存 | B（MCP 先查缓存，必要时同步尝试） | LLM 延迟不可控，超出 HTTP 截止时间；解释可缓存复用；LLM 只读数值证据，不参与判定（design/07 §3“只作建议”） |
| DD-ACH-14 | 同 IP 关联的数据处理 | A 存 IP 哈希做长期关联；B 只在调用内比较，证据存对端用户 ID | B | 哈希 IP 仍属可关联的个人数据，且 IPv4 空间可被穷举还原；只存结论最小化隐私风险 |
| DD-ACH-15 | 时间衰减 | A 入库时折算权重；B 计算时按年龄衰减 | B | 计算时衰减使分数可在任意时间点复现，换半衰期无需改数据；模拟可按历史时间点计算 |
| DD-ACH-16 | `case_resolved.action` 只能表达单个动作 | A 改为数组（破坏兼容）；B 保留 `action`（最严重的一项）并新增 `actions[]` | B | 事件字段只增不删（plugin-api §6） |
| DD-ACH-17 | 用户可见信息的粒度 | A 展示完整证据与分数；B 只展示种类、时间、种子与处置 | B | 暴露阈值与权重会帮助作弊者调整虚报幅度；同时保证用户知道“因为什么、涉及哪些种子”以便申诉 |
