## 1. 引言

### 1.1 目的

定义 `registration-policy` 插件（WASM，提供 `ctx.registration`）的功能与非功能需求：决定“谁、何时、经过哪些关卡才能注册”。包括开放 / 关闭 / 限时开放、名额上限、答题注册（题库）、可插拔验证码、邮箱域名白 / 黑名单、同 IP / 设备限制（隐私合规）、策略组合规则，以及审核制注册（申请通过后由本插件调用 `ctx.users.create` 建号）。本文是 HLD-REGP、LLD-REGP、TP-REGP 的依据。

### 1.2 范围

**包含**

- 注册**通道**（channel）模型：`open`（自由注册）、`invite`（带邀请码）、`application`（审核制申请通过后建号）、`admin`（管理员建号）、`import`（导入）；每个通道独立开关与关卡组合。
- 可用性：常开 / 常关 / 限时窗口（一次性、可带名额）/ 周期时段（每周几的几点到几点）/ 紧急强制开关。
- 名额：全站用户上限（达到后关闭所选通道，参考 NexusPHP “最大用户数”、Gazelle `USER_LIMIT`）、窗口名额；钩子内带 TTL 预留、`user.registered` 确认。
- 邮箱域名：白名单（如只允许教育邮箱）、黑名单、一次性邮箱库（内置 + 导入）。
- 同 IP / 同网段 / 同设备注册数限制：只保存不可逆摘要、短保留期、确认后不与账号关联。
- 验证码：内置工作量证明（PoW，默认）、蜜罐 + 最短填写时间、第三方（hCaptcha、Cloudflare Turnstile、reCAPTCHA）、内置图片验证码（P2）、交给第三方插件（external）；通过“前置验证 → 通行票据 → 钩子查票”实现，钩子中不出站 HTTP。
- 答题注册：题库（分类、语言、单选 / 多选 / 判断）、抽题、判分、通过票据、防刷题。
- 审核制注册（申请制）：申请表（自定义字段、证明链接、推荐人）、状态查询、审核队列、通过后异步调用 `ctx.users.create`、失败处理、用户名占用保护、冷却、数据保留与清除。
- 策略组合：通道 × 关卡的固定求值顺序、第一个失败即拒绝、预演（dry-run）。
- `ctx.registration.status()` 与公开状态接口；`check_email_domain` 服务（供 invite 发邀时预检）。
- 统计（各关卡通过 / 拒绝漏斗）、后台页面、审计、MCP 工具（P2）。

**不包含**

- 账号创建、用户名 / 邮箱唯一性、密码、邮箱验证、待审核状态的实现——identity。
- 邀请码的生成、校验、预留、邀请树——invite（本插件只判断“该通道是否开放、是否必须带邀请码”）。
- 注册后的新手考核——newbie-exam（本插件的“答题”是注册**前**的知识测试）。
- 多账号关联判定、IP 封禁——anticheat。
- 向未注册者发邮件（申请结果通知）——需要 notify 新增“发送到外部地址”能力（P2，见 HLD §7）；本期申请人用状态令牌自查。
- 首位管理员的初始化——identity CLI（`pt-server` 管理命令）。

### 1.3 术语与缩写

| 术语 | 说明 |
|---|---|
| 通道（channel） | 注册来源：`open`、`invite`、`application`、`admin`、`import`，由 identity 推导为 `attributes.registration_mode` |
| 可用性（availability） | 通道当前是否开放：`always`、`never`、`windows`、`schedule`，可被紧急开关覆盖 |
| 窗口（window） | 一次性的开放时段（起止时间、可选名额、适用通道） |
| 关卡（gate） | 可按通道启用的检查：`username_hold`、`email_domain`、`captcha`、`quiz`、`ip_limit`、`device_limit`、`window_slots`、`user_cap` |
| 名额池（pool） | 需要计数的关卡的容量单位：`cap`（全站上限）、`window:<id>`、`ip:<摘要>`、`pfx:<摘要>`、`dev:<摘要>` |
| 占位（claim） | 钩子中对名额池写入的带 TTL 记录，持有者为规范化用户名，`user.registered` 时确认 |
| 通行票据（ticket） | 验证码或答题在本插件 HTTP 接口中通过后签发的 128 位随机令牌，TTL 内绑定一个用户名 |
| 申请（application） | 审核制注册的申请记录；通过后由本插件调用 `ctx.users.create` |
| 状态令牌 | 申请提交时返回一次的随机令牌，申请人凭它查询进度 |
| PoW | Proof of Work：浏览器计算 `SHA-256(salt ‖ nonce)` 前导零位数 ≥ 难度的 nonce |

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | WASM（站点规则；热路径仅注册钩子与公开状态接口） |
| 提供服务 | `ctx.registration`（single）：`status()`；★`check_email_domain(domain, channel)` |
| 依赖服务 | `ctx.users`（必需：`create`、`find_by_username`；作用域 ★`write:create`，可选 `write:status`）；`ctx.rbac`（必需：查看申请人完整邮箱需 `identity.users.read_sensitive`）；内核 `ctx.plugins`（检测 invite 插件是否存在） |
| 不依赖 | `ctx.invites`（避免依赖环：invite 可选依赖本服务） |
| 只读视图 | `identity.v_user_public`（全站用户数对账） |
| 钩子 | 处理 `user.before_register`（priority 5，先于 invite） |
| 敏感能力 | `sensitive_optional = ["user.ip"]`：仅用于同 IP 限制，钩子内立即摘要化，不落明文（需内核实现按处理者裁剪钩子输入） |
| 自行收集的个人数据 | 申请人邮箱（加密存储，保留期后删除）、申请表内容 |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 访客 | 查看注册是否开放、剩余名额、下次开放时间；完成验证码 / 答题后注册；提交注册申请、凭令牌查询进度 |
| 版主（`registration-policy.applications.moderate`） | 审核申请队列（通过 / 拒绝 / 写备注）、查看漏斗统计 |
| 管理员（`registration-policy.manage`） | 配置通道与关卡、开放窗口、周期时段、名额、域名名单、IP 限制、验证码提供方、题库；紧急关闭 / 开放；预演策略 |
| identity | 在注册提交时运行 `user.before_register`；发布 `user.registered` |
| invite | 可选调用 `check_email_domain` 预检绑定邮箱；读取 `status()` 显示“当前只能邀请注册” |
| 第三方验证码插件 | 站点将 `captcha.provider` 设为 `external` 后，自行处理 `user.before_register` |

### 2.3 现有开源 PT 程序的做法调研

| 项目 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| NexusPHP | 设置页：“开启注册系统”“允许自由注册”；“用户验证方式”（邮件 / 管理员 / 自动）；“最大用户数”（达到后自由注册与邀请注册都关闭）；“相同 IP 最大注册数”；“限制邮箱域”（`allowedemails` 白名单）+ `bannedemails` 黑名单；“开启图片验证码”（注册 / 登录 / 找回）；注册超时未验证删除 | 配置项完整，贴近国内站点习惯；用户上限与 IP 限制简单有效 | 全部写在注册控制器里，改规则改代码；IP 明文长期保存；验证码为服务端绘图，可访问性差；上限检查与插入之间无锁，开放高峰可超发；“管理员验证”只是激活开关，没有申请材料与审核记录 |
| UNIT3D | `invite-only` 总开关；`application_signups` 申请制：申请人填邮箱、类型、推荐人、≥2 张证明截图、≥2 个链接；员工审核通过后系统生成邀请并发到申请邮箱；隐藏验证码（蜜罐 + 时间）；一次性邮箱黑名单可从远程 JSON 源更新 | 申请制让“没有邀请渠道的老手”有入口；证明材料结构化；隐藏验证码对正常用户无感 | 申请通过要走“发邀请 → 再注册”两步；申请数据（邮箱、截图）无保留期；远程黑名单在请求路径上拉取有可用性风险；没有开放窗口与名额 |
| Gazelle / OPS | `OPEN_REGISTRATION` 常量；`USER_LIMIT`（启用用户超过时关闭邀请）；站点零用户时允许首位注册；`EmailBlacklist` 管理器；`RECOVERY` 模式（旧站用户凭证明恢复账号）；OPS 用 IRC 面试（考音频格式与规则），通过后由面试官签发邀请 | 面试 = 知识门槛，招到懂规则的用户；用户上限防止过度扩张 | 开关是常量，需改配置重启；面试依赖人工与 IRC；没有自动化的答题注册 |
| TorrentPier | `registration.disabled`、`unique_ip`（同 IP 只能注册一个）、`restricted` + `restricted_hours`（只在指定小时开放注册）；验证码服务可选（文本、reCAPTCHA v2/v3、hCaptcha、Turnstile 等） | 按小时开放、验证码可切换提供方，思路接近“可插拔” | 同 IP 限制对校园网 / CGNAT 误伤大且无豁免；第三方验证码把用户 IP 交给第三方 |
| Luminance / Arcadia | Luminance 沿用 Gazelle；Arcadia 早期，开放 / 邀请开关为主 | — | — |

**我们采纳**

1. NexusPHP / Gazelle 的**全站用户上限**、NexusPHP / TorrentPier 的**同 IP 注册限制**、NexusPHP 与 Gazelle 的**邮箱域名白 / 黑名单**、UNIT3D 的**一次性邮箱库**。
2. TorrentPier 的**按时段开放**与**可切换验证码服务**，扩展为“窗口 + 周期时段 + 紧急开关”和“提供方接口”。
3. UNIT3D 的**申请制**（结构化证明材料、推荐人），以及 OPS 面试的“知识门槛”思想——做成可自动判分的**答题注册**。
4. UNIT3D 的**隐藏验证码**（蜜罐 + 时间）作为所有提供方的附加层。

**我们改进**

1. **策略与身份解耦**：全部经 `user.before_register` 钩子，规则在后台可改、即时生效，不改代码。
2. **并发正确的名额**：名额池在行锁下“确认数 + 有效占位 < 容量”才写入占位，`user.registered` 确认，失败的注册在 TTL 后释放——开放高峰不超发（NexusPHP 的检查 / 插入竞态）。
3. **钩子快且不出站**：验证码与答题在本插件 HTTP 接口中完成，钩子只查 Redis 票据（O(1)），符合平台“钩子不出站 HTTP”约束；默认 PoW 不依赖第三方、不泄露用户 IP。
4. **隐私合规的 IP 限制**：只存插件密钥 HMAC 摘要、默认 30 天删除、确认后断开与用户名的关联；支持校园网等 CIDR 豁免；IP 不可得时可配置跳过或拒绝。
5. **申请制一步到位**：通过后直接调用 `ctx.users.create`（幂等），不需要“发邀请 → 再注册”；不收集密码（建号后经邮箱验证 / 设置密码流程激活）；申请人邮箱加密存储并定期删除；未决申请占用用户名，避免审核通过时撞名。
6. **组合规则可解释**：固定的通道 × 关卡求值顺序、第一个失败即拒绝并给出明确错误码；后台预演显示每个关卡的判定结果。

### 2.4 约束与假设

1. WASM 插件每次调用新实例、无内存状态；每次调用一个事务；钩子写入独立提交（kernel/03 §5.2）；钩子中不能出站 HTTP。
2. `user.before_register` 失败策略为 deny（锁定）：本插件超时 / 错误会使注册以 `503 kernel.hook_failed` 失败，因此钩子必须快速、依赖少（PG + Redis）。
3. identity 推导 `registration_mode`：Import → `import`；Admin → `admin`；Service（本插件 `ctx.users.create`）→ `application`；HTTP 带 `invite_code` → `invite`；否则 `open`（identity LLD §1.2）。拥有 `write:create` 的只有本插件。
4. 钩子输入中的 `ip` 只在内核实现“按处理者裁剪”并且站点授予 `user.ip` 时出现（identity DD-IDN-12、Q-IDN-1）；`device_hmac`、`ip_hmac` 为本插件向 identity 申请的新字段（HLD §7）。
5. 钩子输入的 `username` 与 `user.registered.username` 为同一显示形式，持有者规范化后可关联占位。
6. `ctx.users.create` 的 `password` 可为空，建号后用户经找回密码 / 账户设置流程设置密码（identity WIT 注释）。
7. 规模：用户 50 万；平时注册 ≤ 5,000/日；开放窗口高峰 ≤ 200 次/秒注册提交、≤ 2,000 次/秒状态查询；申请 ≤ 500/日；题库 ≤ 10,000 题。

## 3. 功能需求

### 3.1 通道、可用性与名额

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-REGP-001 | 通道识别 | 钩子按 `attributes.registration_mode` 识别通道；`admin`、`import` 默认放行（可配置对其启用关卡） | P0 | 各通道被正确识别；admin / import 默认不受开放与名额限制 |
| FR-REGP-002 | 通道开关 | `open`、`invite`、`application` 各自可启用 / 停用 | P0 | 停用通道的注册（或申请提交）返回 `registration-policy.closed{reason: channel_disabled}` |
| FR-REGP-003 | 需要邀请码 | `open` 不可用而 `invite` 可用时，无邀请码的注册返回 `registration-policy.invite_required`；`invite` 通道启用但 invite 插件未安装时拒绝带码注册（`registration-policy.invite_unavailable`） | P0 | 错误码正确；前端据此提示“仅限邀请注册” |
| FR-REGP-004 | 紧急开关 | 管理员可强制关闭（或强制开放）所选通道，可带到期时间与原因；优先于其他可用性规则；写审计 | P0 | 生效 ≤ 5 s（状态缓存）；到期后自动恢复 |
| FR-REGP-005 | 常开 / 常关 | 通道可用性 `always` / `never` | P0 | 符合配置 |
| FR-REGP-006 | 限时窗口 | 管理员创建开放窗口（起止时间、适用通道、可选名额、标题）；窗口内通道开放，窗口外关闭；同一通道窗口不得重叠；可提前结束 | P1 | 窗口外注册返回 `closed{reason: window_closed, next_window_starts_at?}` |
| FR-REGP-007 | 周期时段 | 可用性 `schedule`：按站点时区配置每周几的开放时间段（可跨午夜） | P1 | 时段边界前后 1 秒判定正确；跨午夜时段正确 |
| FR-REGP-008 | 全站用户上限 | 配置 `max_users` 与适用通道；“当前用户数 + 有效占位 ≥ 上限”时拒绝 | P0 | 达到上限后返回 `closed{reason: cap_reached}`；高峰并发下不超发 |
| FR-REGP-009 | 窗口名额 | 窗口可设名额；名额用尽后返回 `closed{reason: slots_exhausted}` | P1 | 200 次/秒并发注册下，成功注册数 ≤ 名额 |
| FR-REGP-010 | 名额占位与确认 | 钩子中对需要计数的名额池写带 TTL 的占位（持有者为规范化用户名，可重入）；订阅 `user.registered` 确认；失败的注册在 TTL（默认 600 s）后释放 | P0 | 同一用户名重试不重复占位；后续处理者拒绝后 TTL 内名额被占、TTL 后释放；重复事件只确认一次 |
| FR-REGP-011 | 用户数维护 | 订阅 `user.registered`（+1）与 `user.deleted`（-1，每用户只减一次）维护全站用户数；每日按 `identity.v_user_public` 对账 | P0 | 对账后计数与视图一致 |
| FR-REGP-012 | 策略组合 | 求值顺序固定：紧急开关 → 通道开关 → 可用性 → 关卡（`username_hold` → `email_domain` → `captcha` → `quiz` → `ip_limit` → `device_limit` → `window_slots` → `user_cap`）；每个通道单独选择启用哪些关卡；全部启用关卡通过才放行，第一个失败即拒绝；容量类关卡先在锁内全部检查、全部通过后才写占位 | P0 | 组合测试矩阵（TP §3.3）全部符合；被拒绝的请求不留下占位 |
| FR-REGP-013 | 预演 | 管理员输入（通道、用户名、邮箱域名、时间、是否带票据）预演，返回每个关卡的判定与最终结果，不写任何数据 | P1 | 预演结果与真实注册一致；无写入 |
| FR-REGP-014 | 公开状态 | `GET /status` 返回各通道是否开放、原因、当前 / 下一个窗口、剩余名额（可配置隐藏）、需要的关卡（验证码提供方与 site key、是否答题）、表单令牌（蜜罐用） | P0 | 结果缓存 ≤ 5 s；p99 ≤ 20 ms |
| FR-REGP-015 | `ctx.registration.status()` | 提供 catalog 已列字段 `{mode, open, remaining_slots, requires_invite, requires_exam}` 及各通道明细 | P0 | 契约测试通过 |
| FR-REGP-016 | 注册后待审核 | 可选：`open` 通道注册成功后进入待审核（modify `attributes.initial_status = pending`，★`pending_source = registration-policy`），版主在队列中通过后由本插件解除 | P2 | 依赖 identity ★`pending_source` 与 `lift_restriction`；未合入时只能由管理员在 identity 后台解除 |

### 3.2 邮箱域名

### 3.4 验证码

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-REGP-040 | 提供方可插拔 | `captcha.provider` ∈ `none`、`pow`、`hcaptcha`、`turnstile`、`recaptcha`、`image`（P2）、`external`；切换提供方无需重启 | P0 | 切换后新挑战使用新提供方；旧票据在 TTL 内仍有效 |
| FR-REGP-041 | PoW（默认） | 服务端签发挑战（随机盐、难度、5 分钟有效、单次使用）；浏览器求解后提交验证，服务端一次哈希校验 | P0 | 正确解获得票据；重复提交同一挑战失败；难度可配（默认 18 位） |
| FR-REGP-042 | 蜜罐与填写时间 | 隐藏字段必须为空；表单令牌（服务端签名时间戳）距提交 ≥ `min_fill_secs`（默认 3 s）且 ≤ 2 h；可与任一提供方叠加 | P1 | 违反时返回 `registration-policy.captcha_invalid{reason: honeypot/too_fast/form_token}` |
| FR-REGP-043 | 第三方提供方 | 前端渲染第三方组件，令牌提交到本插件验证接口，由本插件向提供方 siteverify（出站 HTTP，不发送用户 IP），成功后签发票据；密钥为 `x-pt-secret` | P1 | 提供方不可达返回 `registration-policy.captcha_provider_unavailable`（502），可配置降级为 PoW |
| FR-REGP-044 | 内置图片验证码 | 服务端生成文本图片（WASM 内绘制），答案只存哈希，3 次错误作废 | P2 | 同上；提供音频或 PoW 替代以满足可访问性 |
| FR-REGP-045 | 通行票据 | 票据 128 位随机、TTL（默认 30 min）、首次在钩子中使用时绑定用户名，此后只对该用户名有效；用户名注册成功后票据自然失效（用户名已被占用）；也可在验证时直接绑定用户名 | P0 | 换用户名使用同一票据被拒（`registration-policy.ticket_invalid`）；同一用户名重试可用 |
| FR-REGP-046 | 外部插件 | `provider = external` 时本插件不检查验证码，由第三方插件自行注册 `user.before_register` 处理者与 `auth.register.form_extra` 组件 | P1 | 文档化接入方式；本插件不报错 |
| FR-REGP-047 | 关卡位置 | 验证码可用于：注册（按通道）、开始答题、提交申请、查询申请状态 | P1 | 按配置要求票据 |

### 3.6 审核制注册（申请制）

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-REGP-060 | 提交申请 | 申请通道启用时，访客提交：用户名、邮箱、语言、自定义字段（后台配置：文本 / 长文本 / 链接 / 单选 / 勾选，必填、长度）、证明链接（≤ 5，可配最少数）、推荐人用户名（可选）；可要求验证码与邮箱域名关卡；返回申请 ID 与状态令牌（只此一次）；发布 `registration.application_submitted` | P1 | 201；邮箱加密存储；令牌只存哈希 |

| FR-REGP-064 | 审核决定 | 通过 / 拒绝（原因码 + 备注），乐观锁防并发审核；发布 `registration.application_reviewed`；写审计 | P1 | 两个版主同时审核只有一个成功 |
| FR-REGP-065 | 通过后建号 | 通过后异步调用 `ctx.users.create{username, email, password: none, locale, origin_ref: "registration-policy:application:<id>", skip_email_verification: false, idempotency_key: "regp:app:<id>"}`；成功置 `created` 并记录 user_id；用户名 / 邮箱冲突或钩子拒绝置 `create_failed`（记录错误码）；可重试的错误自动重试；发布 ★`registration.application_completed` | P1 | 重复执行只建一个账号；失败原因可见；版主可对 `create_failed` 重试（可修改用户名） |
| FR-REGP-066 | 用户名占用 | 未决申请占用其用户名：其他通道以该用户名注册返回 `registration-policy.username_held` | P1 | 申请结束（拒绝 / 过期 / 撤回 / 建号）后释放 |
| FR-REGP-067 | 冷却 | 被拒绝的邮箱（按 HMAC）在 `reapply_cooldown_days` 内不能再次申请 | P1 | 返回 `application_cooldown{until}` |
| FR-REGP-068 | 过期 | 超过 `expire_days` 未审核的申请自动过期 | P1 | cron 重复运行不重复处理 |
| FR-REGP-069 | 截图证明 | 申请可上传 ≤ 3 张截图（对象存储预签名上传、重新编码去元数据） | P2 | 审核页可查看；随申请数据一同清除 |
| FR-REGP-070 | 数据保留与清除 | 决定后 `retention_days`（默认 30）删除邮箱密文、证明与自定义字段；保留匿名统计行；邮箱 HMAC 仅在冷却期内保留 | P0（启用申请制时） | 保留期后库中无可识别申请人的数据（用户名除外，若已建号则由 identity 管理） |
| FR-REGP-071 | 申请事件 | 发布 `registration.application_submitted`、`registration.application_reviewed`、★`registration.application_completed`；载荷不含邮箱 | P1 | 载荷通过 schema 且敏感扫描 0 命中 |
| FR-REGP-072 | 账号激活 | 建号时不设密码；identity 发出邮箱验证，用户验证后经“设置密码”流程激活（申请状态页给出指引）；建议 identity 为无密码建号提供 `account_setup` 挑战（HLD §7） | P1 | 端到端：申请 → 通过 → 收到验证邮件 → 设置密码 → 登录 |

## 6. 外部接口需求概述

- **用户界面**：注册页插槽 ★`auth.register.form_extra`（状态横幅、验证码、答题、蜜罐、隐私告知）；`/p/registration-policy/apply`（申请）、`/p/registration-policy/application-status`；首页 `home.announcements`（开放注册横幅）；后台 `/admin/p/registration-policy/*`（通道与关卡、窗口、名单、题库、申请队列、统计、预演）；`admin.dashboard.widgets`（待审申请、今日注册 / 拒绝）。
