## 1. 设计目标与原则

1. **钩子只查不算**：慢操作（第三方验证码 siteverify、答题判分、申请审核）全部在本插件自己的 HTTP 接口或异步任务中完成，结果以“通行票据”或“申请状态”的形式落到 Redis / PG；`user.before_register` 中只做 O(1) 查询与带 TTL 的占位（平台 README 要点 4）。
2. **占位而非扣减**：名额、IP 计数在钩子中写“以规范化用户名为持有者、可重入、带 TTL”的占位，`user.registered` 确认（与 invite、identity HLD §5.1 一致）。被拒绝的请求不写占位。
3. **固定的组合语义**：通道 × 关卡，固定顺序、全部通过才放行、第一个失败即拒绝（FR-REGP-012）。站点只选择“每个通道启用哪些关卡”，不能写任意布尔表达式——可解释、可预演、可测试。
4. **隐私优先**：IP 只以插件密钥 HMAC 摘要存在且短期保留；申请人邮箱加密存储、打码显示、定期删除；默认验证码（PoW）不依赖第三方。
5. **fail-closed 但依赖少**：注册钩子失败即拒绝（锁定），因此钩子只依赖 PG 与 Redis，不调用其他插件服务（`ctx.plugins` 检测结果在初始化时写入 kv）。
6. **无依赖环**：本插件不 requires `ctx.invites`；invite 可选依赖 `ctx.registration`。

## 2. 总体结构

### 2.2 内部模块

| 模块 | 职责 |
|---|---|
| `availability` | 紧急开关、通道开关、`always/never/windows/schedule` 判定，下一次开放时间计算 |

## 4. 数据设计概要

| 实体 | 存储 | 说明 |
|---|---|---|
| 紧急开关 `overrides` | PG（单行） | 状态 open/closed、通道、到期、原因 |
| 窗口 `windows` | PG | 起止、通道、名额、取消 |
| 名额池 `pools` | PG | `cap`（确认数 = 用户数）、`window:<id>`（确认数） |
| 锁行 `claim_locks` | PG | 每个池一行，`INSERT … ON CONFLICT DO UPDATE` 取行锁 |
| 占位 `claims` | PG | 池、持有者、状态、到期、确认时间；IP 池只有摘要 |
| 已删除用户 `deleted_users` | PG | 用户数只减一次 |
| 域名名单 `domain_rules` | PG | 规范化域名、列表（allow/deny/disposable）、来源 |
| 题库 `questions` | PG | 题目、选项、答案、统计 |
| 申请 `applications` | PG | 用户名、邮箱密文 + HMAC + 域名、字段、证明、状态、令牌哈希、审核、建号结果 |
| 冷却 `application_cooldowns` | PG | 邮箱 HMAC → 到期 |
| 统计 `daily_stats` | PG | 日 × 通道 × 指标 |
| 票据 / 挑战 / 答题会话 / 状态缓存 / 计数 | Redis 私有前缀 | 全部带 TTL（LLD §3.2） |

## 5. 关键流程

### 5.1 注册钩子

```
input → ch = attributes.registration_mode
ch ∈ {admin, import} 且 channels[ch].gates 为空 → allow
holder = lower(nfc(username))
① 可用性：override → channels[ch].enabled → availability(ch, now)
     不可用：ch = open 且 invite 通道可用 → deny invite_required；否则 deny closed{reason, next_open_at}
     ch = invite 且 kv env:invite_present = false → deny invite_unavailable
② 只读关卡（按序，启用才执行）：
     username_hold → 有同名未决申请（ch ≠ application）→ deny username_held
     email_domain  → 判定 deny → deny email_domain_not_allowed{reason}
     captcha       → 蜜罐 / 表单令牌 → 票据 tk:<id>（kind=captcha，绑定或匹配 holder）
     quiz          → 票据（kind=quiz）
③ 容量关卡（一个 PG 事务内）：
     计算涉及的池：ip:<h>、pfx:<h>、dev:<h>、window:<id>、cap
     按池名排序 → 逐个 INSERT claim_locks … ON CONFLICT DO UPDATE（取行锁）
     逐个计数：确认数 + 他人有效占位 < 容量 ？ 任一不满足 → deny（不写任何占位）
     全部满足 → UPSERT claims(pool, holder) reserved_until = now + ttl
④ 统计 INCR；channels[ch].review → modify {attributes: {initial_status: pending, pending_reason★, pending_source★}}；否则 allow
```

### 5.2 验证码票据

```
GET /status → 告知 provider、site_key、form_token（签名时间戳）
PoW：POST /captcha-challenges → {challenge_id, salt, difficulty, expires_at}；Redis pc:<id>（300 s）
     浏览器求 nonce → POST /captcha-verifications {challenge_id, nonce, username?}
     服务端：HGETALL pc:<id> → DEL（返回 1 才有效，单次使用）→ 校验前导零位 → 签发 tk:<id>{k: captcha, h?: holder}
第三方：前端组件拿到 token → POST /captcha-verifications {provider, response, username?}
     服务端 http-client → siteverify（secret、response；不发 remoteip）→ success 且 hostname 匹配 → 签发票据
     不可达：fallback_to_pow → 返回 409 + PoW 挑战；否则 502 captcha_provider_unavailable
注册时：form["registration-policy"] = {captcha_ticket, quiz_ticket?, hp: "", form_token}
```

### 5.3 答题

```
POST /quiz-sessions {captcha_ticket?} → 抽题（分类 × 数量，语言回退）→ 选项洗牌（会话内标签 a/b/c…）
     Redis qs:<id>{questions:[{qid, perm}], exp} TTL = time_limit + 60 → 返回题干与选项（无答案）
POST /quiz-sessions/{id}/submissions {answers, username?} → DEL qs:<id>（单次）→ 判分 → 题目统计 +1
     score ≥ pass → 签发 tk:<id>{k: quiz, s: score, h?} → {passed: true, score, ticket}
     否则 → {passed: false, score}
```

### 5.4 审核制注册

```
POST /applications {username, email, locale, fields{}, proof_urls[], referrer?, captcha_ticket?}
  → 通道 application 启用且可用 → submit_gates（email_domain、captcha…）
  → 预检：用户名格式 / ctx.users.find_by_username / 同名或同邮箱未决申请 / 冷却
  → INSERT applications(email_enc, email_hmac, email_domain, status=submitted, token_hash)
  → publish registration.application_submitted → 201 {application_id, status_token}
版主 POST /admin/applications/{id}/decisions {decision, reason_code?, note?, version}
  approve → status=approved；publish application_reviewed{approved: true}；
            jobs.schedule_once("create_account", now, {id}, dedupe = "app:<id>:<attempt>")
  reject  → status=rejected；冷却 INSERT；publish application_reviewed{approved: false}
延迟任务 create_account：
  ctx.users.create{username, email(解密), password: none, locale, invite_code: none, form: "{}",
                   origin_ref: "registration-policy:application:<id>", skip_email_verification: false,
                   idempotency_key: "regp:app:<id>:<username_version>"}
    → identity 运行 user.before_register（ch = application，本插件只执行 channels.application.gates）
    → ok(user_id) → status=created；publish application_completed{created}
    → identity.username_taken / email_taken / 钩子拒绝 → status=create_failed{failure_code}；publish completed{failed}
    → retryable → 返回 err，由内核延迟任务重试（3 次）；仍失败则 application_maintenance 重新调度
on_user_registered（registration_mode = application）：按 holder 确认占位（同 5.1）
```

### 5.5 确认与对账

```
on_user_registered：
  UPDATE claims SET state=confirmed, confirmed_at=now, holder = NULL（仅 ip/pfx/dev 池）, user_id（非 IP 池）
     WHERE holder = $holder AND state IN ('reserved','released') RETURNING pool
  UPDATE pools SET confirmed = confirmed + 1 WHERE pool = 'cap'（不论是否有 cap 占位）
  对返回的 window:<id> 池：confirmed + 1
on_user_deleted：INSERT deleted_users ON CONFLICT DO NOTHING → 插入成功才 cap.confirmed - 1
cap_reconcile：cap.confirmed = SELECT count(*) FROM identity.v_user_public
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论 | 理由 |
|---|---|---|---|---|
| DD-REGP-1 | 验证码 / 答题在哪里校验 | A 钩子内校验（第三方需出站 HTTP）；B 本插件 HTTP 接口预校验 + 票据，钩子查票 | B | 钩子禁止出站 HTTP；判分与 siteverify 耗时不应占用 500 ms 的锁定钩子预算；B 还能在填写账户信息前给用户即时反馈 |
| DD-REGP-2 | 票据是否需要“确认后消耗” | A 钩子中消耗（失败的注册吞掉票据）；B 事件中消耗；C 首次使用绑定用户名，不消耗 | C | `user.registered` 不携带表单内容，B 难以关联；用户名只能注册一次，绑定后票据对他人无用、对本人重试可用，TTL 到期自然失效 |
| DD-REGP-3 | 名额计数 | A Redis 计数（无 EVAL，无法与检查原子）；B PG 池锁行 + 占位表 | B | 检查与写入在同一事务行锁下；确认在 PG 内恰好一次；200 次/秒下锁持有 < 2 ms，单行吞吐足够（实测不足时把 `cap` 拆为 K 个分片池，见 LLD §7） |
| DD-REGP-4 | 关卡求值顺序与写入 | A 按配置任意顺序；B 只读关卡在前、容量关卡在后，锁内全部检查通过才写 | B | 被拒绝的请求不留下占位；错误码优先级确定；与 invite 的预留叠加时，本插件先执行（priority 5），减少无效邀请预留 |
| DD-REGP-5 | IP 来源 | A 必须授予 `user.ip`；B identity 提供 `ip_hmac`；C 两者都支持 | C | 授予原始 IP 时本插件用自己的密钥摘要，可做 CIDR 豁免；不授予时可用 identity 的盲化摘要（★申请），站点无需把原始 IP 交给本插件；二者都没有时按 `on_unavailable` 处理 |
| DD-REGP-6 | 与 invite 的依赖方向 | A 本插件 requires `ctx.invites` 校验邀请码；B invite 可选 requires `ctx.registration` | B | 邀请码校验本就由 invite 的钩子完成，本插件只需知道 invite 是否存在（`ctx.plugins.list()`，D4 下启动后不变，init 时写 kv） |
| DD-REGP-7 | 申请通过后如何建号 | A 发邀请到申请邮箱（UNIT3D）；B 直接 `ctx.users.create` | B | A 需要向非用户发邮件（notify 无此能力），且要求用户再走一次注册；B 一步完成，identity 负责邮箱验证邮件 |
| DD-REGP-8 | 建号同步还是异步 | A 审核请求内同步调用；B 延迟任务 | B | 建号会再次进入 `user.before_register`（含本插件），同步时审核请求的事务与钩子交叠；B 可重试、不阻塞审核界面 |
| DD-REGP-9 | 申请是否收集密码 | A 收集并暂存；B 不收集，建号后设置 | B | 不在第三方插件中长时间保存口令；identity 已支持无密码建号 |
| DD-REGP-10 | 默认验证码 | A 图片验证码；B 第三方；C PoW + 蜜罐 | C | 无第三方、不泄露 IP、无需视觉交互（可访问性），对脚本批量注册有成本；有更高要求的站点可切换第三方 |
| DD-REGP-11 | 申请人邮箱保护 | A 明文；B 插件内 AES-256-GCM + HMAC | B | WASM 可用纯 Rust crate（`aes-gcm`，MIT/Apache）；密钥来自 `x-pt-secret` 静态配置；HMAC 用于去重与冷却 |
| DD-REGP-12 | 全站用户数 | A 每次 `count(*)` 视图；B 事件维护计数 + 每日对账 | B | A 在 50 万行上每次注册数十毫秒且锁内执行；B O(1)，偏差每日纠正 |
| DD-REGP-13 | 漏斗统计 | A 每次钩子写 PG；B Redis INCR + 每日折叠 | B | 避免高峰期热点行；计数非关键数据，Redis 丢失只影响统计 |

## 7. 对平台契约的新增

### 7.1 事件

| 类型 | 内容 |
|---|---|
| 字段新增 | `registration.application_reviewed`：`reason_code?`、`username`（与 submitted 一致） |
| 新事件 | `registration.application_completed`（registration-policy，key `global`）：`application_id, outcome(created/failed), user_id?, failure_code?` |
| 新事件（P2） | `registration.availability_changed`（registration-policy，key `global`）：`channel, open: bool, reason, window_id?, next_open_at?` |

### 7.2 钩子

| 项 | 内容 |
|---|---|
| 依赖 identity 申请 | `user.before_register` 输入按处理者裁剪 `ip`（Q-IDN-1）；可修改字段 `attributes.pending_reason`、`attributes.pending_source`（FR-REGP-016） |
| 请 identity 新增输入字段 | `ip_hmac`、`ip_prefix_hmac`（identity `ip-mac` 子密钥对 IP 与 /24、/64 网段的 HMAC，非敏感伪名）、`device_hmac`（设备 cookie 摘要，首次访问无 cookie 时为空）。用于在不授予原始 IP 的情况下实现同 IP / 设备限制 |

### 7.3 服务

| 项 | 内容 |
|---|---|
| `ctx.registration` 新方法 | `check_email_domain(domain, channel) -> DomainVerdict` |
| `ctx.registration.status` 返回新增字段 | `channels[]`、`captcha?{provider, site_key?}`、`next_open_at?`、`user_cap?` |
| 依赖 identity | `ctx.users.create` 作用域 `write:create`（identity HLD §7.3 已申请）；建议无密码建号时签发 `account_setup` 挑战（验证邮箱 + 设置密码一步完成），未实现时退化为“验证邮箱 + 找回密码” |
| 内核确认 | WASM 插件可导入 `pt:plugins` 的 `list()`（services.md §1 未注明 WASM 可用性） |
| 请 notify（P2） | 发送到非用户邮箱地址（申请结果通知；与 invite Q-INV-2 相同） |

### 7.4 术语、插槽、MCP、错误码、其他

| 类型 | 新增 |
|---|---|
| 术语 | `registration-policy.open_signup`、`registration-policy.window`、`registration-policy.slots`、`registration-policy.quiz`、`registration-policy.application` |
| 插槽 | 使用 identity 申请的 `auth.register.form_extra`；约定扩展字段写入 `form["<plugin_id>"]` 命名空间 |
| MCP 工具 | `admin_get_registration_status`、`admin_list_registration_applications`、`admin_review_registration_application` |
| 错误码 | 见 LLD §9；注意 catalog 中 `registration-policy.email_domain_not_allowed` 标为 422，但钩子拒绝的 HTTP 状态按后缀规则（catalog/hooks.md §3）会映射为 403——请评审统一（建议钩子映射规则增加“处理者可在 details 中指定 422”或在 error-codes 中允许钩子码声明状态） |
| 规范 | 建议在 security.md 增加“插件自行收集个人数据”的条款（加密、保留期、打码、purge），本插件按本设计执行 |
| 许可证 | 内置一次性邮箱库须选用 CC0 / MIT 等兼容来源（例如 `disposable-email-domains` 项目的 CC0 列表），随插件分发并在 NOTICE 中注明 |

### 7.5 需要确认的问题

| # | 问题 |
|---|---|
| Q-REGP-1 | 内核未实现钩子输入裁剪、identity 也未提供 `ip_hmac` 时，同 IP 限制不可用；是否接受在此情况下默认 `skip` |
| Q-REGP-2 | `ctx.users.create` 触发的 `user.before_register` 会再次调用本插件的钩子：请内核确认这种“服务调用 → 他方钩子 → 回到调用方插件新实例”的路径不被视为回调（plugin-api §1.2 第 4 条） |
| Q-REGP-3 | 第三方验证码会让访客浏览器直接连接第三方；是否需要在 CSP `script-src` / `frame-src` 中按提供方放行（内核统一下发 CSP，需支持插件声明） |
