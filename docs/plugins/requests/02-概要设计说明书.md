## 1. 设计目标与原则

1. **托管而非冻结**：贡献即转入系统（ledger 回收），发放 / 退款为系统发行。理由：ledger 冻结（hold）最长 30 天，而求种可存续 90 天以上。
2. **每笔贡献可追溯**：退款按贡献逐笔发行，幂等键 `req:refund:<contribution_id>`。
3. **状态机 + 延迟任务**：资金动作在 `tx = manual` 的延迟任务中分步提交（同 shop 模式），HTTP 只做状态变更与调度。

## 2. 总体结构

```
状态：open ─应求→ fill_pending ─确认 / 自动确认→ filled ─(撤销)→ open
        │                └─驳回→ open
        ├─过期 / 撤回→ closing ─(退款完成)→ closed
```

| 模块 | 职责 |
|---|---|
| `requests` | 发布、编辑、列表、投票、认领 |
| `bounty` | 贡献、托管、发放、退款、对账（延迟任务） |
| `fills` | 应求、校验、确认、驳回、撤销 |
| `lifecycle` | 过期、撤回、种子删除、用户删除 |
| `search` | requests 索引贡献 |

## 4. 数据设计概要

`requests`（状态、类型、要求 JSON、悬赏总额、投票数、认领）、`contributions`（每笔贡献：用户、金额、状态 escrowed / refunding / refunded / paid）、`fills`（应求记录：种子、应求者、状态、发放 entry）、`votes`、`ops`（资金操作队列：kind payout / refund / revoke、状态）。

## 5. 关键流程

```
贡献：INSERT contributions(state = pending) + 调度 bounty_step → ledger.transfer(from user, to None, key "req:c:<id>") → escrowed，requests.bounty_total += amount
确认：fill.state = confirmed；INSERT ops(kind = payout, amount = Σ escrowed × (1 − fee))；调度 → ledger.transfer(from None, to filler, key "req:p:<fill_id>") → paid；contributions → paid；request filled
过期 / 撤回：request → closing；对每笔 escrowed 贡献 INSERT ops(refund) → ledger.transfer(None → contributor, key "req:r:<contribution_id>") → refunded；全部完成 → closed
撤销填充：ledger.reverse(payout_entry, reason) → 成功：contributions 回到 escrowed，request → open；余额不足：记录 debt，版主处理
```

## 6. 设计决策

| 编号 | 问题 | 结论与理由 |
|---|---|---|
| DD-REQ-1 | 悬赏资金 | 托管（回收 + 发行），见 §1；ledger 的 supply 统计中托管期间表现为“回收”，对账以本插件的 escrowed 余额为准 |
| DD-REQ-2 | 应求并发 | 同一时刻只允许一个待确认应求，避免多个应求者争议 |
| DD-REQ-3 | 要求校验 | 结构化要求用类型插件的字段名与谓词（`pt-predicate`），对应求种子的 `fields` 求值；不满足时拒绝应求（可由版主强制接受） |
| DD-REQ-4 | 保种任务 | 不在本期：需要 accounting 提供“某种子某时间段内的做种者”查询；术语已登记，保留到后续版本 |
