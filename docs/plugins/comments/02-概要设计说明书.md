## 1. 设计目标与原则

1. **一套渲染器**：所有用户内容经 `pt-markup` 渲染并净化，写入时渲染、读取时直接输出缓存的 HTML；渲染器版本升级时后台批量重渲染。
2. **不反向依赖目标插件**：目标存在性与可见性用只读视图判断；“目标被锁定”等业务规则由目标拥有者作为 `comment.before_create` 的处理者实现，避免 comments ↔ requests 的服务依赖环。
3. **反垃圾在钩子之前**：便宜的频率检查先做。

## 2. 总体结构

```
用户 ─POST─► comments ─► 频率 / 重复检查 ─► hooks.run(comment.before_create)（moderation、anticheat、requests、ai-moderation 本地规则）
                     ─► pt-markup 渲染 ─► INSERT ─► publish comment.created ─► notify（@提醒）、ai-moderation、search(forum?不)、medals
```

| 模块 | 职责 |
|---|---|
| `targets` | 目标解析、可见性（视图查询） |
| `antispam` | 频率、重复、新用户、链接数 |
| `posting` | 发表、回复、引用、编辑、删除、编辑历史 |
| `mentions` | @解析与通知 |
| `thanks` | 感谢 |
| `query` | 列表、计数、用户历史、管理检索 |
| `markup`（crate `pt-markup`） | 渲染与净化 |

## 3. 对外接口清单

| 类别 | 内容 |
|---|---|
| 服务 | `count(target)`、`list(target, cursor)`、`create(author_id, target, body)`、`delete(id, reason)`（已登记）；⊕ `count_many(targets)`、`create` 补 `markup` 与 `idempotency_key` |
| 依赖 | `ctx.users`（用户名解析 @、状态）；optional `ctx.notify` |
| 视图 | `torrent.v_torrent_public`、`torrent.v_group_public`；⊕ `requests.v_request_public`、`subtitles.v_subtitle_public`（请对应插件提供） |
| 事件 | 发布 `comment.created`、`comment.updated`、`comment.deleted`；订阅 `user.deleted`、`torrent.deleted`、`group.deleted`（目标删除时隐藏评论） |
| 钩子 | 拥有 `comment.before_create`（输入补 `markup`、`reply_to?`、`mentions[]` ⊕） |
| HTTP（`/api/p/comments/v1`） | `GET /targets/{target}/comments`、`POST /targets/{target}/comments`、`PATCH /comments/{id}`、`DELETE /comments/{id}`、`GET /comments/{id}/history`、`POST/DELETE /comments/{id}/thanks`、`GET /users/{id}/comments`、`POST /preview`（渲染预览）、`GET /admin/comments?q=&user_id=&target=`、`POST /admin/comments/batch-delete`、`GET /emoji` |
| 插槽 | `torrent.detail.tabs`、`group.detail.tabs`、`request.detail.sidebar`、`user.profile.tabs` |
| cron | `rerender`（渲染器版本变化时，分批）、`cleanup`（编辑历史保留 365 天） |
| 权限点 | `comments.create`、`comments.update_own`、`comments.moderate`（已登记） |

## 4. 数据设计概要

`comments`（目标、楼层号、作者、回复对象、markup、source、rendered、render_version、状态、计数）、`edits`（历史）、`thanks`、`emoji`（站点自定义表情）、Redis 频率计数与重复内容指纹。

## 5. 关键流程

见 §2；楼层号：`UPDATE target_counters SET next_floor = next_floor + 1 … RETURNING`（同目标串行，行锁）。

## 6. 设计决策

| 编号 | 问题 | 结论与理由 |
|---|---|---|
| DD-CMT-1 | 写时渲染还是读时渲染 | 写时：读多写少；渲染器升级用后台重渲染 |
| DD-CMT-2 | 混合语法 | 不混合：每条内容声明 `markup`，避免解析歧义 |
| DD-CMT-3 | 图片外链 | 默认只允许站内 blob（用户先上传图片）与白名单主机；可选图片代理（防止跟踪与混合内容）——代理属于内核 / web 的能力，本期不做 |
| DD-CMT-4 | 楼中楼深度 | 一层：长讨论应在论坛 |

## 7. 对平台契约的新增

服务方法 `count_many`、`create` 参数补充；钩子 `comment.before_create` 输入补字段；视图 `requests.v_request_public`、`subtitles.v_subtitle_public`；共享 crate `pt-markup`（conventions/security.md 中应规定“所有插件渲染用户内容必须使用 pt-markup”）；术语 `comments.thanks`；图片上传：请内核或 web 提供通用的“用户图片上传”接口（blob 存储 + 尺寸限制），或由 comments 提供 `POST /v1/images`（本期由 comments 提供，见 03）。
