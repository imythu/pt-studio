## 1. 设计目标与原则

1. **等级只是标签，权限在 RBAC**：等级通过 `set_class_roles` 绑定动态角色 `levels:class_<id>`，权限点由管理员在角色上配置（NexusPHP `class >= X` 硬编码比较的改进）。
2. **条件数据驱动**：升级 / 保级条件为谓词列表（与 anticheat、medals、promotion 同一格式）；指标集合由本插件白名单定义。
3. **温和降级**：保级失败先警告、期满再降级；升级后保护期。
4. **评估分批、增量**：每日全量（含降级）、流量触发的增量（只升级）。
5. **identity 是事实来源**：`class_id` 存在 identity；本插件记录评估状态与历史，巡检比对。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
traffic.settled ──► 标记脏用户 ──┐
user.registered / roles_changed ─┤
cron daily_evaluate / incr_evaluate ─► levels (WASM) ── users.set_class ──► identity ── user.class_changed
                                 │      rbac.set_class_roles（等级定义变化时）
                                 │      invites.grant_quota（升级奖励）
       只读视图：v_user_public / v_user_totals / v_balance / v_snatch

                       PG schema levels；events level.*
```

| 实体 | 说明 |
|---|---|

| `user_levels` | 每用户：当前等级、来源（auto/manual/vip/honor）、锁定到期、保护期到期、警告状态、保号、最后活跃日 |

## 5. 关键流程

### 5.1 评估单个用户

```
eval(u, metrics, mode):                              // mode = full | promote_only
  if override 生效（manual 锁定 / vip / honor）: target = override.class_id → apply；return
  cur = u.class_id（普通等级）
  cands = 普通等级中 rank > cur.rank 且 promote 条件全部满足者
  if cands: target = promote_mode == highest ? max_rank(cands) : 下一级（若满足）
            apply(target, cause=auto)；清除警告；protect_until = now + protect_days；return
  if mode == promote_only: return
  if now < protect_until: return
  if keep 条件全部满足: 清除警告（若有，发布 warning_cleared）；return
  if 无警告: 设警告 deadline = now + warning_days；发布 level.warned；通知；return
  if now ≥ deadline: target = rank < cur 的普通等级中 keep 条件满足的最高者（无则最低等级）
                     apply(target, cause=auto)；发布 level.demoted
```

### 5.2 apply

```
apply(uid, target, cause):
  users.set_class(uid, target, reason = "levels.<cause>")      // identity 幂等，相同等级不发事件
  UPDATE user_levels；INSERT history
  首次到达且等级有奖励 → rewards（invites.grant_quota，幂等键 "lvl:reward:<uid>:<class>"）
  promoted / demoted 事件
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论与理由 |
|---|---|---|---|
| DD-LVL-1 | 权限如何随等级变化 | 插件内比较 class 数值 / RBAC 角色 | RBAC：`set_class_roles` 在等级定义变化时一次性设置，用户等级变化即权限变化，无需逐用户授予 |
| DD-LVL-2 | 指标数据来源 | 订阅流量事件自行累计 / 读 accounting 视图 | 视图：避免重复累计与漂移；评估批量 SQL |
| DD-LVL-3 | 增量评估是否降级 | 是 / 否 | 否：降级需要警告流程，每日一次足够；增量只做升级，减轻负载 |
| DD-LVL-4 | VIP 实现 | 独立等级 / 角色 | 角色到等级的映射：shop 售卖 `shop:vip` 角色（含到期），本插件订阅 `user.roles_changed` 把 VIP 等级作为覆盖层；VIP 的权限仍由该等级的角色决定 |
| DD-LVL-5 | 外部改等级 | 覆盖回去 / 视为手动锁定 | 视为手动锁定（无期限），在后台标出，管理员可解除 |
| DD-LVL-6 | 不活跃处理 | 删除账号（NexusPHP） / 限制 | 只做 restrict（可解除），不自动删除；默认关闭 |

## 7. 对平台契约的新增

| 类别 | 内容 |
|---|---|
| 服务方法 | `ctx.levels.grant_honor(...)`；作用域 `grant` |
| 事件 | 新增 `level.warned`、`level.warning_cleared`；`level.promoted` 补 `cause` |
| 钩子 | 处理 `invite.before_issue`；`search.before_query`（P2）需要 torrent 在搜索文档中提供 `min_class_id` 字段（“等级限定资源”），请 torrent 设计确认 |
| 视图 | 需要 `torrent.v_torrent_public` 提供 `uploader_id` 与 `status`（已有），以计算 `uploads_count`；`accounting.v_snatch` 用于 `seeding_size`（需与 `torrent.v_torrent_public.size` 关联）——按 30 万用户批量计算成本较高，建议 accounting 在 `v_user_totals` 中增加 `seeding_size`、`seeding_count`（当前做种体积与数量） |
| 术语 | `levels.warning`、`levels.metric.<metric>` |
| 动态角色 | `levels:class_<id>`（`write:roles`） |
