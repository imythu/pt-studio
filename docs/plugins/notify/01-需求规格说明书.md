## 1. 引言

### 1.1 目的

定义通知插件 `notify` 的需求：全站统一的通知发送服务，渠道包括站内通知中心、邮件、Telegram、Discord；用户可按通知类别设置偏好；负责 identity 的验证 / 找回邮件投递。

### 1.2 范围

包含：通知中心（铃铛图标、未读、列表、已读）；渠道适配器（邮件经 HTTP 发信服务、Telegram Bot、Discord Bot 私信）；渠道绑定（Telegram / Discord 账号绑定流程）；通知类别与模板（术语与 MessageFormat）；用户偏好（类别 × 渠道）；摘要合并与限流；退订链接；投递重试与失败记录；挑战投递（`user.challenge_issued`）；登录提醒（`user.logged_in` 的 `risk_flags`）；幂等发送。

不包含：站内信（messages）；营销群发（messages 的广播或管理员工具）。

### 1.3 参考资料

- docs/plugins/identity/（`challenge_delivery`、`user.challenge_issued`）、docs/plugins/terms/（模板渲染）
- UNIT3D：Notifications（数据库通知 + 用户偏好开关）、Telegram 通知（可选）
- NexusPHP：站内短讯作为通知；邮件仅用于注册与找回

## 2. 总体描述

WASM，ID `notify`，缩写 `NOTIFY`；提供 `ctx.notify`；依赖 `ctx.users`、`ctx.auth`（挑战投递）、`ctx.terms`；**不依赖 messages**（避免 reports → notify → messages → reports 的服务依赖环）。

### 2.1 现有开源 PT 程序的做法调研

| 程序 | 做法 | 优点 | 缺点 | 我们的取舍 |
|---|---|---|---|---|
| UNIT3D | Laravel Notifications：数据库通知 + 邮件；用户在设置中按类型开关 | 结构清晰 | 每类通知代码写死 | **采纳**数据库通知 + 偏好；**改进**：类别与模板由插件在清单中登记，渠道可扩展 |
| NexusPHP | 用站内短讯作为通知 | 无需额外系统 | 通知淹没私信；无法按类别关闭 | 通知中心与站内信分离 |

## 3. 功能需求

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-NOTIFY-001 | 发送接口 | `send(user_id, template_key, args, channels?, idempotency_key)`、`send_many(user_ids ≤ 1000, …)` | P0 | 同一幂等键只投递一次 |
| FR-NOTIFY-002 | 模板 | 模板键 `<plugin_id>.<name>`，由插件在清单 `[notify.templates]` 或经服务 `register_templates` 登记：类别、各渠道标题与正文模板（术语键）、默认渠道、是否可退订 | P0 | |
| FR-NOTIFY-003 | 类别 | 类别：security（安全，不可退订）、account、social（@、回复）、content（种子、求种）、economy、system；用户按类别 × 渠道设置偏好 | P0 | |
| FR-NOTIFY-004 | 通知中心 | 站内通知列表、未读计数、标记已读、全部已读、保留 90 天 | P0 | |
| FR-NOTIFY-005 | 邮件 | 通过 HTTP 发信服务（Mailgun / SendGrid / Postmark / Amazon SES v2 / 自建 HTTP 中继）发送；需 `user.email` 授权 | P0 | |
| FR-NOTIFY-006 | Telegram | 绑定（用户在站内获取一次性绑定码 → 向站点 Bot 发送 `/start <code>`）；发送消息；解绑 | P1 | |
| FR-NOTIFY-007 | Discord | 绑定（OAuth2 获取用户 ID）后由 Bot 私信 | P2 | |
| FR-NOTIFY-008 | 挑战投递 | 订阅 `user.challenge_issued`，调用 `ctx.auth.challenge_delivery` 获取收件人与链接，发送验证 / 找回邮件 | P0 | |
| FR-NOTIFY-009 | 登录提醒 | 订阅 `user.logged_in`：`new_device` 或 `risk_flags` 非空时发送 security 类通知 | P1 | |
| FR-NOTIFY-010 | 摘要 | 同一用户同一模板在合并窗口内（模板配置，默认 0 = 不合并）合并为一条 | P1 | |
| FR-NOTIFY-011 | 限流 | 每用户每渠道每小时上限（邮件 20、Telegram 60）；security 类不受限 | P0 | |
| FR-NOTIFY-012 | 退订 | 邮件带签名退订链接（一键退订该类别的邮件，`List-Unsubscribe` 头）；security 类无退订 | P1 | |
| FR-NOTIFY-013 | 重试 | 渠道临时失败按退避重试（≤ 5 次）；永久失败（地址无效、Bot 被屏蔽）标记并停用该渠道绑定 | P0 | |
| FR-NOTIFY-014 | 投递记录 | 记录每次投递（渠道、状态、错误码），保留 30 天；发布 `notify.delivered` / `notify.failed` | P1 | |
| FR-NOTIFY-015 | 非用户地址 | 对未注册的邮箱发送（registration-policy 申请制通知申请人）：`send_to_address(address, template, args, idem)`，需作用域 `send:address` 与 `user.email` 授权 | P2 | |
| FR-NOTIFY-016 | 匿名保护 | 模板参数中的用户引用渲染前检查匿名（如匿名发布者不出现在通知中） | P1 | |
| FR-NOTIFY-017 | 用户删除 | 删除通知、绑定、偏好 | P1 | |

## 4. 非功能需求

| 编号 | 描述 | 指标 |
|---|---|---|
| NFR-NOTIFY-001 | send 受理 | p99 < 30 ms（异步投递） |
| NFR-NOTIFY-002 | 投递延迟 | 站内 < 2 s；外部渠道 p95 < 30 s |
| NFR-NOTIFY-003 | 吞吐 | 1000 通知/秒（站内）、50 封邮件/秒（受发信服务限制） |
| NFR-NOTIFY-004 | 隐私 | 邮箱、Telegram chat_id 不进事件与日志；挑战令牌不落库不进日志 |

## 5. 可配置项与站点术语

静态：`email.provider`（mailgun / sendgrid / postmark / resend / ses / http_relay）、各提供方凭据（secret）、`email.from`、`telegram.bot_token`、`telegram.webhook_secret`、`discord.bot_token`、`discord.client_id/secret`、`unsubscribe_secret`。运行时：各渠道开关、限流、保留期。术语：`notify.category.<category>`、`notify.channel.<channel>`、各模板的标题与正文术语键（由模板所属插件提供）。

## 6. 外部接口需求概述

服务 `ctx.notify`（`send`、`send_many`、`channels_of`；⊕ `register_templates`、`send_to_address`）；事件 `notify.delivered`、`notify.failed`；订阅 `user.challenge_issued`、`user.logged_in`、`user.deleted`；HTTP `/api/p/notify/v1/*`（通知中心、偏好、绑定、Telegram webhook、退订）；插槽 `nav.user_menu`（铃铛）、`user.settings.tabs`（通知设置）。
