## 1. 设计目标与原则

1. **受理与投递分离**：`send` 只写 `outbox` 并调度投递任务；投递在延迟任务中逐渠道执行（出站 HTTP 只能在非钩子调用中进行，且调用方不应等待外部渠道）。
2. **模板集中**：模板由发送方插件登记，渲染在 notify 中按收件人语言进行，渲染结果只用于投递，不写日志。
3. **邮件走 HTTPS**：WASM 插件只有 `http-client` 能力，没有 SMTP；用 HTTP 发信服务或站点自建的 HTTP→SMTP 中继。
4. **安全类通知必达**：不受偏好与限流影响（仍受渠道可用性限制）。

## 2. 总体结构

```
插件 ─ctx.notify.send─► notify：偏好过滤 → 限流 / 合并 → INSERT inbox（站内）+ outbox（外部渠道）→ 调度 deliver
deliver（延迟任务）─► 渲染模板 ─► 适配器（email / telegram / discord）─► 记录投递 ─► 事件
Telegram ─webhook─► /v1/telegram/webhook（绑定码）
identity ─user.challenge_issued─► notify ─ctx.auth.challenge_delivery─► 邮件
```

| 模块 | 职责 |
|---|---|
| `templates` | 模板登记、校验、渲染（terms） |
| `prefs` | 类别 × 渠道偏好、默认值 |
| `intake` | send / send_many / send_to_address：幂等、偏好、限流、合并 |
| `center` | 站内通知中心 |
| `outbox` | 外部投递队列与重试 |
| `adapters` | email（多提供方）、telegram、discord |
| `bindings` | Telegram / Discord 绑定 |
| `security` | 挑战投递、登录提醒 |
| `unsubscribe` | 签名退订 |

## 3. 对外接口清单

| 类别 | 内容 |
|---|---|
| 服务 | `send(user_id, template_key, args, channels: Option<Vec>)`、`send_many(user_ids, …)`、`channels_of(user_id)`（已登记）；⊕ 全部写方法增加 `idempotency_key`；⊕ `register_templates(defs)`、`send_to_address(address, template_key, args, locale, idempotency_key)`（作用域 `send:address`） |
| 依赖 | `ctx.users`（用户名、语言、状态、`get_sensitive(email)`）、`ctx.auth`（`challenge_delivery`；作用域 `challenges:deliver`）、`ctx.terms` |
| 能力 | `sql`、`redis`、`kv`；`sensitive = ["user.email"]`；`http_outbound = ["api.telegram.org", "discord.com", "config:email.endpoint_host"]` |
| 事件 | 发布 `notify.delivered`、`notify.failed`；订阅 `user.challenge_issued`、`user.logged_in`、`user.deleted`、`kernel.settings_changed`（模板缓存失效） |
| HTTP | 见 03 §2.4 |
| 插槽 | `nav.user_menu`（铃铛 + 下拉）、`user.settings.tabs`（通知设置、渠道绑定） |
| cron | `cleanup`（`20 4 * * *`）、`digest_flush`（`* * * * *`） |
| 延迟任务 | `deliver` |
| 权限点 | `notify.preferences.update_own`、`notify.manage`（已登记） |

模板也可在清单中静态登记：

```toml
[notify.templates."comments.mentioned"]
category = "social"
default_channels = ["center"]
title_term = "comments.notify.mentioned.title"
body_term = "comments.notify.mentioned.body"     # MessageFormat：{actor} 在 {target_title} 中提到了你
unsubscribable = true
digest_minutes = 0
```

（⊕ 需要内核在启动时把各插件清单中的 `[notify.templates]` 交给 notify 的 `register_templates`，与 terms 的登记机制相同。）

## 4. 数据设计概要

`templates`、`prefs`、`inbox`（站内通知，按月分区）、`outbox`（外部投递）、`deliveries`（投递记录，按天分区）、`bindings`（telegram / discord）、`bind_codes`、`idempotency`；Redis：未读计数、限流、合并缓冲。

## 5. 关键流程

```
send(uid, key, args, channels?, idem):
  幂等 → 返回首次结果
  t = templates[key]（不存在 → notify.template_not_found）
  u = users.get(uid)；status = deleted → 丢弃（记录 skipped）
  chs = channels ?? t.default_channels；按 prefs（security 类除外）过滤；按绑定可用性过滤
  限流：超出 → 该渠道 skipped（security 类除外）
  合并：t.digest_minutes > 0 → 写入合并缓冲（Redis），由 digest_flush 产出一条
  center ∈ chs → INSERT inbox；INCR unread
  外部渠道 → INSERT outbox(channel, state = pending)；jobs.schedule_once("deliver", now, {outbox_id})
deliver(outbox_id)（tx manual）：渲染（收件人语言）→ 适配器发送 → ok：delivered；临时失败：重试；永久失败：failed + 停用绑定
```

## 6. 设计决策

| 编号 | 问题 | 结论与理由 |
|---|---|---|
| DD-NOTIFY-1 | 邮件发送方式 | HTTP 发信服务适配器：WASM 无 SMTP 能力；站点可部署 HTTP→SMTP 中继以使用自己的邮件服务器 |
| DD-NOTIFY-2 | 站内通知与站内信 | 分离：通知中心是 notify 自有的轻量表，避免依赖 messages（依赖环）且不淹没私信 |
| DD-NOTIFY-3 | 渲染时机 | 投递时渲染（按收件人语言与当前术语）；站内通知存模板键与参数，展示时渲染（术语改名后旧通知也显示新名称） |
| DD-NOTIFY-4 | 挑战令牌 | 只在投递任务内存中出现，不写 outbox（outbox 只存 challenge_id，投递时调用 `challenge_delivery`） |

## 7. 对平台契约的新增

服务方法与作用域（§3）；清单段 `[notify.templates]` 的内核支持；`config:` 出站主机声明；术语 `notify.category.<category>`、`notify.channel.<channel>`。
