> 约定：`N` = 分区数（默认 64，**以 Redis `acct:_meta` 的 `partitions` 字段为准**，不用 `SCAN acct:*` 推断；每分区 `MAXLEN ~ 2,000,000`，容量规划按此计算）；`W` = 结算窗口秒数（默认 900）；`H(t)` = 流时间 t（毫秒）所在小时序号 `floor(t / 3_600_000)`；`WIN(t)` = `floor(t / (W·1000)) · W`（窗口起点，Unix 秒）。所有“时间”未特别说明均为流时间（Stream ID 毫秒部分）。

## 1. 模块详细设计

### 1.1 ingest：分区 worker

**职责**：持有分区 p 的租约时，被内核循环调用 `poll(ctx, p, fence)`（HLD §7 N-1）。每次调用是一个工作单元：读一个微批、落库、提交。

**核心数据结构**（Rust，进程内）：

```rust
/// 解析后的条目（不含 ip/port；ua 只保留指纹所需的前 32 字节，不落库）
struct Entry {
    id: StreamId,            // (ms, seq)
    eid: String,             // {node}:{boot}:{seq}
    ts: i64,                 // announce 时间（秒）
    uid: u64, tid: u64,
    pid: [u8; 20],
    ev: Ev,                  // Started | Stopped | Completed | None
    up: u64, down: u64, left: u64,      // 原始累计值
    dup: u64, ddown: u64, dseed: u64, dleech: u64,
    flags: u32,
    client: ClientFp,        // peer_id 前缀（如 "-qB4630-"）+ UA 指纹类别
}
struct Batch { part: u32, hour: i64, window: i64, entries: Vec<Entry>, first: StreamId, last: StreamId }
```

**算法**：

```
poll(ctx, p, fence):
    cur = SELECT last_id, watermark_ms, fence FROM stream_cursors WHERE part = p FOR UPDATE   -- 本事务锁住游标行
    if cur.fence > fence: return Err(accounting.lease_lost)      -- 旧持有者，放弃
    UPDATE stream_cursors SET fence = fence WHERE part = p        -- 记录新 fencing token（单调）
    conn = ctx.redis.global("acct")
    gap_check(p, cur.last_id)                                     -- §1.11
    entries = []; deadline = now + batch_max_ms
    loop:
        r = XREAD COUNT min(5000, batch_max_entries - len) BLOCK max(0, deadline-now) STREAMS acct:p <cur.last_id 或 entries.last.id>
        if r 为空:
            if entries 为空:
                t = Redis TIME（毫秒）
                UPDATE stream_cursors SET watermark_ms = greatest(watermark_ms, t - 1), idle_since = coalesce(idle_since, now())
                close_windows(p, watermark)                       -- §1.6，读空时也推进窗口
                commit; return Idle{sleep_ms: 200}
            break
        for raw in r:
            if entries 非空 且 H(raw.id.ms) != H(entries[0].id.ms): break 外层   -- 微批不跨小时（因此也不跨窗口）
            match parse(raw):
                Ok(e)  => entries.push(e)
                Err(x) => rejected.push((raw.id, x))              -- 写 rejected_entries，游标照样推进
        if len(entries)+len(rejected) >= batch_max_entries or now >= deadline: break
    batch = dedupe_eid(entries, p)                                -- §1.1.1
    agg = aggregate(batch)                                        -- §1.2
    rates.apply(agg)                                              -- §1.3
    sigs = signals.evaluate(batch, agg)                           -- §1.4
    store.merge(p, agg, sigs, rejected)                           -- §1.5
    close_windows(p, watermark = batch.last.ms)                   -- §1.6
    n = UPDATE stream_cursors SET last_id = batch.last, last_ms = batch.last.ms,
            watermark_ms = greatest(watermark_ms, batch.last.ms), idle_since = NULL,
            committed_at = now(), entries_total = entries_total + len
        WHERE part = p AND last_id = cur.last_id AND fence = fence
    if n != 1: return Err(accounting.lease_lost)                  -- 回滚整批
    commit（内核在 poll 返回 Ok 时提交，含 outbox）
    —— 以下在提交之后执行（失败只记指标，下一次 poll 会补做）——
    live.deduct(p, agg.user_raw, batch.last)                      -- §1.7
    XTRIM acct:p MINID ~ <batch.last.ms - stream_retain_secs*1000>
    XGROUP SETID acct:p accounting batch.last                     -- 进度镜像（组不存在则 XGROUP CREATE … MKSTREAM）
    return Busy
```

**提交后操作的说明**：内核在 `poll` 返回后才提交事务，因此“提交之后”的 Redis 操作放在下一次 `poll` 开头执行：worker 在进程内记住 `pending_post_commit = (p, agg 摘要, last_id)`，下一次 `poll` 开始时先读游标确认 `last_id` 已等于该值（说明已提交）再执行；若进程崩溃丢失该记忆，下一个持有者在首次 `poll` 时对“游标前 `stream_retain_secs` 内”的用户做一次 `live.reconcile`（§1.7）。

#### 1.1.1 eid 去重

pt-tracker 的 XADD 超时重试会产生 `eid` 相同、Stream ID 不同的条目。去重窗口为同一分区最近 10 分钟：

- 进程内 LRU（每分区 20 万条，约 8 MB）；
- 持久化兜底：表 `eid_seen(part, eid, seen_ms)`，只记录 `flags` 含 first_completed 或增量 ≥ 64 MiB 的“高价值”条目（其余条目重复时影响极小，且 pt-tracker 的重试极少）。去重命中时计数 `pt_plugin_accounting_duplicate_entries_total`。

#### 1.1.2 parse

| 字段 | 校验 | 失败处理 |
|---|---|---|
| `v` | == "1" | 其他版本 → rejected（`unsupported_version`） |
| `uid` | u64，`uid % N == p` | 不符 → rejected（`wrong_partition`） |
| `tid` | u64 > 0 | rejected |
| `pid` | 40 位 hex | rejected |
| `ev` | started/stopped/completed/none（大小写不敏感，原型的 `None` 兼容） | rejected |
| `up/down/left/dup/ddown/dseed/dleech` | 十进制 u64，`dseed+dleech ≤ 86400`，`dup,ddown ≤ 2^50` | `dup` / `ddown` 超界 → **只丢弃流量字段**（按 0 计），保留时长、`ev` 与完成标记，并产生 `counter_jump{kind: out_of_range}` 信号（评审 F-03：整条拒收会丢失完成记录）；`dseed+dleech` 超界 → 两者按 0 计；无法解析为 u64 → rejected |
| `flags` | u32（兼容原型的 JSON 写法：解析 `{"first_seen":true,…}`）；**未知位忽略**（pt-tracker 新增标志不需要同步发布 accounting） | 无法解析 → rejected |
| `ip`、`port` | **不解析，直接丢弃** | — |
| `ua` | 截取 ≤ 128 字节，只计算指纹类别，不存储 | — |

### 1.2 aggregate

微批内三级合并（全部用 `HashMap`，键有序输出以保证 SQL 写入顺序一致、避免死锁）：

| 聚合 | 键 | 值 |
|---|---|---|
| `PeerAgg` | (uid, tid, pid) | 最后 ev、left、is_seeder(left==0)、last_ts、Σdseed（写入小时槽）、client 前缀、首见标记 |
| `PairAgg` | (uid, tid, rate_key) | Σdup、Σddown、Σdup_credited、Σddown_credited、Σdseed（仅随传输条目）、Σdleech、first_completed 最早时间、touch（是否需要写 snatch） |
| `UserAgg` | uid | Σ原始与计入上传下载、Σdleech、本批用户原始量（用于 live 扣减） |
| `TorrentUserHourly` | (hour, tid, uid) | Σdup_raw、Σddown_raw |

**做种时长的唯一来源（实现澄清，2026-10-07）**：`snatches.seed_secs`、`user_totals.seed_secs`、`user_daily.seed_secs` 只由小时快照（§1.9）折叠写入；微批落库时不累加 `dseed`（否则随传输条目上报的做种秒数会在快照折叠时再计一次）。`settle_buffer` / `traffic.settled` 中的 `d_seed_secs` 仍保留，仅作参考（事件定义已注明“不完整”）。

`touch` 的判定：`dup>0 || ddown>0 || dleech>0 || flags∩{first_seen, first_completed} ≠ ∅ || ev ∈ {started, completed, stopped}`。`touch = false` 的条目（纯做种续报）只进入 `PeerAgg`。

### 1.3 rates：倍率规则

**规则模型**（与 WIT `rate-rule` 对应）：

```rust
struct RateRule {
    id: u64,
    owner_plugin: String,          // 调用方插件 ID（内核注入的 caller_plugin）
    external_ref: String,          // 调用方自己的引用，如 "promotion:123"
    scope: Scope,                  // Global | Torrents(Vec<u64>) | Users(Vec<u64>) | UserTorrent(u64, u64)
    up_permille: Option<u32>,      // None = 不影响上传
    down_permille: Option<u32>,
    mode: Mode,                    // Favorable | Override
    priority: i32,                 // 仅 Override 使用，越大越优先
    starts_at: i64, ends_at: Option<i64>,   // 毫秒
    removed_at: Option<i64>,       // remove_rate_rule 设置；有效结束 = min(ends_at, removed_at)
    supersedes: Option<u64>,
    reason_term: Option<String>,   // 展示用术语键，如 "promotion.free"
}
```

**进程内索引**（每副本一份，`ArcSwap` 原子替换）：`global: Vec<Rule>`、`by_torrent: HashMap<u64, SmallVec<Rule>>`、`by_user: HashMap<u64, SmallVec<Rule>>`、`by_pair: HashMap<(u64,u64), SmallVec<Rule>>`，只装载“未结束或结束时间晚于 now − 2 h”的规则（迟到条目最多 2 h，见 §1.11）；更早的规则只在重算时从数据库读。

**刷新**：每次 `poll` 开头 `GET p:accounting:rate:ver`（main 实例私有键），与本地版本不同则 `SELECT … WHERE updated_at > $last_loaded - 5s` 增量加载；冷启动全量加载。服务写规则后（提交成功）`INCR rate:ver`。若 INCR 失败，各副本最迟在 `rate_rule_gc`（每小时）全量刷新；为避免这种情况，服务方法在提交后同步重试 INCR 3 次，仍失败则返回成功但告警（规则已持久化）。

**求有效倍率**：

```
effective(uid, tid, t):
    cands = [r ∈ global ∪ by_torrent[tid] ∪ by_user[uid] ∪ by_pair[(uid,tid)] | r.starts_at ≤ t < r.effective_end]
    up = None; down = None
    ov = cands.filter(mode == Override).sort_by(priority desc, id desc)
    for r in ov: if up is None and r.up is Some: up = r.up
                 if down is None and r.down is Some: down = r.down
    if up is None:   up   = max(1000, max(r.up   for r in cands if Favorable and r.up is Some))
    if down is None: down = min(1000, min(r.down for r in cands if Favorable and r.down is Some))
    up = min(up, rates.max_up_permille)
    ids = sorted(r.id for r in cands)                 -- 全部命中规则（重算依据）
    return (up, down, ids)
rate_key = xxh3_64(up, down, ids) as i64
credited_up = dup * up / 1000（u128 中间值，向下取整）；credited_down 同理
```

说明：favorable 模式下规则只能“对用户更有利”（上传 ≥ 1x、下载 ≤ 1x）；惩罚类（个人上传 0x、下载 2x）必须用 Override。`set_rate_rule` 校验：Favorable 规则 `up ≥ 1000`、`down ≤ 1000`，否则 `accounting.rate_rule_invalid`。

### 1.4 signals：基础信号

> 实现说明（2026-10-16，`src/signals.rs`）：阈值为静态配置 `[plugin.accounting.signals]`（键同 SRS §5 `signals.*`，另有 `enabled`）；
> 条目级判定在微批落库事务中执行，活跃 leecher 直接查 `peers`（本批已写入），不维护进程内位图；`counter_jump` 的
> `baseline_reset` 分为 `started_nonzero`（首报 started 携带非零累计值，medium）与 `baseline_reset_nonstart`（low）；
> pt-tracker 截断的超速段（流字段 `xup`）一律 high，details.kind = `tracker_cap`；`client_not_allowed` 尚未实现。
> 交叉校验读 `torrent_user_hourly`（入库时按窗口所在小时累加，保留 48 小时），按全部分区水位逐小时处理（`cross_check_runs`）。
> 另提供视图 `v_swarm_peers`（anticheat 案件的 swarm 快照）与后台 `GET /v1/admin/signals`。

**条目级规则**（在 `evaluate` 中逐条执行，种子体积来自镜像 `torrents`，缺失时跳过体积相关检查并计数）：

| 信号 | 条件 | severity | details |
|---|---|---|---|
| `speed_exceeded` | `dup ≥ speed_min_bytes` 且 `interval = dseed + dleech > 0` 且 `dup / interval > speed_limit_bps` | 超出倍数 <2 → medium；≥2 → high | `{bytes, interval_secs, speed_bps, limit_bps, client}` |
| `negative_delta` | flags 含 upload_regressed 或 download_regressed | low | `{kind: "upload_regressed"|"download_regressed", reported_up, reported_down}` |
| `counter_jump` | ① flags 含 baseline_reset；② `dup > size × jump_size_factor`；③ `left > size`；④ 解析超界 | ① low；②③④ medium | `{kind: "baseline_reset_nonstart"|"delta_exceeds_size"|"left_exceeds_size"|"out_of_range", …}` |
| `peer_not_in_swarm` | `dup ≥ no_peer_min_bytes`，且该种子在最近两次 swarm 统计中 leechers 均为 0（进程内位图，§1.8 每次运行后刷新），且本微批中该种子也没有其他用户的 leecher 条目 | dup ≥ 10 × 阈值 → medium；否则 low | `{kind: "no_leechers", bytes, seeders, leechers: 0}` |
| `client_not_allowed` | `client_fingerprint_check = true` 时：peer_id 前缀对应的客户端族与 UA 族不一致（映射表在设置 `signals.client_families`）→ `fingerprint_mismatch`；同一 (uid, tid, pid) 的前缀与 peers 表记录不同 → `fingerprint_changed` | medium | `{kind, peer_id_prefix, ua_family}`（不含 UA 原文） |

**小时级规则**（cron `cross_check`，§1.10）：`cross_check_mismatch`。

**去重**（与条目处理同一事务）：

```
for s in sigs (按 uid, tid, signal 排序):
    d = INSERT INTO signal_dedupe(user_id, torrent_id, signal, severity, until, signal_id, signal_created_at, hits)
        VALUES (…, now()+dedupe_secs, NULL, NULL, 1)
        ON CONFLICT (user_id, torrent_id, signal) DO UPDATE
          SET hits = CASE WHEN signal_dedupe.until > now() THEN signal_dedupe.hits + 1 ELSE 1 END,
              severity = greatest_sev(…), until = CASE WHEN signal_dedupe.until > now() THEN signal_dedupe.until ELSE EXCLUDED.until END
        RETURNING (xmax = 0) AS inserted, 旧 until 是否过期（借助 CTE 先 SELECT … FOR UPDATE 取旧值）, 旧 severity
    if inserted 或 已过期 或 severity 升级:
        INSERT signals(…) RETURNING id, created_at → 回写 signal_dedupe.signal_id
        events.publish(traffic.signal_raised, key user:<uid>)
    else:

```

`torrent_id` 无关的信号用 0 存储（事件中省略）。

### 1.5 store：落库

每个微批在一个事务中按以下**固定顺序**执行（全部 worker 一致，避免死锁）：

1. `COPY` 到暂存表（UNLOGGED，见 §3.1），每行带 `batch_id`（UUIDv7）。暂存表：`stage_peers`、`stage_pairs`、`stage_users`、`stage_tuh`。
2. `peers` upsert（按 user_id, torrent_id, peer_id 排序）：

```sql
INSERT INTO peers AS p (user_id, torrent_id, peer_id, part, is_seeder, is_active, client_prefix,
                        last_announce_at, first_seen_at, slot0_hour, slot0_secs, slot1_hour, slot1_secs)
SELECT s.user_id, s.torrent_id, s.peer_id, s.part, s.is_seeder, s.ev <> 'stopped', s.client_prefix,
       s.last_announce_at, s.last_announce_at,
       CASE WHEN s.hour % 2 = 0 THEN s.hour END, CASE WHEN s.hour % 2 = 0 THEN s.dseed ELSE 0 END,
       CASE WHEN s.hour % 2 = 1 THEN s.hour END, CASE WHEN s.hour % 2 = 1 THEN s.dseed ELSE 0 END
FROM stage_peers s WHERE s.batch_id = $1
ORDER BY s.user_id, s.torrent_id, s.peer_id
ON CONFLICT (user_id, torrent_id, peer_id) DO UPDATE SET
    is_seeder = EXCLUDED.is_seeder,
    is_active = EXCLUDED.is_active,
    client_prefix = EXCLUDED.client_prefix,
    last_announce_at = greatest(p.last_announce_at, EXCLUDED.last_announce_at),
    slot0_secs = CASE WHEN EXCLUDED.slot0_hour IS NULL THEN p.slot0_secs
                      WHEN p.slot0_hour = EXCLUDED.slot0_hour THEN p.slot0_secs + EXCLUDED.slot0_secs
                      ELSE EXCLUDED.slot0_secs END,
    slot0_hour = coalesce(EXCLUDED.slot0_hour, p.slot0_hour),
    slot1_secs = CASE WHEN EXCLUDED.slot1_hour IS NULL THEN p.slot1_secs
                      WHEN p.slot1_hour = EXCLUDED.slot1_hour THEN p.slot1_secs + EXCLUDED.slot1_secs
                      ELSE EXCLUDED.slot1_secs END,
    slot1_hour = coalesce(EXCLUDED.slot1_hour, p.slot1_hour);
```

   注：stopped 的 peer 置 `is_active=false` 但不删除（其小时槽要等快照折叠）；`peer_gc` 负责删除。

3. 完成判定：对 `PairAgg` 中带 first_completed 的 (uid, tid)：`SELECT user_id, torrent_id, completed_at FROM snatches WHERE (user_id, torrent_id) IN (…) ORDER BY 1,2 FOR UPDATE`，`completed_at IS NULL`（或行不存在）者为“首次完成”。
4. `snatches` upsert（只含 touch 的对，同一 (uid,tid) 的多个 rate_key 先在内存合并）：

```sql
INSERT INTO snatches AS s (user_id, torrent_id, uploaded_raw, downloaded_raw, uploaded, downloaded,
                           seed_secs, leech_secs, first_action_at, last_action_at, completed_at, times_completed)
SELECT … FROM stage_pairs WHERE batch_id = $1 ORDER BY user_id, torrent_id
ON CONFLICT (user_id, torrent_id) DO UPDATE SET
    uploaded_raw   = s.uploaded_raw + EXCLUDED.uploaded_raw,
    downloaded_raw = s.downloaded_raw + EXCLUDED.downloaded_raw,
    uploaded       = s.uploaded + EXCLUDED.uploaded,
    downloaded     = s.downloaded + EXCLUDED.downloaded,
    seed_secs      = s.seed_secs + EXCLUDED.seed_secs,
    leech_secs     = s.leech_secs + EXCLUDED.leech_secs,
    last_action_at = greatest(s.last_action_at, EXCLUDED.last_action_at),
    completed_at   = coalesce(s.completed_at, EXCLUDED.completed_at),
    times_completed = s.times_completed + EXCLUDED.times_completed,
    updated_at     = now();
```

5. `torrent_counters`：首次完成按 torrent_id 升序 `INSERT … ON CONFLICT DO UPDATE SET completed = completed + EXCLUDED.completed`；对每个首次完成发布 `traffic.snatch_completed`。
6. `user_totals` upsert（`stage_users`，按 user_id 排序；字段累加）；`user_daily` upsert（`day` = 流时间按站点时区的日期）。
7. `settle_buffer` upsert（只含传输对，键 (window_start, part, user_id, torrent_id, rate_key)）。
8. `torrent_user_hourly` upsert（只含 dup>0 或 ddown>0）。
9. 信号去重与写入（§1.4）；`rejected_entries` 插入。
10. `DELETE FROM stage_* WHERE batch_id = $1`。
11. 窗口关闭（§1.6）、游标 CAS（§1.1）。

### 1.6 windows：结算窗口关闭

```
close_windows(p, watermark_ms):
    closable = WIN(watermark_ms - settle_grace_secs*1000)        -- 严格小于此起点的窗口都已完整
    rows = DELETE FROM settle_buffer WHERE part = p AND window_start < closable
           RETURNING window_start, user_id, torrent_id, rate_key, up_permille, down_permille, rule_ids,
                     up_raw, down_raw, up, down, seed_secs, leech_secs, completed
    if rows 为空: return
    -- 1) 分段明细（重算依据）
    INSERT INTO traffic_segments(day, user_id, torrent_id, rate_key, up_permille, down_permille, rule_ids, up_raw, down_raw, up, down)
      SELECT … 按 (day(window_start), user, torrent, rate_key) 聚合 ON CONFLICT DO UPDATE 累加
    -- 2) 事件：按 (window_start, user_id) 分组，同一种子多个 rate_key 合并为一项（rule_ids 取并集）
    for (w, uid), items in group(rows):
        batch_id = uuid_v5(NS, "settle:{w}:{uid}")               -- 确定性，重放可识别
        for part_items in split_by_size(items, 60 KiB):
            events.publish({type: traffic.settled, version: 1, key: "user:{uid}",
                            payload: {user_id, window_start, window_end: w+W, items: part_items,
                                      batch_id, part, parts}})
```

由于 DELETE 与发布在同一事务、且同一分区只有一个持有者，每个 (窗口, 用户) 的事件恰好发布一次。迟到条目（流时间早于已关闭窗口，见 §1.11）计入其流时间对应的窗口——由于流时间单调，这种情况不会发生；`settle_grace_secs` 只用于等待“读空时刻”的水位稳定。

兜底 cron `close_windows`：对 `idle_since` 超过 60 s 的分区（worker 未运行或长时间读空）直接调用 `close_windows(p, watermark_ms)`，以 `SELECT … FROM stream_cursors WHERE part = p FOR UPDATE NOWAIT` 防止与 worker 并发（拿不到锁说明 worker 正在处理，跳过）。

### 1.7 live：实时计数扣减

Lua 脚本（内核网关对插件禁用 EVAL，但 `redis_global` 原生连接不受限；脚本随插件发布，`SCRIPT LOAD` 后 EVALSHA）：

```lua
-- live_deduct.lua   KEYS[1] = u:<uid>:live
-- ARGV[1] = 字段前缀 'a'（流量）或 's'（做种时长）
-- ARGV[2] = 本次批次标识：流量为 Stream ID "ms-seq"；做种为小时序号 "h"
-- ARGV[3..] = 字段名、扣减值 成对出现
if redis.call('EXISTS', KEYS[1]) == 0 then return 0 end
local mark = ARGV[1] .. 'id'
local last = redis.call('HGET', KEYS[1], mark)
local function gt(a, b)                       -- a > b ？按 "ms-seq" 或整数比较
  if not b then return true end
  local am, as = string.match(a, '^(%d+)-?(%d*)$'); local bm, bs = string.match(b, '^(%d+)-?(%d*)$')
  am, bm = tonumber(am), tonumber(bm)
  if am ~= bm then return am > bm end
  return (tonumber(as) or 0) > (tonumber(bs) or 0)
end
if not gt(ARGV[2], last) then return 0 end
for i = 3, #ARGV, 2 do redis.call('HINCRBY', KEYS[1], ARGV[i], -tonumber(ARGV[i+1])) end
redis.call('HSET', KEYS[1], mark, ARGV[2])
return 1
```

- 流量：每个微批提交后，对 `UserAgg` 中每个用户 `EVALSHA live_deduct 1 u:<uid>:live a <last_id> up <Σdup> down <Σddown>`（pipeline，每 500 个一组）。同一用户只属于一个分区、游标单调，因此重复执行被 `aid` 拦下。
- 做种时长：小时折叠（§1.9）提交后 `EVALSHA live_deduct 1 u:<uid>:live s <hour> seed_time <Σ>`。
- 键不存在时不扣（键已过期，实时值从 0 开始，只会偏小）。展示值做下限 0 截断。
- `live.reconcile(p)`（接管分区时）：对游标前 `stream_retain_secs` 内出现的用户，比较 `aid` 与游标：`aid` 早于游标则用 `XRANGE acct:p (aid 游标]` 重新累计该用户的原始量并补扣。

`user_totals(user_id)` 返回：`uploaded = DB 计入值`，`live_uploaded = DB 计入值 + max(0, HGET up)`（实时部分未乘倍率，前端以“约”标注）。

### 1.8 swarm：统计与发布

```
cron swarm_stats (tx = manual, timeout 240 s):
    cutoff = now() - peer_timeout_secs
    max_tid = SELECT max(id) FROM torrents
    for lo in 0..max_tid step 20000:
        cur = SELECT torrent_id,
                     count(*) FILTER (WHERE is_seeder) AS seeders,
                     count(*) FILTER (WHERE NOT is_seeder) AS leechers
              FROM peers WHERE torrent_id >= lo AND torrent_id < lo+20000
                AND is_active AND last_announce_at >= cutoff
              GROUP BY torrent_id
        prev = SELECT torrent_id, seeders, leechers, completed FROM swarm_stats WHERE torrent_id 在范围内
        comp = SELECT torrent_id, completed FROM torrent_counters WHERE 范围内
        changed = diff(cur ⊕ comp, prev)          -- 不在 cur 中但 prev 非零的种子 → (0,0)
        UPSERT swarm_stats(changed) SET seeders, leechers, completed, updated_at, zero_leech_runs = CASE leechers=0 THEN +1 ELSE 0
        for chunk in changed.chunks(1000):
            events.publish(traffic.swarm_stats_updated, key "swarm:{bucket}", {items: chunk, computed_at})
        sql.commit()
    INCR p:accounting:swarm:ver                      -- 各副本刷新“无下载者”位图（zero_leech_runs ≥ 2 的种子）
```

注：`(torrent_id % 64)` 分桶用于事件 key（HLD §7 N-3）；同一 chunk 内的种子可能跨桶，按桶再拆分发布。

### 1.9 snapshot：小时快照与做种时长折叠

```
cron seeding_snapshot (schedule "2 * * * *", catch_up once, tx manual, timeout 3300 s):
    h = H(now) - 1                                       -- 上一小时
    wm = SELECT min(greatest(watermark_ms, CASE WHEN idle_since IS NOT NULL THEN watermark_ms END)) FROM stream_cursors
    if wm < (h+1)*3600000 + settle_grace_secs*1000:
        if now < (h+1)*3600 + 3300: 等待 30 s 后重读（循环，最长到截止时间）
        else: 告警 accounting_snapshot_watermark_late，照常继续（落后分区的迟到数据写入 h+1 的槽）
    slot = h % 2
    for p in 0..N:
        if snapshot_runs(h, p).state = 'done': continue  -- 幂等
        loop 每 2000 个用户一组（按 user_id 升序，游标存 snapshot_runs.last_user_id）:
            rows = SELECT user_id, torrent_id, sum(slot{slot}_secs) AS secs, bool_or(is_active AND is_seeder) AS seeding
                   FROM peers WHERE part = p AND slot{slot}_hour = h AND user_id > $last
                   GROUP BY user_id, torrent_id ORDER BY user_id, torrent_id LIMIT … (按用户边界截断)
            secs = min(secs, 3600)                       -- 多个 peer_id 同时做种同一种子，按 1 小时封顶
            -- 折叠
            UPDATE snatches SET seed_secs = seed_secs + v.secs, last_action_at = greatest(last_action_at, h 末), updated_at = now()
              FROM (VALUES …) v WHERE (user_id, torrent_id) = (v.u, v.t)       -- 按键排序
            INSERT INTO snatches … ON CONFLICT DO NOTHING                        -- 只做种、从未 touch 的对（罕见）补建
            UPDATE user_totals SET seed_secs = seed_secs + Σ … ; user_daily 同步累加
            -- 事件
            for uid: events.publish(traffic.seeding_snapshot_taken, key user:uid,
                     {user_id, taken_at: (h+1)*3600, period_secs: 3600, period_start: h*3600,
                      torrents: [{torrent_id, size: mirror.size, seed_secs, seeders: swarm_stats.seeders}]})
                     （超过 60 KiB 拆分，带 batch_id/part/parts）
            UPDATE snapshot_runs SET last_user_id = …; sql.commit()
            （提交后）live_deduct(s, h, seed_time)
        UPDATE snapshot_runs SET state = 'done'; sql.commit()
```

**截止约束**：小时 h 的槽在 h+2 开始被覆盖，因此任务必须在 h+2 前完成；超时告警 `accounting_snapshot_overrun`（该小时剩余用户的做种时长丢失，宁可少记，与 pt-tracker 原则一致）。

### 1.10 cross_check：交叉校验

```
cron cross_check ("7 * * * *"):
    h = H(now) - 1；等待水位越过 (h+1) 整点（同 §1.9）
    per 种子（按 torrent_id 分批 5000）:
        agg = SELECT torrent_id, sum(up_raw) U, sum(down_raw) D, count(*) FILTER (WHERE up_raw>0) n_up
              FROM torrent_user_hourly WHERE hour = h GROUP BY torrent_id
        for t in agg where U > D * (100 + tol)/100 + slack:
            excess = U - D
            top = SELECT user_id, up_raw FROM torrent_user_hourly WHERE hour = h AND torrent_id = t ORDER BY up_raw DESC LIMIT top_k
            for (uid, up) in top where up * 2 >= excess or up >= slack:     -- 只归因到“单人就足以解释大部分超额”的用户
                signal(cross_check_mismatch, uid, t, severity = excess ≥ 10*slack ? high : medium,
                       details {hour_start, swarm_uploaded: U, swarm_downloaded: D, user_uploaded: up,
                                user_share_pct: up*100/U, uploaders: n_up})
        sql.commit()
```

说明：下载方的数据同样来自客户端上报，虚报下载很少（会降低分享率）；超额主要来自虚报上传。小时粒度下存在“上传方在 h 末、下载方计入 h+1”的边界误差，由容差与余量吸收；anticheat 应把单次 `cross_check_mismatch` 视为弱证据，多小时累积为强证据。

### 1.11 maintenance

**流缺口**（`gap_check`）：`XINFO STREAM acct:p` 取 `first-entry` ID；若游标 `last_id < first_id − 1` 且游标非初始值：插入 `stream_gaps(part, from_id, to_id, detected_at)`，指标 `pt_plugin_accounting_stream_gaps_total`；`on_stream_gap = pause` 时返回 `Err(accounting.stream_gap)`（内核按退避重试，后台显示“暂停”，管理员在后台“确认跳过”后写 `stream_cursors.gap_ack = true` 继续）；`continue` 时直接继续。首次部署游标为 `0-0`，以 `XINFO` 的 first-entry 作起点，不算缺口。

**ghost peer 清理**（cron `peer_gc`，每 10 分钟，按 part 分批 `LIMIT 5000` 循环 + commit）：

```sql
UPDATE peers SET is_active = false
 WHERE part = $p AND is_active AND last_announce_at < now() - make_interval(secs => $peer_timeout);
DELETE FROM peers
 WHERE part = $p AND NOT is_active AND last_announce_at < now() - make_interval(secs => $peer_purge)
   AND coalesce(slot0_hour, 0) < $h_cur - 1 AND coalesce(slot1_hour, 0) < $h_cur - 1;   -- 槽已被快照折叠
```

**对账**（cron `reconcile`，tx manual，按用户 1000 一批）：

| 检查 | 公式 | 处理 |
|---|---|---|
| R1 总量 = 每日 + 调整 | `user_totals.{uploaded,downloaded,seed_secs,leech_secs,…raw}` = Σ `user_daily` + Σ `adjustments` | 差异写 `reconcile_issues(kind='totals_vs_daily')`；`auto_fix` 时以右侧覆盖并审计 |
| R2 snatch 传输量 = 分段明细 | 对保留期内首日之后有活动的对：Σ `traffic_segments.up_raw` 等于 snatch 在同期的增长——无法直接比较历史值，改为比较“昨日”：Σ 昨日 `traffic_segments` = Σ 昨日 `user_daily`（传输部分） | 只告警 |
| R3 live 基线 | 抽样 1000 个用户：`HGET aid` 不早于其分区游标前 `stream_retain_secs` | 告警，触发 `live.reconcile` |
| R4 完成数 | `torrent_counters.completed` = `count(snatches WHERE completed_at IS NOT NULL)`（按种子抽样 1000 个，需扫描 32 个分区的 `torrent_id` 索引） | 修正并告警 |

**归档**（cron `archive`，依赖 HLD §7 N-4 的 `archive_hook`；未合入前由本任务在保留期到期前 3 天主动导出）：对即将被删除的分区（`traffic_segments`、`torrent_user_hourly` 按日；`signals`、`rejected_entries` 按月）执行 `SELECT … ORDER BY …` 流式写 CSV.gz 到 blob `archive/<table>/<partition>.csv.gz`，另写 `archive/<table>/<partition>.manifest.json`（行数、sha256、列）；`user_daily` 永久保留不归档删除。

**重算**（延迟任务 `recalc_step`，tx manual）：

```
POST /admin/recalcs {rule_id, action: "set_rates"|"void", up_permille?, down_permille?, from_day, to_day, dry_run}
  校验：from_day ≥ today - recalc.retention_days + 1，否则 accounting.recalc_window_expired
       同一 rule_id 无进行中任务，否则 accounting.recalc_in_progress
  INSERT recalc_jobs(state='planning')；jobs.schedule_once("recalc_step", now, {job_id}, dedupe="recalc:<id>")
recalc_step(job):
    planning：
        rules = 加载 rule_ids 涉及的全部规则（含已结束）；对 rule_id 套用更正（void = 从集合中剔除）
        游标遍历 traffic_segments WHERE day BETWEEN … AND $rule_id = ANY(rule_ids)（GIN 索引）按 (user_id) 分组：
            new_up = up_raw * eff_up(rules', ids) / 1000 …；delta_up = Σ(new_up − up)，delta_down 同理
            UPSERT recalc_items(job_id, user_id, delta_up, delta_down)
        每 5000 行 commit 并保存游标；完成后 state = dry_run ? 'previewed' : 'applying'
    applying：
        遍历 recalc_items WHERE applied_at IS NULL ORDER BY user_id LIMIT 500：
            service.adjust(uid, delta_up, delta_down, reason="accounting.recalc", idempotency_key="recalc:<job>:<uid>",
                           clamp = true)          -- 重算扣减不足时扣到 0，并记录 clamped 差额
            UPDATE recalc_items SET applied_at = now()
        commit；未完则 schedule_once 下一步（dedupe 同键）
    完成：state = 'done'；审计 accounting.recalc
```

“预览”状态下管理员在后台确认后 `POST /admin/recalcs/{id}:apply`（子资源 `/v1/admin/recalcs/{id}/applications`）把状态改为 `applying` 并调度。重算**不修改** snatch 与分段明细（历史仍反映当时的计算），差额只体现在 `user_totals` 与 `adjustments`。

**重建总量**（`rebuild_totals_step`）：按用户批次 `user_totals := Σ user_daily + Σ adjustments`，与对账 R1 自动修复相同逻辑，由 sysop 通过 `pt-server jobs run accounting rebuild_totals` 触发。

**流重放**（PG 故障切换导致已提交事务丢失、游标回退）：无需特殊处理——游标即事实，worker 从回退后的游标重新读取（流中保留了 `stream_retain_secs` 余量）；若回退超过余量，按流缺口处理。

### 1.12 mirror：种子镜像与用户删除

| 订阅 | 处理 |
|---|---|
| `torrent.created` | `INSERT INTO torrents(id, size, status) ON CONFLICT (id) DO UPDATE SET size, status, updated_at` |
| `torrent.status_changed` | `UPDATE torrents SET status = $to, updated_at = now() WHERE id = $id`（行不存在则从视图补一行） |
| `torrent.deleted` | `UPDATE torrents SET is_deleted = true, updated_at = now()`；swarm 统计排除；snatch 保留 |
| `user.deleted`（mode=purge，tx manual） | 分批（每批 5000 行 + commit）删除 `peers`、`snatches`、`settle_buffer`、`torrent_user_hourly`、`traffic_segments`、`signals`、`signal_dedupe`、`user_daily` 中该用户行；`adjustments.note` 置空；`user_totals` 置零并 `purged_at = now()`；`recalc_items` 删除；已归档文件中的该用户行由下次归档覆盖时过滤（manifest 记录 `purged_users` 列表，读取工具过滤） |
| `user.deleted`（mode=soft） | 只设 `user_totals.hidden = true`，对外接口返回 404 |

各订阅以 `_inbox` 保证数据库副作用恰好一次；purge 为 `tx = "manual"`，重复投递时已删除的批次为空操作。

启动（`lifecycle.init`）：若 `torrents` 为空，从 `torrent.v_torrent_public` 分批（1 万行/批）导入；之后每 30 s 各副本增量刷新进程内镜像（`updated_at > $last`）。

| `adjust` | `write:adjust` | `reason` 为原因码 `<plugin>.<code>`；同一 (caller, key) 幂等，`duplicate=true` 返回首次结果；结果使计入总量为负则拒绝（HTTP 管理员接口可选 `clamp`） | `accounting.adjust_would_be_negative`、`accounting.adjust_out_of_range`（单次 \|d\| > 2^50）、`kernel.idempotency_key_reused`（同键不同参数） |
| `signals` | `read:signals` | 区间 ≤ 366 天 | `kernel.validation_failed` |

Rust trait 由 `pt_plugin_api::service!("wit/accounting.wit")` 生成 `AccountingService`，方法首参 `&Ctx`。

## 6. 安全设计

| 项 | 措施 |
|---|---|
| 敏感数据 | 解析时丢弃 `ip`、`port`；UA 只用于内存中的指纹比较；passkey 不在流中出现；事件、日志、MCP、指标标签均不含以上字段（契约测试） |
| 权限 | 路由按 §2.4；服务方法按作用域；读他人 snatch 列表需本人或 `accounting.stats.read`；完成者列表受 `snatch_list_public` 控制 |
| 输入校验 | 流条目严格校验（§1.1.2）；倍率规则：`external_ref` 正则、target 列表 ≤ 10000、千分比范围、Favorable 方向约束；调整：`|d| ≤ 2^50`，`reason` 匹配原因码正则，`note` ≤ 500 字符并去控制字符 |
| 幂等与重放 | 调整与规则移除以 (caller, key) 唯一；同键不同参数 → `kernel.idempotency_key_reused`；重算以 `recalc:<job>:<user>` |
| 审计 | `accounting.adjust`（含 before/after 总量、reason、note）、`accounting.rate_rule.create/end`（管理员手工）、`accounting.recalc.create/apply`、`accounting.reconcile.fix`、`accounting.stream_gap.ack` |
| 越权防护 | `remove_rate_rule` 只能移除 `owner_plugin = caller_plugin` 的规则；promotion 无法改动 shop 的个人规则 |
| Redis | 只访问 `acct:*`、`u:*:live`；ACL 由部署模板约束（accounting 账号对 acct 实例：`~acct:* ~u:*:live +@stream +hincrby +hget +hset +exists +evalsha +script|load +time +xinfo`） |
| 资源滥用 | `/swarm-stats` 每次 ≤ 100 个；`snatches` 列表 limit ≤ 100；限流见 §2.4 |
| 隐私删除 | §1.12 purge |

## 7. 性能设计

### 7.1 热路径

| 环节 | 设计 | 预期 |
|---|---|---|
| XREAD | 每次 ≤ 5000 条，平均每分区 265 条/秒，2 s 一批约 530 条 | Redis RTT 主导，< 5 ms |
| 解析与聚合 | 零拷贝解析 RESP，整数直接解析；HashMap 预分配 | < 1 µs/条 |
| 倍率 | 进程内索引，O(命中规则数) | < 0.5 µs/条 |
| COPY | 二进制 COPY（`copy_in` 的 CSV 也可，实测择优）| 5 万行/s/连接 |
| upsert | 按键排序；`peers` fillfactor 70 便于 HOT（更新列不在索引中：`last_announce_at`、槽、`is_active`、`is_seeder` 均无索引） | 单批 530 条 ≈ 20～40 ms |
| 提交 | 每分区约 0.5 tx/s，全站约 32 tx/s | |

### 7.2 数据库写入预算

| 来源 | 平均行/秒 | 高峰行/秒 |
|---|---|---|
| peers upsert | 17,000 | 51,000 |
| snatches（传输） | 2,500 | 7,500 |
| settle_buffer + torrent_user_hourly | 5,000 | 15,000 |
| user_totals + user_daily | 3,000 | 9,000 |
| 小时折叠（snatches + users，集中在每小时前 30 分钟） | 摊销 8,500，执行时 17,000 | 同 |
| 窗口关闭（traffic_segments 写、settle_buffer 删） | 摊销 5,000 | |
| **合计** | **≈ 3.5 万** | **≈ 9 万（高峰与折叠重叠时）** |

缓解与开关：① 高峰期折叠任务限速（`snapshot.max_rows_per_sec`，默认 2 万）；② `torrent_user_hourly` 可关闭（同时关闭交叉校验）；③ 必要时把 `peers` 迁到独立 PG（插件 schema 不跨库是平台约束，需评审）或改用 DD-ACC-6 的后备方案 A。**以上数字为估算，必须在 P2 记账链路压测中验证（design/09 待验证项）。**

### 7.3 事件量

| 事件 | 平均条/秒 | 平均载荷 | 每日体量 |
|---|---|---|---|
| `traffic.settled`（W=900） | ≈ 70（约 6 万用户/窗口有传输） | ≈ 0.8 KB | ≈ 5 GB |
| `traffic.seeding_snapshot_taken` | ≈ 70（25 万/小时，整点后 30 分钟内发完，峰值 ≈ 140） | ≈ 5 KB（平均 80 个种子） | ≈ 30 GB |
| 其他 `traffic.*` | < 30 | < 1 KB | < 1 GB |

`ev:traffic.seeding_snapshot_taken:<p>` 的 Redis 流按默认 `MAXLEN ~ 1,000,000`/分区 × 16 分区会占用约 80 GB——**不可接受**，必须按类型设置（建议 `stream_maxlen = 200000`，约 4 小时余量 × 16 分区 ≈ 16 GB；或降低至 50000）。与事件日志保留期一并列入 HLD §7 N-2，需内核支持按类型配置 `stream_maxlen`（site.toml `[events.stream_maxlen]`）。

### 7.4 读路径

- `user_totals`：主键查询 + 一次 Redis HMGET；短缓存 10 s（仅 HTTP 层本人统计）。
- `swarm_stats` 批量：主键 `= ANY($1)`。
- 完成者列表：`snatches_torrent_completed_idx`（跨 32 个哈希分区的索引扫描 + 归并，limit 50）。
- `seeding_now`：`peers` 主键前缀 `user_id`（落在单个哈希分区）。
