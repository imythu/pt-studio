## 1. 设计目标与原则

1. **恰好一次**：流游标、业务写入、领域事件三者同一事务提交；Redis 侧副作用（扣减实时计数、修剪流）全部可重复执行。
2. **热路径最少写**：每条条目只必然产生一次“活跃 peer”upsert；只有真正有传输的条目才写 snatch、用户总量与结算缓冲；纯做种时长按小时折叠。
3. **按用户分区、无跨分区锁**：分区 p 只处理 `user_id % N = p` 的用户，所有按用户的表在不同 worker 之间天然不冲突；按种子共享的计数用“分区维度拆行”或“排序加锁”避免死锁。
4. **按流时间划分窗口**：窗口与小时边界用 Stream ID 的时间判定（单分区单调），保证重放结果确定；announce 的 `ts` 只用于速度等信号计算。
5. **机制在此、策略在外**：倍率规则由 promotion/shop 等写入，本插件只存储、合并、应用；信号只陈述事实，判定交给 anticheat。
6. **不碰敏感数据**：IP、端口在解析时丢弃；UA 只用于指纹比对，不落库原文。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
 pt-tracker ×M ──XADD acct:<p>──►  Redis(acct)  ◄──HINCRBY u:<uid>:live── pt-tracker
                                      │  ▲
                        XREAD(游标)   │  │ XTRIM MINID / Lua 扣减 live
                                      ▼  │
 ┌───────────────────────── pt-server 副本 ×R（内核 + Native 插件）─────────────────────────┐
 │ 内核 worker 调度：分区租约 k:lock:wrk:accounting:ingest:<p>  ──► accounting.ingest.poll(p) │
 │                                                                                          │
 │ accounting                                                                               │
 │  ingest ─► aggregate ─► rates ─► signals ─► store(COPY→stage→ON CONFLICT, 游标, outbox)   │
 │  windows（窗口关闭→traffic.settled） snapshot（小时→seeding_snapshot）                    │
 │  swarm（5 min→swarm_stats_updated）  maintenance（ghost/对账/归档/重算）                   │

 └──────────────────────────────────────────────────────────────────────────────────────────┘
          │ PostgreSQL schema accounting             │ 事件 outbox → ev:traffic.*:<p>
          ▼                                          ▼
   peers / snatches / user_totals / …       bonus / hnr / levels / ratio-policy / anticheat / search
          ▲

```

### 2.2 内部模块

| 模块 | 职责 |
|---|---|
| `ingest` | 分区 worker 入口：读游标、`XREAD` 读条目、解析校验、`eid` 去重、组装微批、调用后续模块、提交 |
| `aggregate` | 微批内按 (user, torrent)、(user, torrent, peer)、(torrent, hour) 合并增量 |
| `rates` | 倍率规则存储、进程内索引（global / torrent / user / user_torrent）、按流时间求有效倍率、版本广播 |
| `signals` | 条目级信号（速度、计数异常、无对端、客户端指纹）与小时级交叉校验；去重、持久化、发布 |
| `store` | COPY 到分区暂存表 → `INSERT … SELECT … ON CONFLICT` 合并到正式表；游标 CAS；完成数计数 |
| `live` | `u:<id>:live` 读取与幂等扣减（Lua，按分区游标判重） |
| `windows` | 结算缓冲与窗口关闭：按水位关闭窗口，按用户组装并发布 `traffic.settled` |
| `snapshot` | 小时快照：读取活跃 peer 的小时做种槽，发布 `traffic.seeding_snapshot_taken`，折叠做种时长到 snatch / 总量 / 每日表 |
| `swarm` | 周期计算 swarm 统计，与上次结果比较，发布变化项 |
| `mirror` | 种子镜像（体积、状态）；用户删除处理 |
| `maintenance` | ghost peer 清理、流修剪与缺口检测、对账、归档、重算、重建 |
| `service` | `ctx.accounting` 实现 |
| `http` / `mcp` / `ui` | 路由、MCP 工具、前端插槽 |

## 5. 关键流程

### 5.1 微批落库（恰好一次）

```
worker(p)                               Redis acct                PostgreSQL（一个事务）
  │ 读游标 c, fence（SELECT … FOR UPDATE）                            │
  │── XREAD COUNT k BLOCK t STREAMS acct:p c ─►│                       │
  │◄─ 条目[] ────────────────────────────────── │                       │
  │ 解析/去重/聚合/求倍率/信号                                         │
  │── COPY stage_peers/stage_snatch/stage_settle … ──────────────────►│
  │── INSERT … SELECT … ON CONFLICT（peers, snatches, user_totals, user_daily, settle_buffer, torrent_hourly, torrent_counters, signals）►│
  │── 关闭已越过水位的窗口 → events.publish(traffic.settled …)        │
  │── UPDATE stream_cursors SET last_id=新 WHERE part=p AND last_id=c AND fence=f ─► 1 行？
  │── COMMIT（含 outbox）────────────────────────────────────────────►│
  │── EVALSHA live_deduct（按 user、带分区游标）、XTRIM MINID、XGROUP SETID ─►│（失败只告警，下批重试）
```

### 5.2 窗口与小时边界

- 窗口 `[k·W, (k+1)·W)` 按流时间划分。worker 在每次提交时检查本分区水位：若水位 ≥ 窗口结束 + `settle_grace_secs`，则在**同一事务**中关闭该分区该窗口（读取并删除 `settle_buffer` 中该分区该窗口的行，按用户发布事件）。
- 小时快照需要全部分区越过整点：cron `seeding_snapshot` 读取 `stream_cursors` 的最小水位，未越过则本次退出（下分钟由 `catch_up`/下次触发重试；最晚到 h+1:55 仍未越过则对落后分区告警并照常发布，迟到数据计入下一小时）。

### 5.3 倍率规则写入

```
promotion ──ctx.accounting.set_rate_rule(rule{external_ref, …})──► service
   service: 校验作用域 write:rates → upsert rate_rules（唯一键 owner_plugin+external_ref）→ 写 targets
            → INCR p:accounting:rate:ver（提交后）→ 返回 rule_id
各副本 rates 模块：每个微批开始时 GET rate:ver（与本地版本不同 → 增量加载 updated_at > 上次）
```

### 5.4 swarm 统计

```
cron swarm_stats：for bucket in 0..64（按 torrent_id % 64）：
    SELECT torrent_id, 做种者数, 下载者数 FROM peers WHERE active AND torrent_id % 64 = bucket … GROUP BY
    与 swarm_stats 比较 → 变化项（含 completed 来自 torrent_counters）
    UPDATE swarm_stats；每 1000 项 publish traffic.swarm_stats_updated；sql.commit()
```

### 5.5 重算

```
管理员 POST /admin/recalcs {rule_id, corrected_up, corrected_down | void, dry_run}
 → recalc_jobs(pending) → 延迟任务 recalc_step：
     按 user 分批：从 traffic_segments 中 rate_key 含 rule_id 的行，用“更正后的规则集”重算倍率
     差额 = Σ(新计入 − 旧计入) → recalc_items（预览）
 → 确认执行：逐用户 adjust(…, idempotency_key = "recalc:<job>:<user>")，记录进度，可中断续跑
```

## 6. 设计决策

| 编号 | 问题 | 备选方案 | 结论 | 理由 |
|---|---|---|---|---|
| DD-ACC-1 | 长驻流消费者如何运行 | A 内核新增“分区 worker”扩展点（租约分配，内核循环调用 `poll`）；B 每分钟 cron 内循环 55 s；C 插件在 `init` 中自建 tokio 任务 | A；未合入前用 B 降级 | C 违反 coding.md §2.3（插件不得自建线程/运行时）且无租约、无优雅关闭；B 只有一个副本执行、吞吐受限；A 复用内核事件消费的租约与再平衡机制，每次 `poll` 是一个工作单元，符合“一次调用一个事务” |
| DD-ACC-2 | 恰好一次的游标存哪里 | A 消费组 + XACK；B PG 游标与业务同事务 | B；消费组 `accounting` 仅作为镜像（提交后 `XGROUP SETID`）供监控 | XACK 与 PG 提交无法原子；PG 游标 + CAS + fencing token 天然恰好一次；重放只需把游标改回 |
| DD-ACC-3 | 窗口依据 | A announce `ts`；B Stream ID 时间 | B | 单分区单调、重放确定；`ts` 来自多个 tracker 节点，有时钟偏差与迟到 |
| DD-ACC-4 | 倍率表示与合并 | A 浮点；B 千分比整数，favorable（上传取最大、下载取最小）+ override | B | 金额/流量禁止浮点（database.md §4）；favorable 语义与 UNIT3D 一致、对用户可预期；override 用于惩罚（个人 0x）与特殊活动 |
| DD-ACC-5 | `traffic.settled` 的粒度与内容 | A 每微批每用户；B 每窗口每用户，含全部种子；C 每窗口每用户，只含传输活动 | C，W 默认 900 s | A 每秒数千条事件压垮事件日志与各订阅者 inbox；B 的纯做种项占 90% 以上体量；做种时长由小时快照承载（bonus、hnr 用快照即可） |
| DD-ACC-6 | 活跃 peer 与 swarm 统计（Q13） | A pt-tracker 写 `trk:stats:*`；B accounting 依据流维护 PG `peers` 表并周期聚合 | B（保留 A 作为后备） | 几乎每次 announce 都有非零 `dseed`/`dleech`，流足以判断存活；PG 表同时服务 `seeding_now`、快照、无对端信号；A 需要 pt-tracker 汇总跨节点 swarm，而 swarm 只在负责该 info_hash 的节点上，作为后备 |
| DD-ACC-7 | 做种时长何时写入 snatch | A 每条条目；B 写入 peers 的小时槽，整点折叠 | B | 纯做种条目约占九成，B 使 snatch/user_totals 的写入降到“传输活动 + 每对每小时一次” |
| DD-ACC-8 | 小时槽的清零 | A 快照后 UPDATE 清零；B 双槽交替（槽 = 小时 % 2，带小时标签，写时按标签判断覆盖或累加） | B | 不产生 3000 万行/小时的清零写入；代价是快照必须在下一小时内完成，超时则该小时做种数据丢失（告警） |
| DD-ACC-9 | 跨分区共享计数（完成数、种子平衡） | A 单行累加；B 按分区拆行，读时汇总 | 完成数用 A（按 torrent_id 排序加锁，冲突少）；种子小时平衡用 B | 热门新种的完成事件集中但每批每种子只一行；平衡数据每条传输条目都写，必须拆行 |
| DD-ACC-10 | 批量写入方式 | A UNNEST 数组；B COPY 到 UNLOGGED 暂存表再 ON CONFLICT | B（D2 原定方案） | COPY 吞吐最高；暂存表按分区号 LIST 分区，各 worker 互不干扰；UNLOGGED 免 WAL，事务回滚即丢弃 |
| DD-ACC-11 | 实时计数的结算扣减 | A HINCRBY 负数；B 记录已落库原始量，展示时相减；C Lua 按分区游标判重后扣减 | C | A 不幂等；B 在键过期重建后错乱；C 每个用户只属于一个分区，游标单调，可精确判重 |
| DD-ACC-12 | 倍率更正 | A 回写历史 snatch；B 以调整记录补差 | B | 只追加、可审计；下游（bonus、levels）通过 `traffic.adjusted` 感知 |
| DD-ACC-13 | IP 处理 | A 申请 `peer.ip` 做同 IP 检测；B 解析时丢弃 | B | 同 IP 多账号检测属于 anticheat 判定范畴，anticheat 经授权从 `ctx.tracker.peers()` 获取；accounting 保持无敏感数据 |
| DD-ACC-14 | 流修剪 | A 只靠 pt-tracker 的 MAXLEN；B accounting 落库后 `XTRIM MINID`，MAXLEN 作安全上限 | B | 正常情况下流只保留未消费积压 + 15 分钟余量，内存可控；MAXLEN 修剪导致的缺口可检测 |

## 7. 对平台契约的新增

| # | 类别 | 内容 | 理由 |
|---|---|---|---|
| N-1 | 内核扩展点（plugin-api §3、§4；kernel/03 新增一节） | Native 插件“分区 worker”：清单 `[[workers]] name, shards（数或配置键引用）, lease_secs, tx = "auto"`；内核为每个 (插件, worker, shard) 维护租约 `k:lock:wrk:<plugin>:<name>:<shard>`（分配算法同事件消费 §7.4），持有期间循环调用 `trait PartitionWorker { async fn poll(&self, ctx: &Ctx, shard: u32, fence: u64) -> PResult<PollOutcome> }`（`PollOutcome::{Busy, Idle{sleep_ms}}`），每次 `poll` 是一个工作单元；优雅关闭时等待当前 `poll` 结束；Redis 键前缀 `k:lock:wrk:` 登记到 redis-keys.md | DD-ACC-1；tracker-bridge 若需消费流也可复用 |
| N-2 | 事件日志保留（kernel/03 §7.1、site.toml） | 允许按事件类型设置日志保留期：`[events.log_retention_days] "traffic.*" = 30`；`kernel.event_log` 需改为日分区或对大类型使用单独的日分区表；同时允许按类型设置 Redis 事件流长度 `[events.stream_maxlen] "traffic.seeding_snapshot_taken" = 200000` | `traffic.settled`、`traffic.seeding_snapshot_taken` 合计每日约 3000～4000 万条、数十 GB（LLD §7.3），默认 24 个月保留不可承受 |
