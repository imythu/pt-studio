## 1. 引言

### 1.1 目的

本文定义 `accounting` 插件（Native，提供 `ctx.accounting`）的功能与非功能需求。accounting 是 pt-tracker 产出的原始流量与 PT 业务之间唯一的桥梁：它消费 `acct:<partition>` 流，按窗口聚合、应用流量倍率、以“恰好一次”语义落库，维护 snatch、用户总量、活跃 peer 与种子 swarm 统计，计算反作弊基础信号，并以领域事件把结算结果交给 bonus、hnr、levels、ratio-policy、anticheat、search-meilisearch 等下游插件。

### 1.2 范围

| 包含 | 不包含 |
|---|---|
| 消费 pt-tracker 写入的 `acct:<partition>` 流（格式以 design/10 §5.4 为准） | announce 处理、增量计算本身（pt-tracker） |
| 微批聚合、COPY + `ON CONFLICT` 落库、流游标与落库同事务（恰好一次） | 促销策略（“什么时候免费”由 promotion 决定，accounting 只存储并应用倍率规则） |
| 倍率规则的存储、缓存、按时间应用；`set_rate_rule` / `remove_rate_rule` 服务（平台 Q2） | 魔力值、H&R、等级、分享率规则的判定（各自插件订阅事件处理） |
| snatch（用户×种子）、用户总量、每日统计、活跃 peer、种子 swarm 统计（平台 Q13） | 作弊判定与处置（anticheat） |
| 事件：`traffic.settled`、`traffic.seeding_snapshot_taken`、`traffic.snatch_completed`、`traffic.adjusted`、`traffic.signal_raised`、`traffic.swarm_stats_updated` | peer 列表与 peer IP（tracker-bridge 的 `ctx.tracker.peers()`） |
| 反作弊基础信号的计算、去重、存储与查询 | 用户状态变更、封禁 |
| 手工调整流量（`adjust`）、分区与归档、对账、重算（倍率更正）、从每日表重建用户总量 | 账本与货币（ledger） |
| 前端：用户资料统计、做种/下载记录、种子列表做种数列、完成者列表、后台流量页 | |

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 流 / 分区 | Redis Stream `acct:<p>`，`p = user_id % N`，N 全站固定（默认 64，部署后不可改） |
| 条目（entry） | 流中的一条记录，对应一次 announce 产生的增量，字段见 design/10 §5.4 |
| 流时间 | 条目 Stream ID 的毫秒时间部分（XADD 时刻），单分区内单调递增；本插件所有“窗口”都按流时间划分 |
| 微批 | worker 一次读取并在一个数据库事务中落库的一组条目（默认 ≤ 10,000 条或 ≤ 2 s） |
| 游标 | 每个分区已落库的最后一个 Stream ID，保存在 PostgreSQL，与业务数据同事务提交 |
| 水位（watermark） | 某分区“流时间已确定推进到”的时间点：分区有积压时为游标时间；分区读空时为读空时刻 |
| 结算窗口 | `traffic.settled` 的聚合周期 W（默认 900 s，须整除 3600） |
| 原始量 / 计入量 | `raw`：tracker 上报的增量；`credited`：乘以倍率后的计入量 |
| 倍率（permille） | 千分比整数：1000 = 1x，0 = 免费，2000 = 2x，500 = 50% |
| snatch | 用户与种子的关系记录（参与过即建立），含上传、下载、做种/下载时长、完成时间、最后活动 |
| 活跃 peer | 最近 `peer_timeout_secs` 内 announce 过、且未 stopped 的 (user, torrent, peer_id) |
| ghost peer | 客户端未发 stopped 即消失的 peer（UNIT3D 术语），超时后被清理 |
| 信号 | 反作弊基础事实，如速度超限、无对端上传；不含判定 |
| 重算 | 倍率规则更正后，按留存的分段明细重新计算计入量，并以调整记录补差 |

## 2. 总体描述

### 2.1 插件定位

| 项 | 内容 |
|---|---|
| 类型 | Native（热路径，需要 `copy_in`、`redis_global`、进程内缓存与长驻分区 worker） |
| 提供服务 | `ctx.accounting@0.1.0` |
| 依赖服务 | 无强依赖；`optional_requires = ["ctx.torrents@^0.1"]`（只在补齐种子镜像时使用，通常读视图） |
| 只读视图 | `torrent.v_torrent_public`（种子体积、状态，用于镜像初始化与对账） |
| 全局 Redis | `acct` 实例：`acct:*`（rw，消费与修剪）、`u:*:live`（rw，结算后扣减） |
| 对外视图 | `accounting.v_user_totals`、`accounting.v_snatch`（已在 services.md §3 登记） |

### 2.2 用户角色与使用场景

| 角色 | 场景 |
|---|---|
| 普通用户 | 在个人资料看到上传量、下载量、分享率、做种时间（秒级实时）；查看自己做种中、下载中、已完成、未完成的种子；通过 MCP 问“我现在做种多少个”“哪些资源需要保种” |
| 任意访客（已登录） | 在种子列表看到做种数 / 下载数 / 完成数；在种子详情页看完成者列表 |
| 下游插件 | bonus 订阅 `traffic.seeding_snapshot_taken` 发魔力值；hnr 订阅 `traffic.settled`、`traffic.snatch_completed` 考核；levels、ratio-policy 读 `user_totals`；promotion 调 `set_rate_rule`；shop 调 `adjust`（兑换上传量）；anticheat 订阅 `traffic.signal_raised`、调 `signals`；search-meilisearch 订阅 `traffic.swarm_stats_updated` |
| 版主 | 查看他人流量明细、基础信号 |
| 管理员 | 手工调整流量；查看倍率规则；发起重算；查看对账差异与流水线延迟 |
| 运维 | 观察消费延迟、积压、落库耗时；处理流缺口告警 |

### 2.3 现有开源 PT 程序的做法调研

| 项目 | 做法 | 优点 | 缺点 | 我们采纳 | 我们改进 |
|---|---|---|---|---|---|
| NexusPHP | announce.php 中每次请求直接 `UPDATE users SET uploaded=uploaded+…`、`UPDATE snatched …`、`peers` 表增删；促销倍率在 announce 中按 `torrents.sp_state` 与全站促销计算；`check_cheater()` 在 announce 内同步判定 | 逻辑直观，数据实时 | 每次 announce 多次写库，大站数据库成为瓶颈；作弊判定与记账耦合在热路径；倍率规则写死在代码里 | snatch 表的字段设计（上传、下载、做种/下载时长、完成时间、最后动作时间）；按 (user, torrent, 规则) 在 24 h 内只记一条并累计 `hit` 的信号去重 | 热路径不写库，改为流 + 微批；判定移到 anticheat；倍率为可存储、有生效期、可追溯的规则 |
| UNIT3D + UNIT3D-Announce | Rust 外挂 announce 进程在内存中维护 peers/history 变更队列，按 (user_id, torrent_id) 合并 `uploaded_delta`、`credited_uploaded_delta` 等后定期批量 upsert；倍率按“全站/组/种子/个人免费令牌”多层取上传最大、下载最小；peer 设 `is_active`，超时置 inactive，再超时删除（清理 ghost peer） | 批量写入吞吐高；原始量与计入量分别存储；倍率合并规则清晰 | 队列只在内存中，进程崩溃丢失未刷盘的增量；记账与 tracker 在同一进程，无法独立扩展；没有严格的恰好一次 | 原始量 + 计入量双列；倍率取“上传最大 / 下载最小”的合并语义；`is_active` 两阶段清理 ghost peer | 增量先进 Redis Stream，游标与落库同事务，崩溃可重放且不重复；记账 worker 可按分区水平扩展 |
| Gazelle / OPS（Ocelot） | Ocelot 在内存中累积用户与种子的增量，定时 `flush_users/flush_torrents/flush_snatches/flush_peers` 批量写入 `users_main`、`torrents`、`xbt_files_users`、`xbt_snatched`；启动时清空 `xbt_files_users` 并重置做种数 | 刷盘批处理成熟；swarm 统计（Seeders/Leechers/Snatched）由 tracker 回写 | 刷盘前崩溃丢数据；做种数依赖 tracker 进程内状态，重启时归零 | 定时批量刷盘、swarm 统计周期回写 | 做种数由 accounting 依据持久化的活跃 peer 计算，重启不归零；只发布变化了的种子 |
| Luminance / TorrentPier | 与 Gazelle / NexusPHP 类似，announce 直接写库或简单批处理；TorrentPier 有 `bt_tracker` 内存表与定时 cron 汇总 | 实现简单 | 同上，扩展性受限 | — | — |
| Arcadia | Rust 新项目，tracker 与后端分离，仍在早期 | 方向与我们一致 | 未成熟、AGPL | 只参考方向 | — |
| TU Wien 研究 | 利用 swarm 内上传总量 ≈ 下载总量的守恒关系，结合速度、做种者/下载者数量识别虚报 | 不依赖客户端指纹，难以规避 | 需要按种子、时间段聚合全体用户数据 | 输出 `cross_check_mismatch` 信号：按种子按小时比较全体用户的原始上传与下载，超额部分归因到上传占比最高的用户 | 只输出信号与证据，判定交给 anticheat |

### 2.4 约束与假设

1. 输入格式以 design/10 §5.4 为准：`v=1`，字段 `eid, ts, uid, tid, ih, pid, ip, port, ev, up, down, left, dup, ddown, dseed, dleech, flags, ua`；flags 位：bit0 first_seen、bit1 baseline_reset、bit2 upload_regressed、bit3 download_regressed、bit4 first_completed、bit5 seed_time_capped。
2. 同一用户的条目总在同一分区，分区内按 Stream ID 有序；pt-tracker 保证“先写状态再 XADD”，不会重复记账，但 XADD 超时重试可能写入重复条目（以 `eid` 去重）。
3. 增量已由 pt-tracker 计算，accounting **不重新计算增量**，只做聚合、倍率、落库、统计与信号。
4. 规模：30 万用户、约 3000 万 peer、announce 平均 1.7 万次/秒、高峰 2～3 倍（design/03 §3）。几乎每次 announce 都有非零 `dseed` 或 `dleech`，因此 `emit_zero_delta=false` 只减少极少量条目——平台 Q13 担心的“无增量 announce 不产生事件”对 peer 存活判断影响很小（见 HLD DD-ACC-6）。
5. Native 插件与内核同进程；平台 Q1 的 SET ROLE 加固同样适用于本插件的 SQL。
6. 本插件需要一个由内核托管的“分区 worker”扩展点（见 HLD §7 N-1）；在该扩展点合入前，以每分钟 cron + 租约的降级方案运行（吞吐受限，只用于开发与小站）。
7. 不读取、不持久化 peer IP 与端口（流中虽有该字段，解析时即丢弃），也不把 User-Agent 原文写入事件。

## 3. 功能需求

| 编号 | 名称 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-ACC-001 | 分区消费 | 对 N 个 `acct:<p>` 分区各由一个持有租约的 worker 串行消费；副本增减时分区自动再平衡 | P0 | 3 副本运行时每个分区恰有一个消费者；停掉一个副本，其分区在租约过期（≤ 30 s）后被其他副本接管 |
| FR-ACC-002 | 条目解析与校验 | 按 `v` 解析条目；字段缺失、类型错误、未知版本的条目写入隔离表并计数，不阻塞分区 | P0 | 注入非法条目后分区继续推进，隔离表有记录，指标 `entries_rejected_total` 增加 |
| FR-ACC-003 | 重复条目去重 | 同一分区内 `eid` 重复的条目只计一次（XADD 重试导致） | P0 | 构造两条 eid 相同、ID 不同的条目，落库量只计一次 |
| FR-ACC-004 | 微批聚合 | 每次读取 ≤ `batch_max_entries` 条或 ≤ `batch_max_ms`，在内存中按 (user, torrent) 与 (user, torrent, peer) 合并后一次落库 | P0 | 同一微批内同一 (user, torrent) 的多条增量在 snatch 中只产生一次 upsert，且合计正确 |
| FR-ACC-005 | 恰好一次落库 | 游标与全部业务写入、事件 outbox 在同一事务提交；游标更新带期望旧值与租约 fencing token 检查，失败则整批回滚 | P0 | 在提交前后任意点杀进程并重启，`user_totals`、`snatches` 与参考计算完全一致；两个 worker 争用同一分区时只有一个能提交 |
| FR-ACC-006 | 倍率应用 | 对每条条目按其流时间、user、torrent 求有效倍率（合并规则见 FR-ACC-021），计入量 = 原始量 × 倍率 / 1000（向下取整） | P0 | 免费种子下载计入量为 0；2x 种子上传计入量为原始 2 倍；规则生效边界按流时间精确切换 |
| FR-ACC-007 | snatch 维护 | 维护 (user, torrent) 的原始/计入上传下载、做种/下载时长、首次与最后活动时间、完成时间、完成次数、当前状态（做种中/下载中/不活跃） | P0 | 与参考实现对比 1 万条随机条目，snatch 各字段一致 |
| FR-ACC-008 | 完成记录 | 收到 `first_completed` 位且该 snatch 无完成时间时记录完成时间，发布 `traffic.snatch_completed`，并累加种子完成数；同一用户同一种子只发布一次 | P0 | 同一用户多个 peer_id 先后 completed 只产生 1 条事件；完成数 +1 |
| FR-ACC-009 | 用户总量 | 维护每用户原始/计入上传下载、做种/下载时长、手工调整合计；提供 `ctx.accounting.user_totals` 与视图 `v_user_totals` | P0 | `user_totals` 与该用户 snatch 合计 + 调整合计一致（对账通过） |
| FR-ACC-010 | 实时计数对接 | 读取 `u:<id>:live` 展示实时原始量；每次落库后按已落库的原始量扣减实时计数，扣减按分区游标幂等 | P0 | 重复执行同一批扣减不会重复扣；`user_totals` 的 `live_*` 字段 = 已结算计入量 + 未结算原始量 |
| FR-ACC-011 | 活跃 peer | 维护活跃 peer 表（不含 IP）；stopped 置为不活跃；超过 `peer_timeout_secs` 未 announce 的置为不活跃（ghost），再超过 `peer_purge_secs` 删除 | P0 | stopped 后做种数 5 分钟内减少；客户端直接断网，`peer_timeout_secs` 后不再计入做种数 |
| FR-ACC-012 | swarm 统计 | 每 `swarm_stats_interval_secs`（默认 300）计算各种子 seeders、leechers、completed，只对有变化的种子发布 `traffic.swarm_stats_updated`（平台 Q13） | P0 | 统计与活跃 peer 表一致；无变化的种子不出现在事件中；单条事件 ≤ 1000 项、≤ 64 KiB |
| FR-ACC-013 | 结算事件 | 每个结算窗口 W 结束后，按用户发布 `traffic.settled`：包含该窗口内有传输活动（上传、下载或下载时长非零，或有完成）的种子明细；纯做种时长不进入本事件（由快照事件承载） | P0 | 每用户每窗口至多一条（超 64 KiB 时拆分并带 `batch_id/part/parts`）；重放同一窗口不会重复发布 |
| FR-ACC-014 | 做种快照事件 | 每小时整点后（全部分区水位越过整点），对上一小时有做种的用户发布 `traffic.seeding_snapshot_taken`：各种子体积、该小时做种秒数、当前做种者数 | P0 | 用户在该小时做种 40 分钟的种子 `seed_secs≈2400`；一小时内只发布一次 |
| FR-ACC-015 | 速度信号 | 单条增量对应的上传速度 > 阈值（全站配置，按客户端可分档）时产生 `speed_exceeded`；严重度按超出倍数分级 | P0 | 构造 2 GB / 10 s 的上传条目，产生 severity=high 信号 |
| FR-ACC-016 | 计数异常信号 | `upload_regressed` / `download_regressed` → `negative_delta`；`baseline_reset` 且非 started、单次增量超过种子体积 × `jump_size_factor`、`left` > 种子体积 → `counter_jump` | P0 | 每种情况各产生一条对应信号，details 给出原因 |
| FR-ACC-017 | 无对端信号 | 用户在某种子上报上传增量，但该种子在该时段没有任何活跃下载者（含本用户自己的 leecher peer 除外）时产生 `peer_not_in_swarm` | P1 | 种子只有做种者时上报上传，产生信号；有下载者时不产生 |
| FR-ACC-018 | 交叉校验信号 | 每小时按种子汇总全体用户原始上传与原始下载；上传超出下载 × (1 + 容差) + 余量时，把超额按上传占比归因到前 K 名上传者，产生 `cross_check_mismatch` | P1 | 构造 1 个用户虚报 10 GB、全体下载 1 GB 的种子，该用户收到信号且 details 含种子总量与其占比 |
| FR-ACC-019 | 客户端异常信号 | peer_id 前缀与 User-Agent 指纹不一致、或同一 peer 会话中途更换客户端指纹时产生 `client_not_allowed`（details.kind 区分） | P2 | 构造 peer_id `-qB4630-` + UA `Transmission/4.0` 的条目，产生信号 |
| FR-ACC-020 | 信号去重与存储 | 同一 (user, torrent, signal) 在 `signal_dedupe_secs`（默认 24 h）内只发布一次事件，其余累加 `hits` 与证据；严重度升级时再次发布；信号存储可按用户、时间查询 | P0 | 同一种子 100 次超速只发布 1 条事件，记录 hits=100；严重度由 medium 升到 high 时补发 1 条 |

| FR-ACC-024 | 查询服务 | `user_totals`、`user_totals_many`、`snatches_of_user`（可按状态过滤）、`snatches_of_torrent`、`seeding_now`、`swarm_stats`、`signals` | P0 | 各方法返回值与数据库一致；分页使用游标 |
| FR-ACC-025 | HTTP API | 用户：本人统计、snatch 列表、种子 swarm 统计（批量）、完成者列表、需要保种的种子；后台：他人统计、信号、调整、倍率规则、重算、对账差异、流水线状态、站点概况 | P0 | OpenAPI 与清单一致；权限检查生效 |

| FR-ACC-036 | 站点概况 | 站点总上传/下载、今日增量、活跃用户数、活跃 peer、做种者/下载者、种子数，供后台与 `admin_site_stats` | P2 | 数值与底表聚合一致，缓存 ≤ 60 s |

| FR-ACC-038 | 流水线状态 | 每分区的游标、水位、积压条数、最近提交耗时、租约持有者；后台页与指标可见 | P1 | 后台页显示 N 个分区状态，与 `XINFO STREAM` 一致 |

## 4. 非功能需求

| NFR-ACC-001 | 吞吐 | 持续消费平均流量与高峰流量 | 平均 1.7 万条/秒，高峰 5.1 万条/秒持续 30 分钟，积压在高峰结束后 10 分钟内消化完 |

## 6. 外部接口需求概述

- **输入流**：`acct:<p>`（acct 实例，pt-tracker 写入）；`u:<id>:live`（读取、结算扣减）。
- **服务**：`ctx.accounting`（方法见 FR-ACC-021～024，正式 WIT 见 LLD §2.1）。
- **事件发布**：`traffic.settled`、`traffic.seeding_snapshot_taken`、`traffic.snatch_completed`、`traffic.adjusted`、`traffic.signal_raised`、`traffic.swarm_stats_updated`。
- **事件订阅**：`torrent.created`、`torrent.status_changed`、`torrent.deleted`、`user.deleted`。
- **HTTP**：`/api/p/accounting/v1/…`（LLD §2.4）。
- **MCP**：`get_my_stats`、`list_my_seeding`、`list_torrents_needing_seeders`、`admin_get_user_traffic`、`admin_site_stats`。
- **前端**：见 FR-ACC-027。
- **视图**：`accounting.v_user_totals`、`accounting.v_snatch`。
