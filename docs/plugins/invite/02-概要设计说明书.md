## 1. 设计目标与原则

1. **钩子内只预留，事件中确认**：`user.before_register` 处理者的写入会独立提交（kernel/03 §5.2），因此钩子中只写“带 TTL、以用户名为持有者、可重入”的预留；兑换、计数、邀请树边全部在 `user.registered` 订阅中完成（与 identity HLD §5.1 一致）。
2. **额度单一事实来源**：余额 = 未过期额度批次剩余之和，不维护计数列；所有变动写只追加流水，可对账（SRS NFR-INV-009）。
3. **邀请码不落明文**：库中只存 SHA-256；码由 `HMAC(code_key, 签发幂等键)` 派生（DD-INV-1），使幂等重放与（可选的）链接再次显示都不需要存储明文。
4. **策略外置**：等级、分享率、H&R 等发邀门槛由对应插件处理 `invite.before_issue`；本插件只检查自己的数据（状态、注册天数、暂停、上限、余额）。
5. **连坐由事件驱动、幂等、可撤销**：每个（触发事件, 规则, 目标）恰好一条处置记录；默认动作温和，强处置需站点授权。
6. **WASM 约束**：无内存状态；每次调用一个事务；钩子中不出站 HTTP；cron 与批处理分批 `sql.commit()`，游标存 kv，可断点续跑；跨插件副作用带 `<event_id>:<子键>` 幂等键。
7. **最小能力**：不申请 Redis、blob、出站 HTTP；敏感能力只有可选的 `user.email`（邮箱绑定精确比对）。

### 2.2 内部模块

| 模块 | 职责 |
|---|---|
| `codes` | 码派生（HMAC）、格式化（`INV-` + 26 位 Crockford Base32）、规范化、哈希、码尾 |
| `issue` | 发邀资格检查（FR-INV-002）、`invite.before_issue` 触发、扣额度、写邀请、绑定（邮箱 HMAC / 域名 / 用户名）、系统 / 活动码签发 |
| `redeem` | `user.before_register` 处理（校验 + 预留）；`user.registered` 确认（兑换、计数、树边、事件）；冲突检测 |
| `lifecycle` | 撤销、过期、返还、预留释放 |
| `quota` | 额度批次、FIFO 消耗、发放（等级晋升 / 周期 / 商城 / 管理员 / 初始 / 连坐返还）、扣减、流水、对账 |
| `tree` | 边表 + 闭包表维护；上游链、下游子树分页、计数；整树操作 |
| `penalty` | 连坐规则引擎：触发识别、条件过滤、动作执行、去重、撤销、复核；发邀权暂停 |
| `stats` | 用户统计、日汇总、问题邀请人评分 |
| `jobs` | cron 与延迟任务入口（过期、批次到期、周期发放、批量发放、整树操作、连坐通知、日汇总、对账） |
| `http` | 路由处理、请求校验、错误映射 |
| `mcp` | 3 个 MCP 工具 |
| `events` | 事件载荷构造（只含 ID、码尾，不含码与邮箱） |

## 4. 数据设计概要

| 实体 | 存储 | 说明 |
|---|---|---|
| 账户 `accounts` | PG | 每用户一行：已赠送过的晋升等级、行锁用于串行化同一用户的额度 / 发邀操作 |
| 邀请 `invites` | PG | 码哈希、码尾、类型、来源、邀请人、状态、用量、到期、绑定（邮箱 HMAC、域名、用户名）、签发幂等键哈希、扣用的批次 |
| 预留 `reservations` | PG | `(invite_id, holder)`、到期、状态 active/consumed/released |
| 兑换 `redemptions` | PG | 每个被邀请人一行（唯一），记录超额兑换 |
| 额度批次 `quota_lots` | PG | 来源、数量、剩余、到期 |
| 额度流水 `quota_ledger` | PG（只追加） | delta、原因、关联、变动后余额 |
| 幂等记录 `idempotency` | PG | 服务写方法的 `<caller>:<key>` → 结果 |
| 邀请树 `tree_edges` + `tree_closure` | PG | 边（被邀请人 → 邀请人）+ 闭包表（祖先、后代、深度），支持按深度分页 |
| 发邀权暂停 `suspensions` | PG | 来源（penalty/admin/tree_action）、到期、解除 |
| 连坐处置 `penalties` | PG | 规则、触发事件、被邀请人、目标、深度、计划与实际动作、状态 |
| 后台备注 `user_notes` | PG | 整树操作写备注 |
| 批处理任务 `batch_jobs` | PG | 批量发放 / 整树操作的参数、游标、进度 |
| 统计 `daily_stats`、`inviter_scores` | PG | 日汇总、问题邀请人评分 |
| 游标 | kv | `periodic:<period>:cursor` 等 |

## 5. 关键流程

### 5.1 发邀

```
POST /users/me/invites {email?, username?, expires_days?, note?, request_id?}
 → 鉴权 invite.send、限流 user:10/m
 → tx：
    SELECT accounts FOR UPDATE（不存在则 INSERT … ON CONFLICT DO NOTHING 后再锁）
    幂等：issue_key_hash = sha256("user:<uid>:" + request_id) 已存在 → 重新派生码并返回首次结果（200）
    资格检查（enabled、active、注册天数、暂停、未用上限、每日上限、余额；bypass 权限跳过后三项）
    hooks.run("invite.before_issue", {inviter_id, kind, source, class_id, outstanding, email_domain?, email_bound})
        deny → 返回处理者错误码（不扣额度）
    lot = 按 FIFO 锁定一个有剩余的批次，remaining - 1，写流水 (-1, reason=issue)
    code = encode(HMAC(code_key, "issue:user:<uid>:" + request_id)[0..16])
    INSERT invites(code_hash = sha256(code), code_hint, …, lot_id)
    publish invite.issued、invite.quota_changed
 → 201 {invite{id, code_hint, expires_at, …}, code, url}
```

`request_id` 缺省时由服务端生成随机 UUID（此时不可重放）。钩子触发发生在 invite 自己的事务中：处理者若写入，其副作用独立提交，但 `invite.before_issue` 的预期处理者（levels、ratio-policy、hnr）都是只读判断。

### 5.2 注册：钩子预留 → 事件确认

```
identity POST /users → hooks.run("user.before_register")
  registration-policy（priority 5）：开放 / 名额 / 域名 / 验证码 / 答题 …（只做持有者键控的预留）
  invite（priority 10）：
    无 invite_code → allow
    h = sha256(normalize(code))；holder = lower(nfc(username))
    tx：
      SELECT invites JOIN identity.v_user_public(inviter) WHERE code_hash = h FOR UPDATE OF invites
      不存在 / 非 active / 已过期 / 系统关闭且不允许兑换 / 邀请人不可用 → deny invite.code_invalid{reason}
      绑定：email（有则比对 HMAC）→ 否则比对域名（计降级指标）；username 绑定 → 不符 deny invite.binding_invalid
      others = COUNT(reservations WHERE invite_id AND state=active AND reserved_until > now AND holder <> $holder)
      use_count + others >= max_uses → deny invite.code_reserved
      UPSERT reservations(invite_id, holder) SET reserved_until = now + ttl, state = active
    → modify {attributes: {inviter_id}}（活动码且 campaign_inviter = none 时不设置）
  （其他处理者此后拒绝 → identity 不建号；本预留在 TTL 后释放；同一用户名重试可复用）
identity 事务：建号 + publish user.registered{user_id, username, invite_code, inviter_id, …}

invite on_user_registered（inbox 保证 DB 副作用恰好一次）：
  invite_code 为空 → 仅处理初始额度
  SELECT invites FOR UPDATE；UPDATE reservations SET state=consumed, user_id WHERE invite_id AND holder
  use_count + 1；use_count >= max_uses → status = exhausted
  use_count > max_uses → over_redeemed = true，指标 + 告警（只可能发生在事件延迟 > TTL 且被他人抢用）
  INSERT redemptions；INSERT tree_edges + tree_closure（ON CONFLICT DO NOTHING）
  publish invite.redeemed
```

### 5.3 额度来源

```
level.promoted{user_id, to_class} ─► class_grants[to_class].on_promotion
     accounts.promo_classes 已含 to_class 且 !repeat_on_repromotion → 跳过
     否则 INSERT quota_lots(source=level_promotion, source_ref=<event_id>)；流水；quota_changed
cron periodic_grants（每日 04:00）：今日是周期边界（monthly：1 日；weekly：周一）→
     遍历 identity.v_user_public WHERE status='active' AND class_id = ANY(...) AND id > cursor LIMIT 1000

shop：用户购买 → shop 扣魔力 → ctx.invites.grant_quota{user, amount, reason="shop.<order_id>",

管理员：POST /admin/users/{id}/quota-adjustments；批量 POST /admin/quota-grants → 延迟任务链
新用户：user.registered → initial_quota（source_ref = <event_id>）
```

### 5.4 连坐

```
user.status_changed{user_id: X, to: banned, restriction_source ≠ invite}  或
anticheat.case_resolved{user_id: X, action ∈ rule.cheating_actions}
 → edge = tree_edges[X]；不存在 → 结束
 → 对每条启用的规则 r（trigger 匹配）：
      registered_at(X) + r.within_days < now → 跳过
      for (depth, target) in ancestors(X, r.max_depth)：
          level = r.levels[depth]；无 → 跳过
          同 (invitee=X, target, r.group) 在 dedupe 窗口内已有未撤销处置 → 跳过
          target 有 invite.penalty.exempt → 记录 state=exempt
          INSERT penalties(trigger_event_id, rule, target, …) ON CONFLICT DO NOTHING（幂等）
          执行动作：deduct_quota（本插件）、suspend_invite（本插件）、revoke_outstanding（本插件）、
                    flag_review（本插件，state=pending_review）、
                    restrict_inviter（ctx.users.apply_restriction，幂等键 "<event_id>:<rule>:<target>"）、
                    notify（schedule_once("penalty_notify", now, {penalty_id}, dedupe="pn:<id>")）
          publish invite.penalty_applied
user.status_changed{user_id: X, from: banned, to ∉ {banned, deleted}}
 → 对 X 触发的、规则 reverse_on_lift 的、未撤销处置：返还扣除额度（新批次 source=penalty_refund）、
   解除暂停、lift_restriction（幂等键 "<event_id>:<penalty_id>:lift"）；state=reversed；publish penalty_reversed
```

### 5.5 撤销与过期

```
DELETE /users/me/invites/{id}：本人 + status=active + 无他人有效预留 → revoked；
  refund_on_revoke 且原批次未过期 → 原批次 remaining + 1（或批次已过期则不返还）；流水；事件
cron expire_invites：WHERE status='active' AND expires_at <= now ORDER BY expires_at LIMIT 500 FOR UPDATE SKIP LOCKED
  → expired；refund_on_expire → 返还；publish revoked(reason=expired)；每批 commit
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论 | 理由 |
|---|---|---|---|---|
| DD-INV-1 | 邀请码生成与幂等重放 | A 纯随机 + 只存哈希（幂等重放无法返回同一码）；B 随机 + 加密存明文；C `code = HMAC(code_key, 签发幂等键)` 截 128 位，只存哈希 | C | A 使服务调用的幂等重放失效；B 让库中出现可解密的码；C 对不知道 32 字节密钥的人等价于随机，重放可重新派生同一码，库泄漏不泄漏码（同 identity DD-IDN-14 思路）。HTTP 发邀路由**不**声明 `idempotent`，以免内核把含明文码的响应缓存进 Redis 24 h（kernel/03 §8.4），改用请求体 `request_id` 去重 |
| DD-INV-2 | 兑换的原子性 | A 钩子中直接扣次数；B 钩子预留 + 事件确认 | B | 钩子写入独立提交，A 在后续处理者拒绝或用户名冲突时会“吞码”；B 的预留以用户名为持有者、可重入，失败时 TTL 释放 |
| DD-INV-3 | 预留存储 | A Redis（TTL 天然）；B PG | B | 计数检查需要与邀请行在同一事务行锁下完成（Redis 无法与 PG 行锁原子）；注册峰值 200/s 下单行锁持有 < 2 ms 可承受；省去 Redis 能力 |
| DD-INV-4 | 额度模型 | A 用户计数列（NexusPHP）；B 批次 + 流水 | B | 支持临时额度、FIFO、按来源撤回（商城退款）；余额可由批次重算，流水可对账 |
| DD-INV-5 | 邀请树查询 | A 每次递归 CTE（Gazelle）；B 物化路径；C 闭包表 | C | 子树按深度分页、计数都是索引范围扫描；50 万用户、平均深度 < 10 时闭包表约 500 万行，可接受；插入只需复制邀请人的祖先行 |
| DD-INV-6 | 连坐重复触发（同一违规同时产生 `user.status_changed` 与 `anticheat.case_resolved`） | A 只支持一种触发；B 规则分组 + 去重窗口 | B | 两种触发各有适用场景；`group` 相同的规则在 `dedupe_window_days` 内对同一（被邀请人, 目标）只处置一次 |
| DD-INV-7 | 连坐通知的幂等 | A 事件处理中直接 `ctx.notify.send`（无幂等键，事务回滚重试会重复发）；B 事务内调度延迟任务（dedupe 键）后发送 | B | 延迟任务与业务同事务写入，只在提交后执行；仍可能因任务重试重复一次，§7 请 notify 为 `send` 增加 `idempotency_key` |
| DD-INV-8 | 等级门槛 | A 本插件读 `ctx.levels`；B `invite.before_issue` 钩子 | B | 规则归属各自插件，invite 不依赖 levels；levels 未安装也能工作 |
| DD-INV-9 | 被邀请人状态来源 | A 订阅 `user.status_changed` 自行维护；B 查询时 JOIN `identity.v_user_public` | B（统计）+ A（连坐触发） | 展示与统计以 identity 为准，避免副本漂移；只有“变化”这一触发需要事件 |
| DD-INV-10 | 邮箱绑定 | A 存明文；B 存 HMAC + 域名 | B | 不持有明文邮箱；钩子输入无 `email` 时退化为域名比对并计指标，站点可据此决定是否授予 `user.email` |
| DD-INV-11 | 撤销返还到哪个批次 | A 新建永久批次；B 原批次（已过期则不返还） | B | 防止“临时额度 → 发邀 → 撤销”洗成永久额度 |
