## 1. 设计目标与原则

1. **订单状态机驱动**：每个订单的每一步都持久化后再执行下一步；任何一步失败或崩溃，恢复任务从持久化状态继续（类 Saga）。
2. **钱先冻结，货后发**：先 `ledger.hold`，履约成功后 `capture_hold`（系统回收），失败 `release_hold`；绝不出现“先发货后扣款失败”。
3. **确定性幂等键**：订单 ID 生成后，冻结、履约、扣款、解冻、撤销的幂等键均由订单 ID 派生，重试安全。
4. **适配器隔离**：每种商品类型一个适配器（`validate` / `fulfill` / `revert`），订单流程与商品类型无关。
5. **依赖可选**：适配器依赖的服务都是 `optional_requires`，缺失时该类型不可用而不是插件启动失败。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
用户 / MCP ──► shop (WASM)
                │ hooks.run(shop.before_purchase) ──► levels、ratio-policy …
                │ ledger.hold / capture_hold / release_hold / reverse
                │ 适配器：
                │   upload_credit → accounting.adjust
                │   invite_quota  → invites.grant_quota / deduct_quota
                │   rename        → users.rename
                │   custom_title  → medals.set_custom_title
                │   medal         → medals.grant / revoke
                │   vip           → rbac.grant_role("shop:vip") / revoke_role
                │   makeup_card   → checkin.grant_makeup_cards
                │   promo_card    → promotions.grant_cards
                │   hnr_removal   → hnr.forgive
                ▼
      PG schema shop；事件 shop.item_purchased …
```

## 5. 关键流程

### 5.1 下单

```
状态：created → held → fulfilled → completed
                 └→ failed（release_hold）
 1. 校验商品可用、数量、参数（adapter.validate，无副作用）
 2. hooks.run(shop.before_purchase)
 3. 事务 A：锁商品行（有库存）与 purchase_counters；检查库存 / 限购；计算价格
            INSERT orders(state=created)；扣库存、加计数；commit（sql.commit，手动分段）
 4. ledger.hold(key = "shop:<oid>:hold")          → 余额不足：事务 B 回补库存/计数，state=failed
    UPDATE state=held, hold_id；commit
 5. adapter.fulfill(order, key = "shop:<oid>:fulfill")
    成功 → UPDATE state=fulfilled, fulfill_ref；commit
    业务失败（不可重试）→ ledger.release_hold；回补库存/计数；state=failed；commit
    可重试失败 / 超时 → 保持 held，返回 202（订单处理中），由 recover_orders 继续
 6. ledger.capture_hold(to_user = None, key = "shop:<oid>:capture") → state=completed；发布事件；commit
```

**分段提交的实现**：HTTP 请求是一个工作单元（不能中途提交），而第 4～6 步调用的 ledger 与适配器服务各自独立提交，如果在 HTTP 请求里直接调用，本插件事务回滚时会留下“已冻结 / 已发货但没有订单”的孤儿状态。因此：

- HTTP `POST /orders` 只做第 1～3 步：校验、钩子、预扣库存与限购、`INSERT orders(state=created)`，并在**同一事务**中 `jobs.schedule_once("advance_order", now, {order_id}, dedupe_key = order_id)`，提交后返回 `202 {order_id, state: "created"}`；
- 延迟任务 `advance_order`（`tx = manual`）按状态机逐步推进第 4～6 步，每一步先 `SELECT … FOR UPDATE` 读取当前状态、执行、写回状态并 `sql.commit()`；
- 前端轮询 `GET /orders/{id}`（或等待 `Prefer: wait=3` 长轮询，最多 3 秒）得到最终结果；内核延迟任务唤醒间隔 200 ms，正常情况下 1 秒内完成；
- `recover_orders` 只是兜底：处理任务失败、超时后仍停在中间状态的订单。

### 5.2 退款

```
completed → refunding → refunded
 1. adapter.revert（支持的类型）：invite_quota → deduct_quota；medal → revoke；vip → revoke_role；
    upload_credit → accounting.adjust(负值)；makeup_card / promo_card / rename / custom_title / hnr_removal → 不支持
 2. 不支持撤销且管理员未勾选 refund_only → 拒绝
 3. ledger.reverse(capture_entry_id) → state=refunded；发布 shop.order_refunded
```

## 6. 设计决策

| 编号 | 问题 | 备选 | 结论与理由 |
|---|---|---|---|
| DD-SHOP-1 | 支付方式 | 直接 transfer 扣款后发货 / hold → fulfill → capture | 后者：履约失败只需解冻，无需反向记账；ledger 余额中“冻结”对用户可见 |
| DD-SHOP-2 | 跨服务一致性 | 分布式事务 / Saga + 幂等键 | Saga：平台不提供分布式事务；每步幂等键由订单 ID 派生 |
| DD-SHOP-3 | 库存与限购扣减时机 | 履约成功后 / 下单时预扣、失败回补 | 下单时预扣：防止并发超卖；失败与恢复路径统一回补 |
| DD-SHOP-4 | VIP 实现 | 调 levels / rbac 动态角色 | rbac 动态角色 `shop:vip`（带 `expires_at`）；levels 的“VIP 等级”若存在，由 levels 订阅 `user.roles_changed` 自行映射 |
| DD-SHOP-5 | 改名 | 卖“改名卡”库存，用户另行使用 / 购买时直接改名 | 购买时直接改名（参数 = 新用户名），减少一种库存状态；`require_rename_via_shop` 时阻止其他自助改名路径 |
| DD-SHOP-6 | 不可撤销商品的退款 | 禁止 / 管理员确认“仅退款” | 管理员确认，写审计 |
| DD-SHOP-7 | 多币种 | 每商品单一币种 / 组合支付 | 单一币种（简单可靠）；组合支付不做 |

## 实现说明（2026-10-17，v0.1.0，开站计划 M4.1）

- 商品类型先实现 4 种：`upload_credit`（`ctx.accounting.adjust`，作用域 `write:adjust`）、`invite`（`ctx.invites.grant_quota`，`write:quota`，可设有效天数）、`promo_card`（`ctx.promotions.grant_cards`，`write:cards`，free / double_up）、`hnr_removal`（`ctx.hnr.forgive`，`forgive`，购买时选择本人进行中 / 已失败的记录）。改名卡、VIP、补签卡依赖的服务尚不存在（随 M4.4 补）。
- M4.2 增加第 5 种 `medal`（`ctx.medals.grant`，作用域 `grant`，参数 `medal_id`、可选 `days`；不填 `days` 时按勋章自身有效期，已持有则顺延），数量固定为 1。
- 流程：锁商品行（库存、限购在同一事务内判定）→ 写订单取得序列 ID → `ledger.hold`（15 分钟到期）→ 履约 → `capture_hold`（回收给系统）。冻结 / 履约 / 扣款 / 解冻的幂等键都由订单 ID 派生（`shop:hold:<id>` 等）。履约失败立即 `release_hold` 并返回 `shop.fulfillment_failed`；服务调用各自提交，若在履约后、扣款前中断，冻结到期自动解冻（偏向用户），未做恢复任务。
- 限购：按商品 `per_user_limit` + `limit_period`（none / day / week / month，滚动窗口）统计已完成订单数量；单次购买数量 1～10（消除 H&R 固定为 1）。
- 预置 4 个商品（默认下架），管理员在 `/admin/p/shop/` 调整价格与参数后上架；商品增改写审计。
- 未实现：`shop.before_purchase` 钩子、退款、每日统计、MCP、改名守卫。
