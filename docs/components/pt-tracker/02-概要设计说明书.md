> pt-tracker **不是插件**：没有 `plugin.toml`、不提供也不调用任何 `ctx.*` 服务、不发布也不订阅领域事件、不注册钩子、没有 MCP 工具和前端插槽。模板中这些小节保留标题并写明“无”，它真正的对外接口是 **HTTP（BT 客户端）** 与 **Redis 数据结构（tracker-bridge、accounting）**，见 §3。许可证 AGPL-3.0-only（D16），独立 Cargo workspace。

## 1. 设计目标与原则

1. **热路径不出进程**：announce 的解析、鉴权、准入、swarm 更新、peer 选择、编码全部在本地内存完成；Redis 只出现在异步记账、同步与少量回源中（design/10 §5.2）。
2. **宁可少记，不能多记**：任何不确定（状态丢失、CAS 冲突无法解决、写入结果未知、乱序）都选择“不计增量”或“下一次再算”，并通过信号位如实交给下游（D17、NFR-PTT-005）。
3. **先占位、后改状态**：只有确定能被记账的 announce 才修改 swarm；记账队列满时直接返回 busy，不留下“swarm 已更新但流量没有被接受”的半成品（DD-PTT-3）。
4. **torrust 只在一个 crate 里**：所有 torrust 类型只出现在适配 crate `ptt-torrust` 中，依赖图由编译器保证，便于跟进上游或切换到方案 D（FR-PTT-041、NFR-PTT-014）。
5. **契约以文档为准、两边各自实现**：`trk:*`、`ps:*`、`acct:*`、`u:*:live` 的格式与 tracker-bridge、accounting 文档逐字段一致，并用共享**测试向量（数据文件）**验证，不共享代码（licensing.md §2）。
6. **无业务规则**：不含倍率、促销、H&R、作弊判定；只计算增量和输出事实。
7. **可水平扩展、软状态可重建**：swarm 是软状态；peer 会话状态写穿 Redis，节点重启 / 分片迁移后懒加载恢复。

## 2. 总体结构

### 2.1 在整体架构中的位置

```
                BT 客户端（HTTP(S) announce / scrape）
                              │
                  ┌───────────▼────────────┐   按 URL 解码后的 info_hash 一致性哈希
                  │ 负载均衡：HAProxy 模板  │   （备选：pt-tracker route 薄路由，pt-ring-v1）
                  └──┬─────────┬────────┬──┘
                     ▼         ▼        ▼
               ┌─────────┐┌─────────┐┌─────────┐
               │ 节点 1  ││ 节点 2  ││ 节点 M  │   pt-tracker（AGPL-3.0-only，独立进程）
               └┬──┬──┬──┘└─────────┘└─────────┘
   读 trk:*  ◄──┘  │  └──► 写 acct:<uid%N>、u:<uid>:live          Redis acct ──► accounting（Native 插件）
   写 trk:stats:*  │                                                  （XREAD + PG 游标）
  （tracker_sync） └────► 读写 ps:<info_hash>（CAS）                 Redis tracker_state ──► tracker-bridge（只读 peer 列表）
        ▲
        └── tracker-bridge（唯一写入方：trk:pk / trk:t / trk:clients / trk:cfg / trk:sync）
```

pt-tracker 与内核、插件之间**没有任何代码链接、RPC 或共享内存**，只有上图中的 Redis 键（redis-keys.md §3、§5）。

### 2.3 Cargo workspace 与 crate 划分

`crates/pt-tracker/` 是独立 workspace（主 `Cargo.toml` 中 `exclude`），细化 design/10 §5.1 的模块划分为多个 crate，使“torrust 只在适配层”由编译器保证：

| crate | 类型 | 职责 | 依赖 torrust | 对应 design/10 §5.1 模块 |
|---|---|---|---|---|
| `ptt-types` | lib | 领域类型：`InfoHash20`、`PeerId20`、`Passkey`、`UserEntry`、`TorrentEntry`、`Report`、`PeerState`、`Delta`、`Flags`、`SwarmPeer`、`SelectedPeer` | 否 | — |
| `ptt-core` | lib | 纯逻辑：增量 `compute()`、准入判定、客户端规则匹配、请求头检查、peer 选择算法、失败文案表、`ps` 值编解码、流量事件编码、pt-ring-v1 | 否 | `admission/`、`accounting/`（计算部分）、`shard/` |
| `ptt-torrust` | lib | **唯一**依赖 torrust 的 crate：`swarm`（`SwarmBackend` 的 torrust 实现，包装 `Registry`）、`protocol`（包装 `http-protocol` 的解析与 bencode 编码、错误映射） | **是** | `swarm/`、`protocol/` |
| `ptt-redis` | lib | Redis 访问：会话状态存储（CAS 脚本）、流量 sink、同步加载与变更流消费、节点状态与被拒统计写入 | 否 | `sync/`、`sink/`、`accounting/`（存储部分） |
| `ptt-server` | lib | axum 路由与请求流水线、记账 worker、懒加载重建、清理、健康与就绪、指标 | 否（只依赖 `ptt-torrust` 暴露的自有类型与 trait 实现） | `server/`、`metrics/` |
| `ptt-router` | lib | `pt-tracker route` 薄 L7 路由 | 否 | `shard/`（LB 备选） |
| `pt-tracker` | bin | 命令行：`serve`、`route`、`check-config`、`vectors verify`；配置加载；任务编排；优雅退出 | 否（链接 `ptt-torrust`） | `main.rs` |
| `ptt-bench` | bin（不发布） | 压测负载生成器（TP-PTT §5） | 否 | — |
| `ptt-testkit` | lib（dev） | 内存版 `SwarmBackend`、Redis 容器辅助、测试向量加载 | 否 | — |

CI 检查：`cargo tree -e normal -i torrust-tracker-primitives`（及其余 3 个 torrust 包）的反向依赖只能是 `ptt-torrust`；`ptt-core` 能在不拉取 torrust 的情况下单独编译测试。

### 2.4 内部模块职责

| 模块（crate） | 职责 |
|---|---|
| `protocol`（ptt-torrust） | 原始 query 预规范化（未知 `event`、非法 `numwant` 等）→ torrust `Query` / `Announce` 解析 → 自有 `AnnounceReq`；解析错误按**变体**映射为固定错误码，绝不使用错误的 `Display`；bencode 编码 announce / scrape / failure 响应 |
| `admission`（ptt-core + ptt-server） | 本地准入表（passkey 表、种子表、客户端规则、运行参数）；请求头 / UA / 端口检查；用户与种子状态判定；回源（单飞 + 负缓存 + 令牌桶）；单 passkey 限速 |
| `swarm`（ptt-torrust） | `TorrustSwarm`：upsert / remove、取候选 peer、swarm 统计、恢复（懒加载写回）、超时清理；大 swarm 的选择快照缓存 |
| `select`（ptt-core） | peer 选择算法：按角色和地址族分池、配额、随机起点 + 互质步长 |
| `rebuild`（ptt-server） | 懒加载重建：单飞、`HLEN` 门限、内联超时、后台 `HSCAN` |
| `accounting worker`（ptt-server + ptt-core + ptt-redis） | 消费队列、会话缓存（worker 独占）、`compute()`、CAS 写回、冲突重算、熔断、交给 sink |
| `state`（ptt-redis） | `ps:*` 编解码、`ps_cas` Lua 脚本、HMGET/HSCAN 读取 |
| `sink`（ptt-redis） | `XADD acct:<p>` + `HINCRBY u:<uid>:live` pipeline；同 `eid` 重试；`u:*:live` TTL 节流刷新 |
| `sync`（ptt-redis + ptt-server） | 启动快照加载、`XREAD BLOCK trk:sync`、按 `ver` 应用、缺口检测、全量重载（旧表继续服务 + 重放缓冲） |
| `stats`（ptt-server + ptt-redis） | `trk:stats:node:<node_id>`（10 s）、`trk:stats:denied:<yyyymmdd>`（10 s 批量） |
| `shard`（ptt-core + ptt-server） | pt-ring-v1、错误路由计数 |
| `router`（ptt-router） | `pt-tracker route`：解码 info_hash → HRW 选后端 → 转发 |
| `metrics`、`health` | Prometheus 指标（独立端口）、`/health`、`/ready` |

依赖方向：`pt-tracker(bin) → ptt-server → {ptt-torrust, ptt-redis, ptt-core} → ptt-types`；`ptt-core`、`ptt-redis` 互不依赖 torrust。

## 3. 对外接口清单

### 3.1 提供的服务（`ctx.*`）

无（不是插件）。

### 3.2 依赖的服务

无 `ctx.*` 依赖。外部依赖：

| 依赖 | 用途 | 必需 |
|---|---|---|
| Redis `tracker_sync`（单分片） | 读 `trk:pk:*`、`trk:t:*`、`trk:clients`、`trk:cfg`、`trk:sync`；写 `trk:stats:*` | 是（启动时）；运行中不可用则以本地缓存继续服务 |
| Redis `tracker_state`（≥ 7.4，可 Cluster） | 读写 `ps:*` | 否（不可用时 announce 照常，记账不推进，见 DD-PTT-5） |
| Redis `acct`（可 Cluster） | 写 `acct:*`、`u:*:live`；读写 `acct:_meta`（§7） | 是（不可用时队列积压 → busy） |
| torrust 4 个包（git rev 锁定） | swarm、协议、基础类型、事件 | 是 |

### 3.3 发布的事件

不发布领域事件。等价的“输出”是 Redis 流 `acct:<partition>`（**不是领域事件**，不走 outbox，events.md §6），字段见 LLD §3.5，消费方 accounting。

### 3.4 订阅的事件

不订阅领域事件。等价的“输入”是 Redis 流 `trk:sync`（tracker-bridge 写入），处理见 LLD §1.11。

### 3.5 注册的钩子

无。

### 3.7 MCP 工具

无。

### 3.8 前端插槽与页面

无。tracker 的管理界面由 tracker-bridge 提供（读取 `trk:stats:*` 与 `ps:*`）。

### 3.9 定时任务（进程内）

| 任务 | 周期 | 说明 |
|---|---|---|
| `cleanup` | `swarm.cleanup_interval`（600 s） | 移除超过 `max_peer_timeout` 的 peer 与空 swarm；清理过期的选择快照、重建标记 |
| `tombstone_purge` | 60 s | 本地准入表中 `exp ≤ now` 的墓碑删除 |
| `node_stats` | 10 s | 写 `trk:stats:node:<node_id>`（TTL 30 s） |
| `denied_flush` | 10 s | 批量 `ZINCRBY trk:stats:denied:<yyyymmdd>` |
| `gap_check` | 5 s（及重连后） | `XINFO STREAM trk:sync` 检查是否被修剪越过游标 |
| `cfg_watch` | 随 `trk:cfg` 变更 | 校验 `interval < max_peer_timeout` 等，必要时告警并钳制 |

这些任务都在单个进程内、无跨进程互斥需求；多节点各自执行，互不影响（写入的键按 `node_id` 区分，或为 `ZINCRBY` 这类可交换累加）。

### 3.10 权限点

无（不接入 RBAC）。访问控制由 passkey（客户端）、网络隔离（`/metrics`）、Redis ACL（§3.11）完成。

### 3.11 声明的能力 → Redis ACL

| 实例角色 | ACL（`deploy/redis/acl.conf` 模板，LLD §6.2） |
|---|---|
| `tracker_sync` | 只读 `trk:pk:*`、`trk:t:*`、`trk:clients`、`trk:cfg`、`trk:sync`；读写 `trk:stats:*`；**不能读 `trk:u:*`** |
| `tracker_state` | 读写 `ps:*`（`HGET/HMGET/HGETALL/HLEN/HSCAN/EVALSHA/SCRIPT LOAD`） |
| `acct` | 写 `acct:*`（`XADD`、`EXISTS`、`XINFO`）、`u:*:live`（`HINCRBY`、`EXPIRE`）；读写 `acct:_meta` |

## 4. 数据设计概要

pt-tracker **不访问 PostgreSQL、对象存储、搜索索引**。

| 数据 | 位置 | 生命周期 |
|---|---|---|
| passkey 表 `pk → UserEntry{uid, st, rsn, exp, ver}` | 进程内（ArcSwap 整表 + 增量写） | 由 `trk:pk:*` 同步 |
| 种子表 `info_hash → TorrentEntry{tid, st, acct, size, own, rsn, exp, ver}` | 进程内 | 由 `trk:t:*` 同步 |
| 客户端规则（已编译）、运行参数 | 进程内 | 由 `trk:clients`、`trk:cfg` 同步 |
| 负缓存（pk / info_hash） | 进程内 LRU | `negative_cache_ttl` |
| swarm（torrust Registry） | 进程内 | 软状态，超时清理，可从 `ps:*` 重建 |
| 选择快照（大 swarm） | 进程内 | `snapshot_ttl_ms` |
| 会话缓存 `(uid, ih, pid) → PeerState` | 进程内，按 worker 分片 | LRU + 超时清扫 |
| peer 会话状态 | Redis `tracker_state` `ps:<ih>` HASH | 字段 TTL（HEXPIRE）+ 键 TTL |
| 流量事件 | Redis `acct` `acct:<p>` STREAM | `MAXLEN ~` + accounting `XTRIM MINID` |
| 实时计数 | Redis `acct` `u:<uid>:live` HASH | 7 天 |
| 分区数守卫 | Redis `acct` `acct:_meta` HASH（新增，§7） | 永久 |
| 节点状态、被拒客户端统计 | Redis `tracker_sync` `trk:stats:node:*`、`trk:stats:denied:*` | 30 s / 8 天 |

## 5. 关键流程

### 5.1 announce（正常路径）

```
客户端 ─GET /announce/<pk>?info_hash=…─► 节点
  ① protocol.parse(raw_query) ─失败→ 200 "invalid …"（固定文案）
  ② 请求头 / UA / 端口检查（trk:cfg 开关）─失败→ "client not allowed" / "port not allowed"
  ③ passkey 格式 → 本地表（未命中：负缓存？→ 令牌桶 → 单飞 HGETALL trk:pk:<pk>）→ 用户状态
  ④ 客户端规则 decide(peer_id, UA)（与 tracker-bridge 同一规范）
  ⑤ 种子表（未命中同 ③ 回源 trk:t:<ih>）→ 种子状态（owner_only 比对 own）
  ⑥ leech_disabled 且 left>0 且 event≠stopped → "download privilege disabled"
  ⑦ 本地 swarm 不含该 hash 且未尝试过 → 懒加载重建（内联，≤100 ms）
  ⑧ 若 acct=1：permit = queue[hash(uid,ih,pid) % K].try_reserve() ─失败→ "tracker busy"（swarm 不变）
  ⑨ swarm.announce(ih, peer) → select(peers, 角色, 地址族, k) → 统计
  ⑩ permit.send(AnnounceFact)
  ⑪ bencode 响应（interval、min interval 来自 trk:cfg）
```

### 5.2 异步记账

```
worker(i)：recv_many(≤256, 等待 ≤2 ms)
  对缓存未命中的会话：按 ih 分组 HMGET ps:<ih> <uid:pid>…（一个 pipeline）
  逐条 compute(prev, report, size, policy) → Apply{delta, next} / Discard
  pipeline EVALSHA ps_cas（期望 ver）×n ─► tracker_state
     冲突 → 用返回的当前值重算一次 → 再 CAS → 仍冲突：放弃本次增量（宁少记），丢弃缓存项
     Redis 错误 → 熔断：本批全部“不推进”（缓存不变、不输出，下一次 announce 覆盖这段）
  成功的事件（满足输出条件）→ sink：pipeline XADD acct:<uid%N> MAXLEN ~ …、HINCRBY u:<uid>:live …
     失败 → 同 eid 重试（超时类只重发 XADD），worker 阻塞 → 队列积压 → busy（背压）
```

### 5.3 同步（tracker-bridge → 节点）

```
启动：L = XREVRANGE trk:sync + - COUNT 1（空流为 0-0）
      SCAN trk:pk:* / trk:t:*（pipeline HGETALL）、GET trk:clients、HGETALL trk:cfg → 构建新表 → 就绪
循环：XREAD BLOCK 5000 COUNT 1000 STREAMS trk:sync <游标>
      {kind, key, op, ver} → 重读快照键 → ver 更大才覆盖；键不存在且本地 ver ≤ 消息 ver → 删除本地条目
      kind=all op=reload → 全量重载
gap_check：XINFO STREAM → max-deleted-entry-id > 游标 或 last-generated-id < 游标 → 全量重载
全量重载：记 L2 → 后台构建新表（旧表继续服务并继续应用变更，同时把 L2 之后的消息放入重放缓冲）→ 原子替换 → 在新表上重放缓冲
```

### 5.4 节点重启 / 分片迁移后的懒加载

```
announce(ih) 到达，本地 swarm 无 ih 且 rebuild_marks 无 ih：
  单飞 { n = HLEN ps:<ih>
         n == 0 → 标记，结束
         n ≤ 2000 → HGETALL（≤100 ms 超时）→ 解码，丢弃 last_ts < now − max_peer_timeout
                    → swarm.restore(peers, 保留原 last_ts) → 按会话键把状态发给对应 worker（Preload）
         n > 2000 → 本次不等待；后台 HSCAN COUNT 500 分批 restore + Preload }
  其余并发请求等待同一个单飞结果（同样受超时约束）
```

迁移期间旧节点上残留的 swarm 在超时后被 `cleanup` 回收；两个节点同时处理同一会话时由 CAS 保证不重复计数。

### 5.5 优雅退出

```
SIGTERM → /ready 返回 503 → 等待 drain_secs（LB 摘除）→ 停止 accept，等待在途请求完成
       → 关闭队列入口 → 各 worker 排空（最长 shutdown_flush_secs）→ 写最后一次节点状态 → 退出
未能在期限内写出的事实计数并记录日志（只有条数，无用户数据）
```

## 6. 设计决策

| 编号 | 问题 | 备选方案 | 结论 | 理由 |
|---|---|---|---|---|
| DD-PTT-1 | 代码组织 | A 单 crate 多模块 + CI grep（design/10 §5.1）；B workspace 多 crate | B | torrust 隔离由依赖图强制，而非约定；`ptt-core` 可独立测试与复用到 `route`；升级 torrust 时 diff 只在 `ptt-torrust` 与 `Cargo.*`（NFR-PTT-014 的表述相应改为“只在 `ptt-torrust`”） |
| DD-PTT-2 | 记账并发模型 | A 共享会话缓存 + 分片锁（原型）；B 每个 worker 独占一片缓存，会话按键哈希固定到 worker | B | 同一会话天然串行（FR-PTT-020），缓存访问无锁；批量 pipeline 自然形成 |
| DD-PTT-3 | 队列满时如何拒绝 | A 先更新 swarm 再投递，满了丢弃 / busy；B 先 `try_reserve` 占位，成功才更新 swarm | B | A 会出现“swarm 已更新但流量没被接受”的半状态；B 返回 busy 时没有任何副作用，客户端重试后完整处理 |
| DD-PTT-4 | 会话状态 CAS 粒度 | A 每个会话一个键 `ps:<ih>:<uid>:<pid>`（原型注释）；B `ps:<ih>` HASH，字段为会话，Lua 按字段比较 `ver`，字段级 TTL（HEXPIRE） | B | 与 redis-keys.md、tracker-bridge 一致；按种子聚合便于懒加载（一次 HGETALL）；同种子同槽位，Cluster 友好；HEXPIRE 让热门种子的陈旧字段自动过期，因此要求 `tracker_state` Redis ≥ 7.4 |
| DD-PTT-5 | `tracker_state` 不可用时 | A 用本地缓存继续计算并输出，事后补写（可能与其他节点冲突、重复）；B 超过重试上限后只建基线（SRS NFR-PTT-008 原文）；C 不推进：本次不写状态、不输出、缓存保持在最后持久化的状态，下一次成功的 announce 用持久化状态计算，自然覆盖中间这段 | C | C 不会多记，且只损失被 `max_interval` 截断的时长，比 B 少记得更少；实现最简单（熔断 + 丢弃事实）；满足 NFR-PTT-008 “announce 照常、宁少记” 的本意 |
| DD-PTT-6 | XADD 重试与实时计数 | A 整个 pipeline 重试；B MULTI/EXEC；C 同一 `eid` 重试 XADD，HINCRBY 只在第一次尝试中发送 | C | A 会重复增加 `u:*:live`；B 在 Cluster 下跨槽不可用，结果未知时同样无法判断；C 的重复 XADD 由 accounting 按 `eid` 去重，实时计数最多偏小（展示用，accounting 扣减时截断为 0） |
| DD-PTT-7 | peer 选择 | A torrust `peers_excluding`（按地址顺序取前 N）；B 全量复制后洗牌（原型 / UNIT3D-Announce，O(n)）；C 按角色 × 地址族分池，随机起点 + 互质步长取样；大 swarm 使用周期刷新的快照 | C | A 让所有人拿到同一批地址最小的 peer（design/10 §2.7）；B 在万级 swarm 上每次 announce O(n)；C 每次 O(k)，快照的 O(n) 刷新被摊薄；做种者只拿下载者，下载者优先拿做种者并保留一半名额给其他下载者 |
| DD-PTT-8 | 负载均衡 | A HAProxy `balance hash url_param(info_hash),url_dec` + `hash-type consistent`；B Envoy + Lua 规范化；C 自研薄路由 `pt-tracker route`（HRW，pt-ring-v1） | 首选 A（V5 验证），C 为备选并作为算法参考实现 | A 零开发；C 只在 A 验证失败（如含 `%00` 的 hash 被截断、`+` 处理不一致）时启用；节点侧只有在使用 C 时才能精确判断错误路由，使用 A 时以 CAS 冲突率与稳态重建次数作为间接指标 |
| DD-PTT-9 | 同步缺口检测 | A 比较游标与 `first-entry`；B 使用 Redis 7 的 `max-deleted-entry-id` | B（A 作后备） | A 无法区分“中间被修剪”与“本来就没有消息”；B 精确判断游标之后是否有被删除的条目 |
| DD-PTT-10 | 全量重载期间的服务 | A 暂停服务；B 暂停消费变更流；C 旧表继续服务并继续应用变更，L2 之后的消息另存重放缓冲，换表后重放 | C | 30 s 级的重载期间封禁等变更仍 1 s 内生效；ver 比较保证重放幂等 |
| DD-PTT-11 | 回源防穷举 | A 不回源；B 回源 + 负缓存 + 全局令牌桶 + 单飞 | B（passkey 与种子各一组） | 解决“刚注册 / 刚上传就 announce”的竞态（design/10 §5.5）；穷举时每节点回源 ≤ `miss_lookup_rps` |
| DD-PTT-12 | 未发 `completed` 就变成做种者 | A 只认 `event=completed`（原型）；B 会话内 `left` 从 >0 变为 0 时也视为完成 | B | 部分客户端（重新校验、丢包）不发 completed，B 让 snatch 不漏；只在同一会话内判断，`first_seen` 时 `left=0` 不推断；`event=completed` 但 `left>0` 不算完成（防止提前骗 snatch） |
| DD-PTT-13 | 有旧状态时收到 `started` | A 当普通 announce 相减（回退会打 regressed 标）；B 当新会话：计数器回退时按上报值计、时长不计 | B | BEP 3 规定 started 时累计值从本会话开始；客户端重启沿用 peer_id 是常见行为，不应产生 regressed 噪声；客户端停机的那段时间不计时长 |
| DD-PTT-14 | 乱序 / 陈旧上报 | A 不处理；B 回退且距上次 ≤ `regress_grace_secs`，或时间明显早于已记录的 last_ts 时丢弃 | B | 迁移期间两个节点交错处理同一会话时，晚到的旧上报会把基线拉低，导致下一次重复计数；丢弃只损失这一次（宁少记） |
| DD-PTT-15 | hybrid 种子 | A 两个 hash 都计账后由下游去重；B 只对 `acct=1` 的 hash 建会话与输出（D17、design/10 §5.3） | B | 下游无法可靠判断两条流量是否同源；`acct=0` 的 hash 只参与 swarm，不写 `ps:*`（因此其 swarm 不能懒加载恢复，等客户端重新 announce） |
| DD-PTT-16 | 错误文案 | A 透传 torrust 错误文本；B 按错误**变体**映射到固定文案表 | B | torrust 错误文本含源码绝对路径（design/10 §6.3）；固定表也防止把 passkey、内部状态写进响应 |
| DD-PTT-17 | 分区数 N 的一致性 | A 只靠部署文档；B 在 `acct:_meta` 记录 N，所有节点启动时校验 | B（§7 新增键） | N 部署后不能改（design/10 §5.4）；节点之间、节点与 accounting 之间 N 不一致会把用户写进错误分区（accounting 会以 `wrong_partition` 拒收） |
| DD-PTT-18 | 懒加载是否阻塞 announce | A 后台异步（首个 announce 拿到空列表）；B 内联等待；C `HLEN` 门限：小 swarm 内联（≤100 ms 超时），大 swarm 后台 HSCAN | C | 满足“重启后第一次 announce 即返回完整 peer 列表”（FR-PTT-017）且不让超大种子拖慢请求 |
| DD-PTT-19 | 就绪判定 | A 三类 Redis 都可达才就绪（FR-PTT-034 原文）；B 首次加载完成 + `acct` 可达 + 队列未满 | B | `tracker_sync`、`tracker_state` 不可用时 NFR-PTT-007/008 要求继续服务，若因此摘除节点会把局部故障放大成全站不可用；`acct` 不可用时队列必然积压，摘除与返回 busy 等价 |

## 7. 对平台契约的新增

pt-tracker 不是插件，以下条目需要合入 `docs/platform/catalog/redis-keys.md` 或同步修改 tracker-bridge / accounting 文档：

| # | 类别 | 内容 | 说明 / 需要谁配合 |
|---|---|---|---|
| N-1 | Redis 键（acct） | `acct:_meta` HASH：`partitions`（N）、`created_at`、`created_by`（node_id）；首个节点 `HSETNX` 写入，其他节点启动时比对，不一致拒绝启动；无 TTL | DD-PTT-17；accounting 可选择同样比对（替代 `EXISTS acct:0…` 的启发式检查）。注意该键名不符合 `acct:<partition>` 的数字格式，accounting 不得用 `SCAN acct:*` 枚举分区 |
| N-2 | 流量事件 flags | 新增 bit6 `left_exceeds_size`（`size > 0` 且 `left > size`）；bit7～bit31 保留，**消费方必须忽略未知位** | FR-PTT-018；accounting 当前用镜像体积自行判断 `left > size`，可直接改用该位，或忽略；需 accounting 文档在 parse 中写明“未知位忽略” |
| N-3 | `ps:*` | 值头部（`fmt`、`flags`、`port`、`ver`，偏移 0～7）固定，未来的 `fmt` 只能在偏移 8 之后变化；字段级 TTL 用 `HEXPIRE`，**`tracker_state` 要求 Redis ≥ 7.4**；键 TTL 与字段 TTL 均为 `2 × max_peer_timeout` | redis-keys.md §2、§3 补充；tracker-bridge 的解码只依赖已登记字段，无需修改 |
| N-4 | Redis ACL | pt-tracker 在 `tracker_sync` 上的权限收窄为 `%R~trk:pk:* %R~trk:t:* %R~trk:clients %R~trk:cfg %R~trk:sync %RW~trk:stats:*`（不能读 `trk:u:*` 反向索引） | 比 tracker-bridge LLD §6 的 `~trk:* +@read` 更小；redis-keys.md §5 与 `deploy/redis/acl.conf` 采用本写法 |
| N-5 | `trk:stats:denied:<yyyymmdd>` | 日期按 **UTC**；member 中 peer_id 前缀的转义规则：`0x21～0x7E` 中除 `%`、`|` 外原样，其余 `%XX`（大写） | tracker-bridge LLD §3.2 未写时区与转义细则，需确认 |
| N-6 | 指标命名空间 | Prometheus 前缀 `pt_`（除 `pt_kernel_`、`pt_plugin_` 外）保留给 pt-tracker；沿用 design/10 §5.9 的指标名 | 与内核、插件指标不冲突 |
| N-7 | 测试向量 | `docs/components/pt-tracker/vectors/`：`client-rules.json`、`ps-values.json`、`status-mapping.json`（与 tracker-bridge 共用）、`acct-entries.json`（与 accounting 共用：事件字段编码与 flags）、`ring-v1.json`（pt-ring-v1）、`failure-reasons.json`（文案表） | 数据文件，不是代码；格式见 LLD §10 |
| N-8 | `trk:t` 的 `rsn` | 建议 tracker-bridge 在 `st = 1`（owner_only）时也写 `rsn`（`pending` / `rejected`），以便 pt-tracker 给出准确文案；缺省按 `pending` 处理 | 只增字段，pt-tracker 已兼容缺失 |
| N-9 | `u:<uid>:live` TTL | pt-tracker 写入时 `EXPIRE 604800`，同一节点对同一用户每 `live_ttl_refresh_secs`（默认 3600 s）最多刷新一次，因此实际“无更新过期”时间为 7 天 ～ 7 天 + 1 小时 | redis-keys.md 表述补充 |
| N-10 | `acct:<p>` 的 `MAXLEN ~` 默认值 | 每分区 2,000,000（约平均负载 2 小时；全满约 64 × 2M × 120 B ≈ 15 GB） | accounting 的 `acct` 实例容量规划需按此上限留余量；accounting 正常 `XTRIM MINID` 后实际只占约 2 GB |

不需要新增服务、领域事件、钩子、权限点、术语、插槽、MCP 工具、错误码（pt-tracker 的失败原因是 BT 协议文本，不进入 error-codes.md）。
