### 1.2 进程与任务编排

```rust
// bins/pt-tracker/src/main.rs（概要）
fn main() -> ExitCode {
    let cli = Cli::parse();                     // serve | route | check-config <path> | vectors verify <dir>
    let cfg = Config::load(&cli.config)?;       // TOML + 环境变量 PT_TRACKER__<段>__<键>，§4 校验，失败打印字段路径并退出 2
    match cli.cmd {
        Serve => runtime(cfg.runtime_threads).block_on(serve(cfg)),
        Route => runtime(..).block_on(ptt_router::run(cfg.route)),
        ..
    }
}

async fn serve(cfg) -> Result<()> {
    let boot_epoch = unix_secs();               // 写入 eid
    let redis = Redis::connect(&cfg.redis).await?;          // 三个角色，各自连接池
    redis.state.check_version(">=7.4").await?;             // INFO server；失败拒绝启动（HEXPIRE）
    redis.state.load_scripts().await?;                     // SCRIPT LOAD ps_cas
    redis.acct.check_partitions(cfg.accounting.partitions, &cfg.node_id).await?;   // acct:_meta，§3.5.4
    let tables = AdmissionTables::empty();                 // ArcSwap<Tables>
    let ready = ReadyState::new();
    let (workers, queues) = spawn_workers(cfg.accounting.workers, &redis);           // §1.8
    let swarm = TorrustSwarm::new(&cfg.swarm);             // ptt-torrust
    spawn(sync_runtime(redis.sync.clone(), tables.clone(), ready.clone()));          // §1.11：初次加载完成后 ready.mark_loaded()
    spawn(cleanup_task(swarm.clone(), ...));               // §1.6.6
    spawn(stats_task(redis.sync.clone(), ...));            // §1.13
    let app = App { cfg, tables, swarm, queues, redis, ready, metrics, .. };
    let http = axum::serve(listener, routes(app)).with_graceful_shutdown(shutdown_signal(ready));
    let metrics = axum::serve(metrics_listener, metrics_routes());
    join(http, metrics).await;
    drain_workers(workers, cfg.shutdown.flush_secs).await;  // §1.14.3
}
```

线程：tokio 多线程运行时，`runtime_threads` 默认 = CPU 核数；记账 worker 是 tokio 任务（不是独立线程），每个 worker 的批处理在单个任务内顺序执行。没有阻塞调用；正则匹配和编码是纯 CPU 且有界（§7）。

### 1.3 请求流水线（`ptt-server::pipeline`）

#### 1.3.1 announce

```rust
async fn announce(State(app), Path(raw_pk): Path<String>, ConnectInfo(remote), headers, RawQuery(q)) -> Response {
    let t0 = Instant::now();
    let r = handle_announce(&app, &raw_pk, remote, &headers, q.as_deref()).await;
    app.metrics.announce(r.label(), t0.elapsed());          // pt_announce_total{result}、duration
    match r {
        Ok(body) => bencode_200(body),
        Err(f)   => bencode_200(app.encode_failure(f)),       // 固定文案表 §2.2；永远 HTTP 200
    }
}

async fn handle_announce(app, raw_pk, remote, headers, q) -> Result<Bytes, Failure> {
    if !app.ready.loaded() { return Err(Failure::Busy) }                       // FR-PTT-029
    let cfg = app.tables.load().cfg.clone();                                   // 运行参数快照（Arc）
    // ① 解析
    let q = q.ok_or(Failure::MissingParam(Param::InfoHash))?;
    if q.len() > app.cfg.http.max_query_bytes { return Err(Failure::BadRequest) }
    let req = protocol::parse_announce(q)?;                                    // §1.4：AnnounceReq，错误已映射为 Failure
    // ② 请求头 / UA / 端口
    let ua = headers::user_agent(headers);                                     // Option<&[u8]>，截断前的原值
    headers::check(&cfg, headers, ua, req.port, req.event)?;                  // §1.5.5
    // ③ passkey → 用户
    let pk = Passkey::parse(raw_pk).ok_or(Failure::InvalidPasskey)?;           // 32 位 [0-9a-f]
    let user = app.admission.user(&pk).await?;                                 // §1.5.2：含回源、墓碑、状态
    app.admission.rate_limit(&pk)?;                                            // FR-PTT-013（默认关闭）
    // ④ 客户端规则
    let (action, rule_id) = app.tables.load().clients.decide(&req.peer_id, ua.unwrap_or(b""));
    if action == Deny { app.stats.denied(&req.peer_id, ua); return Err(Failure::ClientNotAllowed(DenyReason::Rule)) }
    // ⑤ 种子
    let t = app.admission.torrent(&req.info_hash, user.uid).await?;           // §1.5.3：含 owner_only
    // ⑥ 禁止下载
    if user.st == UserSt::LeechDisabled && req.left > 0 && req.event != Ev::Stopped {
        return Err(Failure::LeechDisabled)
    }
    app.shard.observe(&req.info_hash);                                         // pt_misrouted_total，§1.12.4
    // ⑦ 懒加载重建（只在本地 swarm 不存在该 hash 时）
    if app.cfg.swarm.rebuild_on_miss && !app.swarm.contains(&req.info_hash) {
        app.rebuild.ensure(&req.info_hash, t.acct).await;                      // §1.7：单飞 + 超时，失败不阻塞
    }
    // ⑧ 记账占位（只对 acct=1）
    let key = SessionKey { uid: user.uid, ih: req.info_hash, pid: req.peer_id };
    let permit = if t.acct {
        Some(app.queues.try_reserve(key.worker(app.k)).map_err(|_| Failure::Busy)?)   // DD-PTT-3
    } else { None };
    // ⑨ swarm + 选择
    let ip = client_ip(&app.cfg.http, remote, headers, &req);                  // §1.3.4
    let speer = SwarmPeer { peer_id: req.peer_id, addr: SocketAddr::new(ip, req.port), uploaded: req.uploaded,
                            downloaded: req.downloaded, left: req.left, event: req.event, updated: now_secs() };
    let want = PeerWant { k: peer_count(&cfg, req.numwant, req.event), seeder: req.left == 0, family: ip.family() };
    let reply = app.swarm.announce(&req.info_hash, &speer, &want).await;       // §1.6：不会因业务原因失败
    // ⑩ 投递
    if let Some(p) = permit {
        p.send(WorkerMsg::Fact(AnnounceFact { key, tid: t.tid, size: t.size, ts: speer.updated,
                                              ip, port: req.port, up: req.uploaded, down: req.downloaded,
                                              left: req.left, ev: req.event, ua: ua_trunc128(ua) }));
    }
    // ⑪ 响应
    Ok(protocol::encode_announce(&reply, &cfg, req.compact, req.no_peer_id, jitter(&app.cfg.announce)))
}
```

`peer_count(cfg, numwant, event)`：`event = stopped` → 0；否则 `min(numwant.unwrap_or(cfg.max_peers), cfg.max_numwant)`（FR-PTT-015 中 “min(numwant, max_peers)” 按 `trk:cfg` 的 `max_peers`（默认值）与 `max_numwant`（上限）两个字段细化）。

**为什么占位在 swarm 之前、在懒加载之后**：懒加载可能等待最多 `rebuild_timeout_ms`，占位后再等待会让许可长时间占用队列容量；占位失败时 swarm 尚未改变，客户端重试即可得到完整处理。

#### 1.3.2 失败的分类

`Failure` 枚举（`ptt-core::failure`）与文案一一对应（§2.2），并决定指标标签。没有“透传字符串”的变体——`Failure::Internal` 也只输出固定的 `internal error`，详细原因只进日志（且已脱敏，§8.2）。

#### 1.3.3 scrape

```
GET /scrape/<pk>?info_hash=<20B>
  ready 检查 → protocol::parse_scrape(q)：info_hash 个数 0 → MissingParam(InfoHash)；>1 → MultiHashScrape
  cfg.scrape_enabled == 0 → ScrapeDisabled
```

`downloaded` 为本节点 swarm 中记录的完成次数（torrust `SwarmMetadata.downloaded`，节点重启或迁移后从 0 开始，**只作参考**；站点展示的完成数以 accounting 为准）。

#### 1.3.4 客户端 IP

```
fn client_ip(http, remote, headers, req) -> IpAddr:
    ip = remote.ip()
    if http.reverse_proxy && in_cidrs(ip, http.trusted_proxies):
        // X-Forwarded-For 从右往左，跳过可信代理，取第一个不可信地址
        for a in xff(headers).rev(): if !in_cidrs(a, http.trusted_proxies) { ip = a; break }
    if http.use_ip_from_query && req.ip.is_some(): ip = req.ip          // 默认关闭
    canonical(ip)                                                        // IPv4-mapped IPv6 → IPv4
```

XFF 解析使用 torrust `peer_ip_resolver`（经 `ptt-torrust::protocol` 包装）之外再加可信代理判断：torrust 的实现只取最右侧地址，不判断来源，直接使用会允许客户端伪造 IP。IPv6 的 `ipv6=` 参数（BEP 7）忽略。

### 1.4 protocol 适配（`ptt-torrust::protocol`）

#### 1.4.1 预规范化（`normalize.rs`）

torrust `Query: FromStr` 对少数非标准但常见的输入会直接报错。在交给 torrust 之前对**原始 query 字符串**做以下处理（不解码 info_hash / peer_id，只按 `&`、`=` 切分参数名）：

| 输入 | 处理 | 计数 |
|---|---|---|
| `event` 值不在 `started`/`stopped`/`completed`/`` 中（如 `paused`，BEP 21） | 删除该参数（视为 `none`） | `pt_protocol_normalized_total{kind="event"}` |
| `numwant` 非数字、负数或 > 10^6 | 删除（使用默认值） | `kind="numwant"` |
| `compact`、`no_peer_id` 非 `0`/`1` | 删除 | `kind="flag"` |
| 参数 `ip`、`ipv4`、`ipv6`、`key`、`trackerid`、`corrupt`、`supportcrypto`、`redundant`、未知参数 | 保留 `key`（不使用），其余 torrust 不识别的删除 | 不计数 |
| 同名参数重复（`info_hash` 除外） | 保留第一个 | `kind="dup_param"` |
| `info_hash` 出现多次（announce） | 不处理，解析后报 `InvalidInfoHash` | — |

#### 1.4.2 解析与映射

```rust
pub struct AnnounceReq {
    pub info_hash: InfoHash20, pub peer_id: PeerId20, pub port: u16,
    pub uploaded: u64, pub downloaded: u64, pub left: u64,      // 0 ≤ x ≤ 2^63−1
    pub event: Ev, pub compact: bool, pub no_peer_id: bool, pub numwant: Option<u32>, pub ip: Option<IpAddr>,
}
pub fn parse_announce(raw: &str) -> Result<AnnounceReq, Failure>;
```

torrust 错误到 `Failure` 的映射按**错误类型与变体**进行（`match`），任何未覆盖的变体落入 `Failure::BadRequest`；**绝不**调用 `to_string()` 把 torrust 的错误放进响应（错误中含 `Location`，即源码绝对路径，design/10 §6.3）：

| torrust 情况 | `Failure` | 文案 |
|---|---|---|
| 缺少 `info_hash` / `peer_id` / `port` | `MissingParam(InfoHash / PeerId / Port)` | `missing parameter: info_hash` 等（参数名来自固定枚举） |
| `info_hash` 解码后不是 20 字节 | `InvalidInfoHash` | `invalid info_hash` |
| `peer_id` 不是 20 字节 | `InvalidPeerId` | `invalid peer_id` |
| `port` 非数字或超范围 | `InvalidPort` | `invalid port` |
| `uploaded` / `downloaded` / `left` 非数字、负数、> 2^63−1 | `InvalidNumber(Param)` | `invalid parameter: uploaded` 等 |
| query 无法切分 / 百分号编码非法 | `BadRequest` | `invalid request` |

附加校验（torrust 不做的）：`port == 0 && event != stopped` → `InvalidPort`；缺少 `uploaded`/`downloaded`/`left` 时按 0 处理（BEP 3 必填，但部分客户端在 stopped 中省略，按 0 不会多记：0 < 旧值会被判为回退，且 stopped 只输出 Δ = 0 的那一部分）。

> 关于“缺失按 0”：若 stopped 省略了 `uploaded`，`compute` 会看到回退，在 `regress_grace` 之外标 `upload_regressed`、Δ = 0，会话删除——少记最后一段，符合“宁少记”。

#### 1.4.3 编码（`encode.rs`）

复用 torrust `responses::Announce<Compact | Normal>`、`responses::error::Error`。字段：

| 字段 | 值 |
|---|---|
| `interval` | `cfg.interval`（钳制见 §4.3）+ 抖动 `rand(0..=interval_jitter_secs)` |
| `min interval` | `cfg.min_interval` |
| `complete` / `incomplete` / `downloaded` | swarm 统计（本节点） |
| `peers` | compact：IPv4 6 字节串；非 compact：`l d7:peer id20:…2:ip…4:porti…e e`（`no_peer_id=1` 时省略 `peer id`） |
| `peers6` | compact 时 IPv6 18 字节串（BEP 7）；非 compact 时 IPv6 peer 混在 `peers` 列表中 |

失败响应：`d14:failure reason<len>:<text>e`；`Failure::Busy` 额外加键 `retry in` = 1（编码为 `8:retry ini1e`，BEP 31，单位分钟），其他失败不加。所有响应头：`Content-Type: text/plain`、`Cache-Control: no-store`；`Server` 头只含 `pt-tracker`，不带版本号以外的信息。

### 1.5 admission（准入）

#### 1.5.1 本地表

```rust
pub struct Tables {                              // 整体放在 ArcSwap<Tables> 中；增量更新通过内部分片锁
    pub pk: ShardedMap<[u8; 16], UserEntry>,     // passkey 按 hex 解码为 16 字节；64 个分片 RwLock<HashMap>
    pub t:  ShardedMap<[u8; 20], TorrentEntry>,
    pub clients: ArcSwap<CompiledRules>,
    pub cfg: ArcSwap<RuntimeCfg>,
    pub sync_id: AtomicStreamId,                 // 已应用的 trk:sync 最新 ID
}
pub struct UserEntry    { uid: u64, st: UserSt, rsn: Rsn, exp: u32, ver: i64 }        // exp = 0 表示无
pub struct TorrentEntry { tid: u64, st: TorrentSt, acct: bool, size: u64, own: u64, rsn: Rsn, exp: u32, ver: i64 }
pub enum UserSt    { Active = 0, LeechDisabled = 1, Disabled = 2, Revoked = 3 }
pub enum TorrentSt { Open = 0, OwnerOnly = 1, Disabled = 2, Deleted = 3, Replaced = 4 }
pub struct Rsn([u8; 32], u8);                    // 已校验 [a-z0-9_]{1,32}；不合法时为空
```

未知的 `st` 值（例如未来新增）：用户按 `Disabled`、种子按 `Disabled` 处理并计数 `pt_sync_unknown_value_total{field}`（拒绝优于放行）。

#### 1.5.2 用户判定

```
fn user(pk) -> Result<UserEntry, Failure>:
    e = tables.pk.get(pk) 或 miss_lookup_pk(pk)?            // §1.5.7
    if e.exp != 0 && e.exp <= now: return Err(UnregisteredPasskey)     // 墓碑已过期 = 未注册
    match e.st:
        Active | LeechDisabled → Ok(e)
        Disabled → Err(match e.rsn { "pending" → AccountPending, _ → AccountDisabled })
        Revoked  → Err(match e.rsn { "reset" → PasskeyReset, _ → PasskeyRevoked })
```

#### 1.5.3 种子判定

```
fn torrent(ih, uid) -> Result<TorrentEntry, Failure>:
    e = tables.t.get(ih) 或 miss_lookup_t(ih)?
    if e.exp != 0 && e.exp <= now: return Err(TorrentNotRegistered)
    match e.st:
        Open      → Ok(e)
        OwnerOnly → if e.own != 0 && e.own == uid { Ok(e) } else { Err(match e.rsn { "rejected" → TorrentNotApproved, _ → TorrentPending }) }
        Disabled  → Err(TorrentDisabled)
        Deleted   → Err(TorrentDeleted(e.rsn))           // 文案 "torrent deleted: <rsn>"，rsn 为空时 "torrent deleted"
        Replaced  → Err(TorrentReplaced)
```

```
fn decide(rules, peer_id: &[u8;20], ua: &[u8]) -> (Action, Option<u64>):

        if let Some(p) = r.pid_prefix  { if !peer_id.starts_with(p) { continue } }
        if let Some(p) = r.ua_prefix   { if !ua.starts_with(p) { continue } }

                if min && cmp(digits, min) < 0 { continue }
                if max && cmp(digits, max) > 0 { continue }
        return (r.action, Some(r.id))
    (rules.default, None)
```

#### 1.6.2 `TorrustSwarm::announce`

```
announce(ih, p, want):

    registry.handle_announcement(ih, &peer, None)                             // upsert / remove（stopped）
    if want.k == 0: return reply(stats_only)

    else:
```

`build_pools` 一次遍历把 peer 按 `(角色, 地址族)` 放入 4 个 `Vec<SelectedPeer>`：`S4`、`S6`（做种者：`left == 0`）、`L4`、`L6`。快照中可能含已被移除最多 `snapshot_ttl_ms` 的 peer，属于可接受的陈旧（客户端会自行跳过不可连接的 peer）。快照表为 `DashMap<InfoHash20, (Instant, Arc<Pools>)>`，`cleanup` 时移除过期项；刷新使用单飞，避免热门种子在过期瞬间被并发重建。

#### 1.6.3 选择算法（修正 torrust 按地址顺序取前 N 的问题）

```
select(pools, me, want) -> Vec<SelectedPeer>:
    fam = want.family；other = fam.other()
    if want.seeder:                                  // 做种者只需要下载者
        plan = [(L[fam], k), (L[other], k)]
    else:                                            // 下载者：做种者优先，但至少给其他下载者留一半名额
        S = |S[fam]| + |S[other]|，L = |L[fam]| + |L[other]|（扣除自己）
        s_quota = min(S, max(ceil(k/2), k − L))
        plan = [(S[fam], s_quota), (S[other], s_quota), (L[fam], k), (L[other], k), (S[fam], k), (S[other], k)]
    out = []；quota_used = {S: 0, L: 0}
    for (pool, cap) in plan:
        need = min(k − out.len(), cap − used[pool.role])
        if need == 0: continue
        take_random(pool, need, me, &mut out)        // 已取过的 pool 再次出现时只补足剩余部分
    out

take_random(pool, need, me, out):
    n = pool.len(); if n == 0 return
    start = rng.u64() % n
    step = coprime_step(n, rng)                      // 从 [1, n) 中随机取与 n 互质的步长（预计算 n 的质因数，最多 8 次尝试，失败用 1）
    for i in 0..n:                                   // 实际在取满 need 后提前结束，期望 O(need)
        c = pool[(start + i*step) % n]
        if c.addr == me.addr || c.peer_id == me.peer_id: continue
        if out.contains_addr(c.addr): continue       // 同一池二次补足时防重复（out ≤ 200，线性查找）
        out.push(c); if 已取 need: return
```

性质：

- 起点与步长均匀随机，任意 peer 被选中的概率 ≈ k/n，**与地址大小无关**（FR-PTT-015 的覆盖率检验见 TP-PTT TC-PTT-040）。
- 每次 O(k)；大 swarm 的 O(n) 只发生在快照刷新时（每种子每 3 s 至多一次）。
- 优先返回与请求者同地址族的 peer，不足再用另一族填充（双栈客户端可用）；同族不足而另一族有余时仍能拿满 k。
- 排除自己：同时比较地址与 peer_id（torrust 以地址为键，同地址不同 peer_id 已在 swarm 中互相覆盖，R4）。

随机数：每个 tokio worker 线程一个 `SmallRng`（`thread_local!`，启动时用 OS 熵播种），不加锁。

### 1.7 懒加载重建（`ptt-server::rebuild`，FR-PTT-017、FR-PTT-032）

```rust
struct Rebuild { marks: LruTtl<InfoHash20, ()>, inflight: SingleFlight<InfoHash20, ()>, state: StateStore, swarm, queues }

async fn ensure(&self, ih, acct: bool):
    if !acct || marks.contains(ih) { return }                       // acct=0 的 hash 没有 ps:*（DD-PTT-15）
    let fut = inflight.run(ih, || async {
        marks.insert(ih, ttl = mpt)                                  // 先标记：失败也不重复尝试（每 hash 每节点一次 / mpt）
        n = state.hlen(ih).await?                                    // HLEN ps:<ih>
        if n == 0 { return }
        if n <= rebuild_inline_max_fields (2000) {
            fields = state.hgetall(ih).await?
            apply(ih, fields).await
        } else {
            spawn(background_scan(ih))                               // HSCAN COUNT 500，每批 apply；本次不等待
        }
    });
    let _ = timeout(rebuild_timeout_ms (100), fut).await;           // 超时：本次请求不等待，单飞任务继续执行完

async fn apply(ih, fields):
    cutoff = now − mpt；peers = []；preload = [[]; K]
    for (field, value) in fields:
        (uid, pid) = parse_field(field)?；st = ps_codec::decode(value)?       // fmt 未知 → 跳过并计数
        if st.last_ts < cutoff { continue }
        peers.push(SwarmPeer { peer_id: pid, addr: (st.ip, st.port), uploaded: st.up, downloaded: st.down, left: st.left,
                               event: None, updated: st.last_ts })
        key = SessionKey { uid, ih, pid }；preload[key.worker(K)].push((key, st))
    swarm.restore(ih, &peers)
    for i in 0..K: queues[i].try_send(WorkerMsg::Preload(preload[i]))      // 满则丢弃（只是缓存预热，worker 未命中时会自己 HMGET）
    metrics: pt_swarm_rebuild_total{result}、pt_swarm_rebuild_peers += peers.len()
```

worker 处理 `Preload`：对每个会话 `cache.insert_if_absent`（已有更新的状态时不覆盖）。

**迁移语义**：新节点首次见到某 hash 时恢复 swarm 与状态缓存；旧节点不再收到该 hash 的请求，其 swarm 在 mpt 后被清理。迁移窗口内若同一会话的请求在两节点交错（LB 规则变化瞬间），两边的 CAS 只有一方成功，另一方重算（§1.9.3）。

### 1.8 记账：增量算法与 worker

#### 1.8.1 类型（`ptt-types::session`）

#### 1.8.2 `compute()`（`ptt-core::accounting`，纯函数）

```
fn compute(prev: Option<&PeerState>, r: &Report, size: u64, p: &Policy) -> Outcome:
    f = 0
    if size > 0 && r.left > size { f |= LEFT_EXCEEDS_SIZE }
    let completes = |was_completed, prev_left: Option<u64>| -> bool:
        !was_completed && r.left == 0 && (r.ev == Completed || prev_left.is_some_and(|l| l > 0))
        // event=completed 但 left>0 不算完成；会话内 left 由 >0 变 0 视为完成（DD-PTT-12）

    match prev:
      None:                                                         // 首见
        f |= FIRST_SEEN
        (dup, ddown) = (0, 0); if r.ev != Started || r.up != 0 || r.down != 0 { f |= BASELINE_RESET }
        (dseed, dleech) = (0, 0)
        done = completes(false, None)
        started_ts = r.now
        ver = 1
      Some(s) if r.ev == Started:                                    // 有旧状态又收到 started：新会话（DD-PTT-13）
        dup   = if r.up   >= s.up   { r.up   - s.up   } else { r.up   }    // 计数器已归零 → 按上报值
        ddown = if r.down >= s.down { r.down - s.down } else { r.down }
        (dseed, dleech) = (0, 0)                                     // 停机期间不计时长
        done = completes(s.completed, Some(s.left))
        started_ts = r.now
        ver = s.ver.next()
      Some(s):
        reg_up = r.up < s.up；reg_down = r.down < s.down
        if (reg_up || reg_down) && r.now <= s.last_ts + p.regress_grace: return Discard(OutOfOrder)   // DD-PTT-14
        if r.now + p.regress_grace < s.last_ts:                    return Discard(Stale)
        dup   = if reg_up   { f |= UPLOAD_REGRESSED;   0 } else { r.up   - s.up }
        ddown = if reg_down { f |= DOWNLOAD_REGRESSED; 0 } else { r.down - s.down }
        elapsed = r.now.saturating_sub(s.last_ts)
        counted = if elapsed > p.max_interval { f |= SEED_TIME_CAPPED; p.max_interval } else { elapsed }
        (dseed, dleech) = if s.left == 0 { (counted, 0) } else { (0, counted) }    // 时长记到上一次的角色
        done = completes(s.completed, Some(s.left))
        started_ts = s.started_ts
        ver = s.ver.next()
    if done { f |= FIRST_COMPLETED }
    next = if r.ev == Stopped { None } else {
        Some(PeerState { up: r.up, down: r.down, left: r.left, last_ts: r.now, started_ts,
                         completed: prev.is_some_and(|s| s.completed) || done, ip: r.ip, port: r.port, ver })
    }
    Apply { delta: Delta { up: dup, down: ddown, seed: dseed, leech: dleech, flags: f }, next }

u32::next(v) = if v == u32::MAX { 1 } else { v + 1 }
```

`ver` 只用于 CAS 比较，不参与语义；跨过 `u32::MAX` 后回到 1（同一会话需要 40 亿次 announce 才会回绕）。

#### 1.8.4 worker

```rust
enum WorkerMsg { Fact(AnnounceFact), Preload(Vec<(SessionKey, PeerState)>), Flush(oneshot::Sender<()>) }
struct Worker { id: usize, rx: mpsc::Receiver<WorkerMsg>, cache: SessionCache, state: StateStore, sink: Sink,
                breaker: Breaker, policy: Policy, metrics }
```

队列：每个 worker 一个 `tokio::sync::mpsc::channel(queue_capacity / K)`；请求路径用 `try_reserve()` 取得 `Permit` 后再 `send`（DD-PTT-3）。

```
loop:
    batch = rx.recv_many(batch_max = 256)，若不足则最多再等 batch_linger_ms (2 ms)
    处理 Preload（insert_if_absent）与 Flush（记下，在本批完成后回复）
    facts = 本批 Fact，保持到达顺序
    if breaker.open(): 全部 drop（pt_accounting_dropped_total{reason="state_unavailable"}）；continue

    // ① 读旧状态：缓存未命中的会话按 ih 分组
    misses = facts 中 cache.get(key) == None 且不在本批前面已出现的 key
    if misses 非空:
        r = state.hmget_grouped(misses)                        // pipeline：每个 ih 一条 HMGET ps:<ih> f1 f2 …
        Err → breaker.trip()；本批全部 drop；continue
        for (key, v) in r: v 为 Some → cache.insert(key, decode(v))；None → overlay[key] = Absent

    // ② 计算（overlay 处理同一批内同一会话出现多次的情况）
    plans = []
    for f in facts:
        prev = overlay.get(f.key).or(cache.get(f.key))
        match compute(prev, &f.report(), f.size, &policy):
            Discard(r) → metrics.discarded(r)；continue
            Apply{delta, next} →
                expected = prev.map_or(0, |s| s.ver)
                plans.push(Plan { f, expected, next, delta })
                overlay[f.key] = next.map_or(Absent, Present)

    // ③ CAS
    results = state.cas_pipeline(plans)                        // 每个 plan 一条 EVALSHA ps_cas（§3.6）
    Err（连接错误 / 超时，整体结果未知）→ breaker.trip()；对这些 key cache.remove()；全部 drop；continue
    ok = []
    for (plan, res) in zip(plans, results):
        match res:
            Ok                → ok.push(plan)
            Conflict(current) → metrics.cas_conflict()
                                // 同一批后面依赖本 plan 的同 key plan 也会冲突，依次在这里重算
                                retry = recompute(plan.f, current)      // compute(current.map(decode), …)
                                再 CAS 一次（单条，同步）：Ok → ok.push(retry)；Conflict/Err → cache.remove(key)；
                                    metrics.cas_giveup()；放弃本次增量（宁少记）
    for p in ok: match p.next { Some(s) → cache.put(p.f.key, s), None → cache.remove(p.f.key) }

    // ④ 输出
    events = ok.filter(should_emit).map(to_traffic_event)     // eid 在这里分配：seq.fetch_add(1)
    sink.write(events).await                                   // §1.10：内部重试直到成功或进入退出流程；期间 worker 阻塞
    回复本批中的 Flush
```

`should_emit(p) = cfg.emit_zero_delta || p.delta.up | down | seed | leech != 0 || p.f.ev != None || p.delta.flags != 0`。`emit_zero_delta` 取 `trk:cfg.emit_zero_delta`，未下发时取本地配置默认值。

**熔断**（`Breaker`）：`tracker_state` 出错后打开 `state.circuit_open_secs`（5 s），期间新事实直接丢弃；到期后半开，放行下一批，成功则关闭。熔断期间 announce 正常响应（NFR-PTT-008），`pt_state_circuit_open` gauge = 1。

**会话缓存**（`SessionCache`，worker 独占，无锁）：`HashMap<SessionKey, (PeerState, lru_tick)>` + 近似 LRU（CLOCK 算法），容量 `state.cache_capacity / K`。每 60 s 扫描 1/60 的桶，删除 `last_ts < now − 2 × mpt` 的项。

**为什么同一会话的事实不会乱序**：同一 `SessionKey` 永远进入同一个 worker 的 FIFO 队列；worker 按到达顺序处理；同一批内用 overlay 串联。跨节点的交错由 CAS + E8/E9 处理。

### 1.9 会话状态存储（`ptt-redis::state`）

#### 1.9.1 键与字段

- 键：`ps:<info_hash 40 位小写 hex>`；字段：`<uid 十进制>:<peer_id 40 位小写 hex>`；值：§3.4 的 40 / 52 字节二进制。
- 键 TTL 与字段 TTL：`state.key_ttl_secs` / `state.field_ttl_secs`，默认均为 `2 × mpt` = 5400 s（redis-keys.md：`max_peer_timeout × 2`）。每次写入刷新两者；字段 TTL 由 `HEXPIRE` 设置（Redis ≥ 7.4），因此热门种子的键永不过期时，陈旧会话字段也会自行消失。
- 删除（stopped）：`HDEL`。

#### 1.9.2 读取

| 场景 | 命令 |
|---|---|
| worker 未命中 | `HMGET ps:<ih> <f1> <f2> …`（同一 ih 合并；pipeline 多个 ih） |
| 懒加载 | `HLEN ps:<ih>`；`HGETALL ps:<ih>` 或 `HSCAN ps:<ih> <cursor> COUNT 500` |

Cluster：`tracker_state` 可为 Cluster；同一 ih 的全部操作只涉及一个键（一个槽），pipeline 由客户端按节点拆分（`redis::cluster_async`）。

#### 1.9.3 CAS 与冲突

脚本见 §3.6。返回：`{1}` 成功；`{0, <当前值>}` 冲突（当前存在）；`{0}` 冲突（当前不存在而期望存在）。

冲突的典型来源与处理：

| 来源 | 现象 | 处理结果 |
|---|---|---|
| 分片迁移，另一节点处理过该会话 | Redis ver 大于本地 | 用 Redis 值重算 → 通常是正常差值，不重复 |
| 本地缓存陈旧（另一节点处理 stopped 删除了字段） | 期望存在、当前不存在 | 按首见重算 → `baseline_reset` |
| 字段 TTL 过期 | 同上 | 同上 |
| 上一次 CAS 超时但实际已执行（E29） | Redis ver = 本地 ver + 1，值为“上一次”的新状态 | 用它重算 → 上一次的 Δ 已丢（少记），本次正常 |
| 乱序（另一节点处理了更新的上报） | 重算时触发 E8/E9 | 丢弃本次 |

### 1.10 流量事件出口（`ptt-redis::sink`）

#### 1.10.1 一个事件的命令

```
XADD acct:<uid % N> MAXLEN ~ <stream_maxlen> * v 1 eid <eid> ts <ts> uid <uid> tid <tid> ih <ih> pid <pid>
     ip <ip> port <port> ev <ev> up <up> down <down> left <left> dup <dup> ddown <ddown> dseed <dseed> dleech <dleech>
     flags <flags> ua <ua>
HINCRBY u:<uid>:live up <dup>              （dup > 0 时）
HINCRBY u:<uid>:live down <ddown>          （ddown > 0 时）
HINCRBY u:<uid>:live seed_time <dseed>     （dseed > 0 时）
EXPIRE  u:<uid>:live 604800                （本节点对该 uid 距上次刷新 ≥ live_ttl_refresh_secs 时，HLD §7 N-9）
```

字段见 §3.5。`eid = <node_id>:<boot_epoch>:<seq>`，`seq` 是进程内 `AtomicU64`（从 1 开始），在事件生成时分配，重试不改变。

#### 1.10.2 批量与重试

```
write(events):
    attempt = 0；pending = events.map(|e| (e, first = true))
    loop:
        cmds = for (e, first) in pending: XADD …；if first: HINCRBY …、EXPIRE …
        r = acct.pipeline(cmds, atomic = false).timeout(redis.command_timeout_ms)
        match r:
            全部成功 → return
            部分回复（连接中途断开 / 超时）→ 已确认成功的 XADD 移出 pending；其余 pending 标记 first = false
            连接错误（请求未发出，如连接被拒）→ first 保持不变
            Redis 错误回复（OOM、NOPERM 等）→ 记录 ERROR；按“连接错误”处理（同一事件稍后重试）
        attempt += 1；sleep(backoff(attempt))       // 10 ms × 2^n，上限 1 s，抖动 ±20%
        if shutdown.deadline_passed(): metrics.sink_abandoned(pending.len())；return
```

- “first = false”的事件重试时只发 XADD（同 `eid`），不再发 HINCRBY：若第一次实际已执行，accounting 按 `eid` 去重，实时计数不重复；若未执行，实时计数少一笔（展示用，accounting 扣减时截断到 0）。
- worker 在 `write` 内阻塞期间不再从队列取消息，队列积压直到 `try_reserve` 失败 → `tracker busy`（FR-PTT-020、NFR-PTT-006）。恢复后自动追上。
- `acct` 为 Cluster 时，`acct:<p>` 与 `u:<uid>:live` 可能在不同槽位；非原子 pipeline 由客户端按节点拆分，语义不变。

### 1.11 同步（`ptt-redis::sync_*` + `ptt-server::sync_rt`）

#### 1.11.1 启动加载（FR-PTT-025）

```
initial_load():
    L = XREVRANGE trk:sync + - COUNT 1 → id，空流为 "0-0"
    new = Tables::empty()
    for pattern in ["trk:pk:*", "trk:t:*"]:
        cursor = 0
        loop: (cursor, keys) = SCAN cursor MATCH pattern COUNT 1000 TYPE hash
              pipeline HGETALL keys → decode → new.upsert_if_newer
              break if cursor == 0
    new.clients = compile(GET trk:clients)  缺失 → NotReady("clients_missing")（重试，不就绪）
    new.cfg     = decode(HGETALL trk:cfg)   缺失 → NotReady("cfg_missing")
    tables.swap(new)；tables.sync_id = L；ready.mark_loaded()
    整体超时 sync.initial_load_timeout_secs（120 s）→ 重试（指数退避），期间 /ready 503、announce busy
```

`SCAN … TYPE hash` 过滤掉同前缀下的非 hash 键；键名解析失败（如 `trk:pk:` 后不是 32 位 hex）跳过并计数。ACL 不允许读取 `trk:u:*`，因此 MATCH 必须精确（`trk:pk:*` 不会匹配 `trk:u:*`）。

#### 1.11.2 变更流消费（FR-PTT-026）

```
loop:
    r = XREAD BLOCK sync.xread_block_ms COUNT sync.xread_count STREAMS trk:sync <tables.sync_id>
    Err → 退避重连（NFR-PTT-007：本地表继续服务）；重连后先执行 gap_check
    for (id, {kind, key, op, ver}) in r:
        match kind:
          "pk"      → neg_pk.remove(key)；batch_pk.push(key, ver)
          "t"       → neg_t.remove(key)；batch_t.push(key, ver)
          "clients" → 重读 GET trk:clients → 解析 ver > 本地才编译替换
          "cfg"     → 重读 HGETALL trk:cfg → ver > 本地才替换；校验（§4.3）
          "all"     → op == "reload" → full_reload()；（本批剩余消息仍照常应用）
          其他      → 计数 unknown，忽略
    pipeline HGETALL 所有 batch_pk / batch_t 的键（去重）
    for each (key, msg_ver, h):
        if h 存在: e = decode(h)；if e.ver > local.ver: upsert
        else:      if local.ver ≤ msg_ver: remove(key)                 // 删除或过期
    tables.sync_id = r.last_id；last_apply_lag = now_ms − id_ms(r.last_id)
```

`op` 字段（`upsert` / `delete`）只用于日志与指标——处理统一为“重读快照键并按 `ver` 决定”，因此丢失、重复、乱序的流消息都无害（tracker-bridge HLD §1 原则 2）。

#### 1.11.3 缺口检测与全量重载（FR-PTT-027）

```
gap_check（每 5 s 及每次重连后）:
    info = XINFO STREAM trk:sync
    if info.last_generated_id < tables.sync_id: reason = "stream_reset"        // 流被删除重建
    elif info.max_deleted_entry_id > tables.sync_id: reason = "trimmed"       // 游标之后有条目被修剪
    else return
    full_reload(reason)

full_reload(reason):
    if reloading: return（合并）
    L2 = XREVRANGE trk:sync + - COUNT 1；replay = BoundedVec(sync.reload_replay_buffer = 100,000)
    消费循环继续运行：消息照常应用到旧表，同时 push 到 replay（溢出 → 放弃本轮，稍后重新开始）
    后台按 §1.11.1 构建 new（不改变就绪状态）
    swap(new)；sync_id = max(L2, 当前游标)；对 new 重放 replay 中 id > L2 的消息
    metrics: pt_sync_full_reload_total{reason}
```

`max-deleted-entry-id` 需要 Redis ≥ 7.0；`tracker_sync` 低于 7.0 时退化为“游标 < `first-entry` 且游标 ≠ 0-0”判断（可能把“流中正好没有新消息”误判为无缺口，安全方向）。

#### 1.11.4 墓碑过期（FR-PTT-028）

查询时 `exp ≤ now` 即视为不存在（§1.5.2、§1.5.3）；`tombstone_purge` 任务每 60 s 遍历一个分片（64 分钟遍历完一轮）删除过期条目，只为回收内存。

#### 1.11.5 运行参数生效

`trk:cfg` 替换后立即对新请求生效（`interval`、`min_interval`、`max_peers`、`max_numwant`、`emit_zero_delta`、各开关、`port_blacklist`）。未知字段忽略；字段缺失或非法时取本地配置默认值并计数 `pt_sync_apply_errors_total{kind="cfg"}`。

### 1.12 分片与负载均衡

#### 1.12.1 一致性哈希的输入

LB 与节点使用同一个哈希输入：**URL 解码后的 20 字节 info_hash**。解码规则：`%XX`（大小写均可）→ 字节；其他字符按字面字节（包括 `+`，**不**解释为空格）。这与 torrust 解析结果一致（TP-PTT V5 用测试向量验证）。

#### 1.12.2 HAProxy 模板（首选，V5 验证）

```haproxy
# deploy/haproxy/pt-tracker.cfg（HAProxy ≥ 2.6）
frontend tracker
    bind :443 ssl crt /etc/haproxy/tracker.pem alpn http/1.1
    mode http
    option http-keep-alive
    http-request set-var(txn.ih) url_param(info_hash),url_dec        # 不带 in_form 参数：'+' 不转为空格
    # 访问日志中去掉路径（含 passkey）与 query
    log-format "%ci %tr %ST %B %Tt %b/%s"
    default_backend pt_tracker

backend pt_tracker
    mode http
    balance hash var(txn.ih)
    hash-type consistent sdbm avalanche
    hash-balance-factor 0
    option httpchk GET /ready
    http-check expect status 200
    http-request set-header X-Forwarded-For %[src]
    server trk-1 10.0.0.11:7070 check inter 1s fall 3 rise 2
    server trk-2 10.0.0.12:7070 check inter 1s fall 3 rise 2
    server trk-3 10.0.0.13:7070 check inter 1s fall 3 rise 2
```

缺少 `info_hash`（scrape 也带 info_hash；只有 `/`、`/health`、`/source` 没有）时 HAProxy 按轮询回退，不影响正确性。待验证：`url_dec` 输出对含 `%00` 的二进制是否完整参与哈希、`var()` 作为 `balance hash` 表达式的行为（V5）。

#### 1.12.3 备选：`pt-tracker route`（pt-ring-v1）

```
pt-ring-v1：
    owner(ih20, nodes) = argmax_{n ∈ nodes} score(n, ih20)，平分时取 node_id 字典序较小者
    score(n, ih20) = xxh3_64_with_seed(ih20, seed = xxh3_64(n.id 的 UTF-8 字节))
```

- HRW（rendezvous）哈希：增删一个节点只移动约 1/M 的种子；无需虚拟节点；M ≤ 64 时每次计算 < 1 µs。
- `route` 进程：hyper 反向代理；只解析 query 中第一个 `info_hash` 并按 §1.12.1 解码；只在健康后端集合（每秒 `GET /ready`）中取 owner；追加 `X-Forwarded-For`；连接池复用；不解析也不记录 passkey。缺少或非法 `info_hash` → 按 passkey 段的 xxh3 选择（scrape/announce 的错误由节点返回）。
- `route` 本身无状态，可多实例部署在 L4 负载均衡之后。

#### 1.12.4 节点侧错误路由计数（FR-PTT-030）

`shard.mode = "ring"`（使用 `route` 或其他实现了 pt-ring-v1 的 LB）时：节点按 `shard.nodes` 计算 owner，`owner ≠ node_id` → `pt_misrouted_total{reason="not_owner"}` +1，**照常处理**（CAS 保证正确，不转发）。由于节点不知道 LB 侧的健康状态，某节点下线期间其他节点的计数会上升，告警需结合 `nodes_online`。

`shard.mode = "none"`（HAProxy 原生哈希，算法不可在节点复现）时不计算 owner；改用间接指标：稳态下 `pt_peer_state_cas_conflict_total` 与 `pt_swarm_rebuild_total` 的速率（应接近 0）。

### 1.13 节点状态与统计（`stats`）

#### 1.13.1 节点状态（FR-PTT-033）

每 10 s：

```
HSET trk:stats:node:<node_id> ver <crate 版本>+<torrust rev 前 8 位> boot <boot_epoch> sid <tables.sync_id>
     lag_ms <最近 10 s 内应用消息的最大 (apply_ms − id_ms)，无消息为 0> pk <passkey 表条目数> t <种子表条目数>
     peers <swarm peer 数> torrents <swarm 数> mpt <max_peer_timeout> rps <最近 60 s 平均 announce/s> ts <now>
EXPIRE trk:stats:node:<node_id> 30
```

字段与 tracker-bridge LLD §1.9 一致。写入失败只计数，不影响服务。

#### 1.13.2 被拒客户端（FR-PTT-012）

每 `stats.denied_flush_secs`（10 s）：交换出本地计数表 → pipeline `ZINCRBY trk:stats:denied:<UTC yyyymmdd> <count> <member>` ×n；当天第一次写某日期键时追加 `EXPIRE … 691200`（8 天）。写入失败：把计数合并回本地表（上限同 §1.5.6），下次再写。

### 1.14 健康、就绪与退出

#### 1.14.1 `/health`

进程存活即 200 `ok`。

#### 1.14.2 `/ready`

```json
200 {"ready": true}
503 {"ready": false, "reasons": ["initial_load", "acct_unavailable", "queue_high", "draining"]}
```

| 条件 | 说明 |
|---|---|
| `initial_load` | 首次加载未完成（FR-PTT-029） |
| `acct_unavailable` | `acct` 连续 5 s 不可达（PING 失败或 sink 连续失败） |
| `queue_high` | 任一 worker 队列使用率 ≥ 90% |
| `draining` | 收到 SIGTERM |

`tracker_sync`、`tracker_state` 不可用**不**影响就绪（DD-PTT-19），在指标中体现。

#### 1.14.3 退出（FR-PTT-036）

```
SIGTERM / SIGINT:
  ready.set_draining()                                  // /ready 503，LB 开始摘除
  sleep(shutdown.drain_secs = 10)
  停止 accept；等待在途请求完成（最长 5 s）
  queues 关闭入口（之后的请求不会再来）
  向每个 worker 发送 Flush 并等待，总时长 ≤ shutdown.flush_secs (30 s)
  写最后一次节点状态（ts 更新）；退出码 0
  若期限内未完成：记录 pt_shutdown_abandoned_total（条数），退出码 0
第二次 SIGTERM：立即退出
```

### 3.1 读取：`trk:*`（tracker_sync，tracker-bridge 写入）

### 3.4 `ps:<info_hash>`（tracker_state，契约）

- 字段：`<uid 十进制>:<peer_id 40 位小写 hex>`
- 值（大端，`fmt = 1`，与 tracker-bridge LLD §1.10 一致）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `fmt` | 1 |
| 1 | 1 | `flags` | bit0 completed、bit1 ipv6、bit2 seeder（left = 0）；其余位 0 |
| 2 | 2 | `port` | |
| 4 | 4 | `ver` | CAS 版本（1..=u32::MAX） |
| 8 | 8 | `uploaded` | 最近一次被接受的累计值 |
| 16 | 8 | `downloaded` | |
| 24 | 8 | `left` | |
| 32 | 4 | `last_ts` | Unix 秒 |
| 36 | 4 | `started_ts` | 会话开始（首见或最近一次 started） |
| 40 | 4 / 16 | IP | v4 / v6（bit1） |

总长 44 或 56 字节。偏移 0～7 的头部布局对所有未来的 `fmt` 保持不变（HLD §7 N-3），CAS 脚本只依赖偏移 4 的 `ver`。解码时：长度不符、`fmt ≠ 1` → 视为“不可用”（跳过、计数 `pt_state_decode_errors_total`），CAS 时按 `ver` 头部比较仍然有效。

TTL：键 `EXPIRE 2 × mpt`；字段 `HEXPIRE 2 × mpt`（每次写入刷新）。

容量（集群全量）：3000 万字段 × (47 B 字段名 + 44 B 值 + ~40 B 内部开销 + 字段 TTL 元数据 ~16 B) ≈ 4.4 GB（design/10 §5.6 估算约 4 GB，V1 实测校正）。

### 3.5 `acct:<partition>` 与 `u:<uid>:live`（acct，契约）

#### 3.5.1 流量事件字段（`XADD acct:<uid % N>`，字段顺序固定）

| # | 字段 | 编码 | 说明 |
|---|---|---|---|
| 1 | `v` | `1` | 格式版本 |
| 2 | `eid` | `<node_id>:<boot_epoch>:<seq>` | node_id `[a-z0-9-]{1,32}`；boot_epoch、seq 十进制；全长 ≤ 64 |
| 3 | `ts` | 十进制 Unix 秒 | announce 被接受的时间 |
| 4 | `uid` | 十进制 u64 | `uid % N == partition` |
| 5 | `tid` | 十进制 u64 | 来自 `trk:t.tid` |
| 6 | `ih` | 40 位小写 hex | 被 announce 的 hash（acct=1 的那个） |
| 7 | `pid` | 40 位小写 hex | peer_id |
| 8 | `ip` | IPv4 点分 / IPv6 RFC 5952 压缩形式 | 敏感，accounting 解析时丢弃 |
| 9 | `port` | 十进制 | |
| 10 | `ev` | `started` / `stopped` / `completed` / `none` | 小写；如实上报客户端的 event（含 `completed` 但 `left > 0` 的情况） |
| 11 | `up` | 十进制 u64 | 上报的累计值 |
| 12 | `down` | 十进制 u64 | |
| 13 | `left` | 十进制 u64 | |
| 14 | `dup` | 十进制 u64 | 增量 |
| 15 | `ddown` | 十进制 u64 | |
| 16 | `dseed` | 十进制 | 做种时长增量（秒，≤ mpt） |
| 17 | `dleech` | 十进制 | 下载时长增量（秒，≤ mpt） |
| 18 | `flags` | 十进制 u32 位掩码 | bit0 first_seen、bit1 baseline_reset、bit2 upload_regressed、bit3 download_regressed、bit4 first_completed、bit5 seed_time_capped、**bit6 left_exceeds_size（新增）**、bit7 speed_exceeded（该段流量已置 0）；其余保留为 0 |
| 19 | `ua` | UTF-8，≤ 128 字节 | 按 UTF-8 边界截断；非法 UTF-8 以 U+FFFD 替换；控制字符删除；缺失为空串 |

与 accounting LLD §1.1.2 的校验对照：`dseed + dleech ≤ 86400`（本实现恒 ≤ mpt ≤ 7200）；`dup, ddown ≤ 2^50`（本实现不截断；客户端上报的巨大跳变会产生更大的值，由 accounting 以 `out_of_range` 拒收并产生 `counter_jump` 信号——这是有意的：tracker 不判定）。原型中的 `node`、`seq` 字段与 JSON 形式的 `flags` **不再输出**。

#### 3.5.2 输出条件

见 §1.8.4 `should_emit`。`emit_zero_delta = false` 时，只有“同一秒内重复、无 event、无 flags”的 announce 被省略；周期 announce 几乎总有 `dseed` 或 `dleech > 0`，因此 accounting 的活跃 peer 判断（accounting DD-ACC-6）不受影响。

| 字段 | 写入 | 说明 |
|---|---|---|
| `up` | `HINCRBY +dup` | 原始值，不乘倍率 |
| `down` | `HINCRBY +ddown` | |
| `seed_time` | `HINCRBY +dseed` | 秒 |
| `aid`、`sid` | 不写 | accounting 的扣减标记 |

### 3.6 Lua 脚本 `ps_cas`

```lua
-- SPDX-License-Identifier: AGPL-3.0-only
-- KEYS[1] = ps:<ih>
-- ARGV[1] = 字段 <uid>:<pid hex>
-- ARGV[2] = 期望 ver（0 = 期望不存在）
-- ARGV[3] = 新值（二进制；空串 = 删除）
-- ARGV[4] = 键 TTL（秒）
-- ARGV[5] = 字段 TTL（秒）
local cur = redis.call('HGET', KEYS[1], ARGV[1])
local curver = 0
if cur then
  if string.len(cur) >= 8 then
    curver = struct.unpack('>I4', cur, 5)
  else
    curver = -1                                   -- 损坏：任何期望都冲突，由调用方按“当前值不可用”重算
  end
end
if curver ~= tonumber(ARGV[2]) then
  if cur then return {0, cur} else return {0} end
end
if ARGV[3] == '' then
  redis.call('HDEL', KEYS[1], ARGV[1])
else
  redis.call('HSET', KEYS[1], ARGV[1], ARGV[3])
  redis.call('HEXPIRE', KEYS[1], tonumber(ARGV[5]), 'FIELDS', 1, ARGV[1])
end
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[4]))
return {1}
```

- 加载：启动时 `SCRIPT LOAD`，缓存 SHA；`NOSCRIPT`（Redis 重启 / failover）时重新加载并重试一次。
- 损坏值（长度 < 8，`curver = -1`）：任何期望都不匹配，脚本返回冲突与当前值；调用方解码失败时先执行 `HDEL ps:<ih> <field>`，再以期望 0 按首见（`prev = None`，结果为 `baseline_reset`）重试一次，计数 `pt_state_decode_errors_total{action="reset"}`。
- 脚本只访问一个键，符合 Cluster 要求。

### 3.7 Redis 写入量估算（集群峰值 5 万次/秒）

| 实例 | 每次 announce | 峰值 ops/s | 说明 |
|---|---|---|---|
| tracker_state | 1 EVALSHA（脚本内 HGET + HSET + HEXPIRE + EXPIRE） | 5 万脚本/s | 未命中时另有 HMGET（稳态 < 1%）；建议 3 分片 Cluster（V1 实测） |
| acct | 1 XADD + 0～3 HINCRBY（典型 1：纯做种只有 seed_time）+ 偶尔 EXPIRE | 约 11 万命令/s | pipeline 批量；V1 实测单实例上限 |
| tracker_sync | 回源 HGETALL（受限速）、XREAD、10 s 一次统计 | < 1000/s | |

## 6. 安全设计

### 6.1 敏感数据

| 数据 | 处理 |
|---|---|
| passkey | 只存在于本地表（16 字节）与请求处理的栈上；日志只输出前 4 位（`0123…`）；不进指标标签、失败文案、节点状态、被拒统计；HTTP 访问日志不记录路径（pt-tracker 自身不输出访问日志；HAProxy 模板的 `log-format` 不含路径） |
| IP | 只出现在 swarm、`ps:*` 值、`acct:*` 的 `ip` 字段（Redis ACL 保护，accounting 解析时丢弃）；info 级日志不输出 IP；debug 级输出时截断为 /24、/48 |
| UA | 截断到 128 字节进入流；被拒统计只用前 32 字节 |
| Redis 密码 | 只经环境变量；`check-config` 打码；错误日志中的 URL 去掉 userinfo |

### 6.2 Redis ACL 模板（`deploy/redis/acl-pt-tracker.conf`）

```
# tracker_sync 实例
user pt-tracker on >${PT_TRACKER_SYNC_PASSWORD} resetkeys resetchannels -@all
     %R~trk:pk:* %R~trk:t:* %R~trk:clients %R~trk:cfg %R~trk:sync %RW~trk:stats:*
     +ping +hello +auth +client|setname +info +scan +get +hgetall +xread +xrevrange +xinfo|stream
     +hset +expire +zincrby
# tracker_state 实例
user pt-tracker on >${PT_TRACKER_STATE_PASSWORD} resetkeys -@all ~ps:*
     +ping +hello +auth +client|setname +info +hget +hmget +hgetall +hlen +hscan +evalsha +script|load
     +hset +hdel +hexpire +expire                 # 脚本内调用的命令同样受 ACL 检查
# acct 实例
user pt-tracker on >${PT_TRACKER_ACCT_PASSWORD} resetkeys -@all ~acct:* ~u:*:live
     +ping +hello +auth +client|setname +info +xadd +exists +xinfo|stream +hincrby +expire +hsetnx +hset +hget
```

注意 `~u:*:live` 模式也会匹配 `u:x:y:live` 形式的键，只是 pt-tracker 不会生成这样的键名（uid 为十进制）。

### 6.3 输入校验

- query ≤ `http.max_query_bytes`；请求头总量 ≤ 8 KiB（hyper）；不接受请求体。
- 所有数值参数做上下界检查（§1.4.2）；`info_hash`、`peer_id` 必须恰为 20 字节；passkey 严格 32 位小写 hex（大写视为非法，避免同一 passkey 两种写法）。
- 来自 Redis 的数据同样校验（§3.1），`rsn` 字符集限制，防止 tracker-bridge 被攻破后向 BT 客户端注入任意文本。
- 客户端规则正则使用线性时间引擎并限制编译大小（与 tracker-bridge 一致）。

### 6.4 抗滥用

- passkey / 种子回源：负缓存 + 每节点令牌桶 + 单飞（NFR-PTT-012）。
- 可选单 passkey 限速；连接数上限；hyper 读超时防慢速攻击。
- 失败文案不区分“passkey 不存在”和“回源被限速”。

## 7. 性能设计

### 7.1 热路径预算（单次 announce，release 构建，单核）

| 步骤 | 预算 | 说明 |
|---|---|---|
| hyper 读请求、路由 | 8 µs | keep-alive |
| 预规范化 + torrust 解析 | 3 µs | |
| 请求头检查 | 0.5 µs | |
| passkey / 种子查表（分片 RwLock 读） | 0.5 µs | |
| 客户端规则（典型 20 条，前缀优先） | 1～3 µs | 500 条正则最坏 ≈ 30 µs（TP 测量） |
| swarm upsert（每种子 tokio Mutex） | 1～2 µs | |
| 选择 k = 50 | 2 µs | 小 swarm 另含 O(n ≤ 512) 分池 ≈ 5 µs |
| try_reserve + send | 0.3 µs | |
| 编码 + 写响应 | 5 µs | |
| **合计** | **≈ 25～35 µs** | 8 vCPU ≈ 22～32 万次/秒理论值；NFR-PTT-001 目标 2.5 万次/秒、CPU ≤ 80% 有 > 5 倍余量（留给内核网络栈、TLS、GC 外的抖动） |

### 7.2 记账吞吐

- 每节点 2.5 万事实/s，K = 8 → 每 worker 约 3100/s；批 256 → 约 12 批/s/worker，每批 1 次 state pipeline + 1 次 acct pipeline（RTT 0.3～1 ms）→ worker 利用率 < 5%，余量充足。
- 记账延迟（NFR-PTT-004，响应到 XADD 完成）：排队（≤ batch_linger 2 ms）+ 两次 pipeline RTT（~2 ms）→ p99 目标 ≤ 50 ms，远低于 2 s 指标。

### 7.3 容量

- 单节点内存见 §3.3（≈ 3.3 GB / 1000 万 peer）。
- 集群：3000 万 peer / 3 节点 = 每节点 1000 万；峰值 5 万次/秒 / 3 = 每节点 1.7 万次/秒（NFR-PTT-003 目标 3 节点 ≥ 5 万次/秒）。
- 重启风暴：节点重启后，其负责的种子在 mpt 内陆续懒加载；首个 announce 内联加载 ≤ 2000 字段（HGETALL ~1 ms / 1000 字段）。

### 7.4 已知 O(n) 点

| 点 | 频率 | 缓解 |
|---|---|---|
| 大 swarm 的选择快照刷新 | 每种子 ≤ 1 次 / 3 s | 单飞；10 万 peer 刷新 ≈ 3 ms |
| `remove_inactive_peers` | 每 10 分钟全量 | torrust 内部逐 swarm 加锁，单次持锁 O(该 swarm) |
| 节点状态中的 `count_peers` | 每 10 s | 同上 |
| 懒加载大 swarm | 每种子每节点一次 | 后台 HSCAN |
