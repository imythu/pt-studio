## 2. 测试环境与数据

| 环境 | 配置 |
|---|---|
| 单元 / 属性 | CI 普通 runner，无网络 |
| 集成 | docker compose：pt-tracker × 1～2、Redis 7.4 × 3（各自 ACL）、toxiproxy；`trk:*` 由测试桩写入（按 tracker-bridge LLD §1.1 的 Lua 脚本，保证格式一致） |
| 联调 | 全栈：pt-server（内核 + identity + torrent + tracker-bridge + accounting）、PG 17、Redis × 4（main + 三个角色）、pt-tracker × 3、HAProxy |
| 压测 | 负载机 2 台（各 16 vCPU）；pt-tracker 节点 3 台（各 8 vCPU / 16 GB，release，`target-cpu=x86-64-v3`）；Redis：tracker_state 3 分片 Cluster、acct 单实例（另测 Cluster）、tracker_sync 单实例（各 4 vCPU / 16 GB）；10 GbE 同机房 |
| 真实客户端 | 2 台 Linux + 1 台 Windows；客户端矩阵见 V7 |

**数据**：

- 小规模：100 用户（各状态、各 rsn）、1000 种子（open / owner_only / disabled / deleted / replaced、hybrid、纯 v2、`size = 0`）、客户端规则集 = tracker-bridge 预设。
- 大规模：30 万 passkey、100 万种子（含 10 万 hybrid → 110 万 `trk:t` 键）、`ps:*` 预灌 3000 万会话（压测重启场景）。
- 测试向量：`vectors/` 全部文件（LLD §10）。
- 负载模型（`ptt-bench`）：会话由下标确定性生成（用户、种子按 Zipf(s = 1.1) 分布、peer_id、端口、上传速度），累计值是时间的单调函数，因此生成器无状态且可算出每个用户的“真实增量”；事件比例：started 1%、completed 0.3%、stopped 1%、其余周期；IPv4 : IPv6 = 8 : 2；info_hash 百分号编码随机采用 4 种客户端风格。

## 5. 压测方案（NFR-PTT-001～004、009、010；V6）

目标：design/03 §3 的平均 **1.7 万次/秒**，高峰 **2～3 倍（3.4 万～5.1 万次/秒）**；单节点 NFR 2.5 万次/秒。

### 5.1 工具

- **`ptt-bench`**（自研，`bins/ptt-bench`，不发布）：tokio + hyper 客户端；每台负载机维持 2 万条 keep-alive 连接；按 §2 的会话模型生成真实分布的 announce（不同 peer_id、Zipf 种子热度、4 种 info_hash 编码风格、started / stopped / completed 比例）；开环发送（按目标速率定时发出，不因响应变慢而降速，避免协调遗漏）；输出 HdrHistogram（p50/p90/p99/p99.9/max）与错误分类；结束时输出“每用户真实增量”文件供对账。
- **`oha`**：固定单个 URL 的纯 HTTP 基线，用于区分框架开销与业务开销。
- **采集**：节点 `/metrics`（15 s 抓取）、`node_exporter`、Redis `INFO commandstats` / `latency`、`perf` 火焰图（P1、P7）。

### 5.2 场景

| 编号 | 场景 | 拓扑 | 负载 | 时长 | 通过标准 |
|---|---|---|---|---|---|
| P1 | 单节点基线 | 1 节点（8 vCPU），预热 1000 万会话 | 2.5 万次/秒恒定 | 30 min | 节点内处理 p50 ≤ 1 ms、p99 ≤ 10 ms（`pt_announce_duration_seconds`）；CPU ≤ 80%；错误率 0（busy = 0）（NFR-PTT-001、002） |

### 5.3 Redis 写入量验证（NFR-PTT-010、R6）

P3、P4 期间统计 `INFO commandstats`：每次 announce 的命令数 = `evalsha`（≈ 1）+ `xadd`（≈ 1）+ `hincrby`（≤ 3，期望均值 ≈ 1.1）+ `expire`（≪ 1）+ `hmget`（稳态 < 0.01）。结果写入压测报告，用于修正 redis-keys.md 的容量说明。

### 5.4 报告

每个场景输出：吞吐曲线、延迟分位数、CPU / 内存、Redis ops 与延迟、busy 与各失败类别、记账对账结果、火焰图（P1、P2、P7）、结论与调优建议。压测结果作为 V6 的验收依据记录到 `docs/reviews/`。

## 7. 通过准则

1. 全部 P0 需求的用例通过；安全与合规用例（006、013、018、120、122～125）任一失败为阻断。

3. 属性测试（TC-PTT-063）与混沌测试（TC-PTT-080）无违反“宁少记”不变式的反例。
4. 共享测试向量在 pt-tracker、tracker-bridge、accounting 三方全部通过。
5. 压测 P1、P3、P4、P6 达标（NFR-PTT-001～004、006）；P9 无内存增长。
6. 行覆盖率：`ptt-core` ≥ 95%（`accounting`、`clients`、`select` 100% 分支覆盖），其余 crate ≥ 80%。
